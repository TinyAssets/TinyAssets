## Goals / Non-Goals

Allow the owner to delegate read/message/control/costly actions to any OAuth client, inspect attribution, edit grants and revoke immediately. Cross-user isolation is the only immutable platform behavioral invariant: an outside client acts strictly as the authorizing owner within that owner's editable grants. No brand-specific adapter, platform model, second public endpoint or replacement approval system.

Talk-back (`read_graph target=live` and per-client outbox), A2A client/server, and outbound MCP attachment are separate later changes, as listed in proposal.md. This change does not claim to complete the founder's entire two-way vision.

## Decisions

### 1. Bind client identity separately from account identity

Every authenticated OAuth bearer request first binds the existing owner/home and a verified client classification. Outside clients additionally carry an `outside_client` value: verified issuer, exact OAuth client id (CIMD URL or DCR id), registration kind, metadata name/logo/redirect host, and metadata availability/source. Resolve identity from validated AuthKit claims or an authenticated AuthKit lookup bound to this token; never infer it from User-Agent, an MCP payload, OAuth audience, an arbitrary header or a claimed brand. Do not assume `client_id` or `azp` is present until verified against live AuthKit. Contradictory/missing client identity refuses before data or effects and directs reconnect; no fallback to unrestricted owner authority.

Issuer + client id identify the app registration; owner + universe + that pair identify its grant. The same owner on two clients still has one account/home, with independent grants. CIMD/DCR metadata is display-only, sourced from the registered metadata with safe rendering and existing URL-fetch protections; changes to a name/logo/redirect do not mint identity or authority. Missing optional metadata is explicitly unavailable; display the exact id, never fabricate a name. Redirect host comes from registered redirect URIs, not a caller-provided redirect argument. Multiple hosts remain a displayed set.

Here owner means the authorizing user; existing universe ACLs remain independently required. Connected apps and the client audit are readable only by that authorizing user, never by another user merely because they share universe access.

The configured first-party TinyAssets web/phone/desktop app is **not an outside client**, including when it calls `/mcp`. Classify it only by a verified issuer + exact client-id allowlist in platform configuration (seeded from `TINYASSETS_ONBOARDING_APP_CLIENT_ID`, `tinyassets/onboarding/__init__.py:156`); never by name, redirect, headers or an owner-editable grant. Its ordinary owner/ACL checks remain, but outside grants and the outside kill switch do not apply. First-party bearer identity alone still cannot approve or edit grants: those actions require the separate protected interactive owner session. OAuth bearers are not sender-constrained: a stolen token acts as its verified client until expired or fenced; display metadata cannot fix token theft.

### 2. Store current owner grants; tokens are not the grant store

An owner-scoped record keyed by `(owner_user_id, universe_id, issuer, client_id)` holds explicit agent ids or owner-selected `*`, a set of levels, optional expiry, active/revoked status, monotonically increasing revision/authorization generation, timestamps and last-used. A unique key makes concurrent first calls snapshot one owner-editable starter default; the initial suggested setting is `agents=[main]`, `levels=[read,message]`, `message_mode=message-only`. The owner can change agents, levels and message mode before connecting a new client; edits to the starter do not reset existing grants. Each grant also holds `message_mode` (`message-only` or `message-and-act`). A revoked tombstone is retained; presenting an old token cannot recreate defaults.

The named new store is **OutsideClientAuthority**, a daemon-owned SQLite database at `<data>/.outside-client-authority.sqlite3`, outside every universe directory and inaccessible to universe code. Tables hold `client_grants` keyed by owner/universe/issuer/client, `client_fences` keyed by owner/issuer/client (no universe), `owner_client_defaults`, audit, credential-generation bindings, and an outside-admission switch. All serving workers must use the same durable database through one platform authority service; no per-worker/per-universe copies or positive authorization cache. SQLite transactions serialize revision edits, generation binding, revoke and effect admission; acknowledge revoke only after commit. Workers on another host call that same authenticated authority service rather than open a replica or SQLite over a network filesystem. A missing/unreachable store fails closed for outside clients. Register this platform-root store with the storage registry and backup lifecycle; reconcile placement with `platform-state-outside-command-centers`. Never initialize an empty replacement on loss of the authority store.

Grant resolution follows authenticated home resolution. For a new user, verify client identity and the owner/client revocation fence first; the existing first `converse` home-creation path snapshots the owner's starter grant in the same admission step, before delivering the message. This narrowly permits the existing private-home bootstrap, not arbitrary control. An early no-home status response requires verified active client identity and its revocation fence, returns only the caller's no-home state, exposes no universe content and does not provision. An existing home never uses this bootstrap to reset a grant or bypass denial.

Levels are independently editable capabilities, not cumulative numeric ranks. `costly` adds authority for spend/publish/external posts to the required ordinary operation level; it does not itself imply control, access to every agent, consent or approval. Agent ids are resolved through the existing addressed-agent authority, not display names. `*` explicitly includes future owned agents; a fixed list does not. Owner edits are revision-checked and atomic; stale edits return a conflict and current readback. Widening, reconnection and revocation use the protected owner app service. A bearer may request a change through the approval sheet but cannot apply it, even with `control` or `costly`.

The OAuth scopes and advertised OIDC security schemes remain unchanged. Per-action and per-agent authority is read from the current grant, so narrower rights and revoke do not wait for token refresh. Full-account OAuth scopes and UI-only filtering were rejected because neither enforces owner edits at dispatch.

### 3. Enforce the resolved operation and all affected resources

One daemon-side admission path checks authenticated owner/home and existing ACLs, active client generation, current grant, resolved resource/agent scope and operation levels before returning data or committing work. All public handle paths use it, including aliases, bulk operations and embedded app/page bridges. Every bearer HTTP surface must use the same admission or explicitly refuse outside clients; the complete route disposition and file:line inventory is [bearer-surfaces.md](bearer-surfaces.md). This slice refuses outside clients on all listed app HTTP routes, while preserving first-party access. Transport discovery authenticates and checks active client identity; it grants no content authority.

| Existing handle | Required client grant |
|---|---|
| `get_status`, `read_graph`, `read_page` | `read`; return only resources within allowed agent scope |
| `converse(agent_id)` | `message` for the resolved agent, defaulting an omitted selector to `main`; its reply belongs to that admitted message |
| `write_graph`, `write_page` | `control` for all affected agents/resources; add `costly` for spend, publication or external posts |
| `run_graph` | `control` for its resolved execution scope; add `costly` for chargeable/external effects at dispatch |

An agent-scoped read filters mixed collections before serialization; explicit out-of-grant targets refuse. Shared command-center resources affecting or exposing multiple agents require coverage of every affected agent; no implicit association with main. Account-wide control requires explicit `agents=*` and `control`; sensitive effects additionally require `costly`. Owner-app Connected apps remains available through the protected owner door. The connector's `target=access` projection reports the caller's own effective client grant and only otherwise authorized access data, without other clients' private details. Global summaries, page content, snippets, search results and status conversation inclusions cannot leak excluded agents. An unresolved scope refuses clearly instead of becoming account-wide.

Message delegation is an owner-editable per-client choice. In `message-only`, downstream reads/effects are bounded by the client's current agents and levels; main cannot borrow broader resident-agent authority. In `message-and-act`, the owner explicitly delegates the addressed resident agent's own powers for work caused by admitted messages, including its authorized downstream delegation, subject to existing owner/resource authority, spend policy and sensitive-action approvals. This option does not widen direct bearer tool calls or permit grant editing/approval. Both modes persist outside-client origin through turns, runs, nested/scheduled work and pending actions, and recheck active generation, expiry, revocation, the original addressed agent's current message permission and the current message mode at every downstream admission/resume. Narrowing to message-only immediately restores the client's agent/level bounds. Ordinary inference for an admitted message follows existing owner model/consent policy. Universe/owner-origin automations and queued runs have their own trusted provenance, are not outside-client work, and are not held by this change; a client-origin schedule retains its client origin.

For an authenticated owner-scoped denial return an MCP error naming `client_grant_missing`, required level and safe target/agent scope, with direction to Connected apps. For example: `Missing control grant for agent researcher; ask the owner to edit this app in Connected apps.` Resolve cross-user authorization first and retain uniform not-found/auth refusal rather than revealing a foreign agent's existence. No side effect on denial. Unknown effect classification follows the owner's existing editable policy in inline-connect-and-approve; it does not silently receive control/costly authority.

### 4. Connected apps, audit and immediate revoke

The protected app lists each connected client with exact id, name/logo/redirect hosts (or unavailable), allowed agents/levels/expiry, status and last authenticated use. Owners can edit or revoke a single client without changing another client or owner. Last-used records authenticated attempts, including grant denials, with their outcome; unauthenticated spoofed requests do not advance it. Reuse `target=access` for the constrained connector readback and existing app owner service for full inventory/edit/revoke; do not introduce a top-level tool or bearer grant-management bypass.

Record owner, universe, verified client identity/metadata snapshot, resolved addressed agent/resource, handle/operation, request/turn/run reference, grant revision, timestamp and outcome (allowed, denied, pending, executed, revoked) in durable owner-readable audit events. Grant edits/revoke record the interactive owner actor. No raw bearer, refresh token, credential, prompt or full response is copied into the audit. Preserve client origin in the existing turn/run/activity records, not a competing execution identity.

Revoke atomically marks the grant inactive, increments its authorization generation and invalidates all access/refresh-token use for that owner/client at TinyAssets, across universes sharing that owner/client authorization. Keep per-universe grant edits distinct from Connected apps' app-wide revoke. Maintain a durable owner/client revocation fence consulted on every request and effect dispatch across daemon workers; cached JWT validity, open MCP sessions and refresh cannot bypass it. AuthKit consent/session/token revocation should also run where supported, but local token invalidation does not depend on that API succeeding. Never report success before the local fence is durable and effective across workers.

A reconnect requires fresh owner-interactive authorization bound to a new generation; all pre-revoke credentials stay invalid. Implementation must prove how AuthKit exposes issuance/session identity to distinguish generations, using verified OIDC `auth_time` (unchanged by refresh) or AuthKit `sid` as concrete candidates. If neither reliably distinguishes fresh consent, the owner can re-consent in the protected app: bind a newly completed interactive OAuth exchange to a server-held credential-family handle and the new generation, accept only that family, and keep all pre-revoke/unbound tokens fenced. A token issue time or a client-supplied generation is insufficient. This owner recovery path is required before enforcement; a permanent reconnect lockout is not an acceptable fallback. Merely clearing the tombstone on a new-looking token is forbidden. Revocation fences queued/resumed work and pending approvals before any new admission. Serialize revoke and effect admission: an irreversible effect already committed before the revoke boundary cannot be undone; no effect admitted after it succeeds. Preserve the audit and give honest in-flight receipts.

### 5. Sensitive actions use the existing approval sheet

Use inline-connect-and-approve's existing protected bound action and owner-editable standing rules. Add verified outside client id/metadata and grant generation/revision to its provenance and owner preview alongside addressed agent and normalized action. For direct calls and message-only work, a required missing level returns a clear grant refusal; message-and-act work uses the resident agent's delegated powers under decision 3; approval of an effect alone does not widen a client grant. The owner can edit the grant separately and retry. Once the applicable grant/message-mode policy admits the request, sensitive actions enter the existing approval flow (including its explicitly owner-authorized standing decisions), without inventing a second approval policy here.

Bearer clients can request/read pending actions and receive a protected approval link, but can never approve, retry with dispatch authority, mint owner proof or use rule/grant-write aliases to self-approve. Owner approval rechecks the live grant/message-mode policy and provenance before dispatch; stale/revoked requests do not execute. URL-mode elicitation may convey the existing link when supported; a normal link remains usable without assuming Muse implements elicitation. Custom-agent control depends on addressed-agent-control-provenance; sensitive dispatch depends on inline-connect-and-approve. Until those paths are available, return an honest unavailable/refusal with no bypass.

## Risks / Trade-offs

- AuthKit client claims, metadata lookup and per-client token/session revocation are unverified (research C4) → prove the binding and reconnect generation before implementation acceptance; retain a local durable invalidation fence.
- Shared command-center content can span agents → scope all contributors before returning data; avoid treating a page or status summary as globally readable under main-only grants.
- Queued work could launder an outside client's authority → persist client origin beside addressed-agent provenance and recheck at dispatch, not only at ingress.
- Existing primary connectors must not silently lose rights → preserve their current authority in explicit migration grants until the owner changes it, or obtain the owner's visible choices before cutover; never infer privilege from a brand name.
- Muse's callback remains unverified → keep its rendered connection as additional evidence; mandatory two-client proof and first-party regression proof cannot be waived by a Muse blocker.

## Migration Plan

Enforcement has a hard prerequisite: `inline-connect-and-approve` must provide a deployed, tested protected owner session, and Connected apps must let that owner widen/narrow grants, change the starter/message mode, revoke and recover a revoked connection from day one. Merely having stubs or a link is insufficient. Verify this through the first-party app before enabling enforcement. Reconcile addressed-agent provenance and AuthKit bindings, deploy additive store/provenance and admission support, then reconcile the cutover inventory.

Existing primary claude.ai / ChatGPT connections retain their pre-cutover authority via explicit grandfathered migration grants (including message-and-act where needed to preserve existing delegated behavior), until the owner narrows them, or the owner chooses their grants visibly in Connected apps before enforcement. Apply this by verified owner/client binding, not brand. If historical identity cannot be proven, notify the owner and complete protected reconnect/selection before that owner's cutover; do not silently replace established authority with the new-client starter. Do not infer full rights merely from a past powerful call. Hold only work known to originate from an outside client whose attribution cannot be reconciled. Trusted universe/owner-run automations and queued runs continue; unknown historical audit remains unknown rather than being relabeled as an outside client.

The NEW admission code must ship an operator-controlled durable `outside_admission_enabled` kill switch in OutsideClientAuthority before/with enforcement. False, unreadable or invalid state refuses outside ingress and downstream admission on every worker, including existing sessions, message-and-act work and queued resumes. Verified configured first-party app clients and trusted owner/universe work are exempt. A deny-only process override may force false but can never override durable false. Test activation and next-call refusal on multiple workers before cutover.

Before/at rollback, set that switch false and verify outside refusal plus first-party read/write/run and protected grant editing still work. Keep the new identity/admission layer and authoritative store running while rolling back other components, or first backport the same classification and deny layer to the rollback artifact and prove it. A raw rollback to the old bearer-only binary is prohibited: it cannot honor the switch. Preserve additive grants, fences and audit, and never restore a backup that revives revoked generations. No migration, kill-switch implementation or deployment occurs in this docs-only round.

Acceptance requires focused auth/grant/revoke/provenance/HTTP tests, affected heavy tests and ruff, one floor/correctness cross-family implementation review, strict OpenSpec validation, public canary and deployed SHA assertion. Mandatory rendered live proof uses two independent clients on one account (claude.ai + ChatGPT, or OpenClaw): distinct editable grants, a missing-grant refusal, revoke effective on the very next call, the other client unaffected, and first-party app read/write/run plus owner grant widening after cutover. Muse callback/connect/grant/approval proof remains additional; record its exact blocker if unavailable, never substitute that blocker for the mandatory live pass. Sync/archive only after implementation and mandatory proof; proposed requirements are not as-built truth.
