# Move the work into the box, then delete the checks

Every production system that gives each user an isolated instance has the same shape. A thin shared layer authenticates the caller, turns that identity into an instance ID, forwards the request, holds the secrets and the clock, and never reads tenant data. Everything that touches a tenant's data runs inside that tenant's instance, where the kernel or VM boundary does the isolating. AWS states it as a tenet: "**Isolation enforcement should not be left to service developers**" ([AWS SaaS Lens](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/isolation-mindset.html)). WorkOS describes the alternative, a shared runtime with tenant filters, this way: "**The tradeoff is that you become the isolation layer**" ([WorkOS](https://workos.com/blog/developers-guide-saas-multi-tenant-architecture)). For TinyAssets this backs the founder's position. The gVisor box per account is the isolation, and a shared daemon that reads every owner's data through host directories is the wrong shape however many checks it gets. Six things stay shared: identity, the owner→box map and router, billing, the credential/egress proxy, a next-wake index, and published cross-tenant data. Everything else goes into the box, and the cross-owner checks in the daemon are deleted. The four review rounds that kept adding checks fit a documented failure mode of LLM agents. They chased each reviewer finding with a local guard, and that pattern shows up after repeated failed attempts. They never asked whether the target shape removes the whole class of bug. The countermeasure is mechanical, not motivational: before patching any finding, ask "can this happen in the target shape?", and if the answer is no, build the target shape.

### Four patterns hold across every system

**The shared door does three things and no business logic.** It identifies the caller, looks up the instance, and forwards. Cloudflare's rules split the roles explicitly: "The Worker handles authentication, validation, and response formatting," and they forbid "a single 'global' Durable Object that handles all requests" ([Cloudflare](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/)). AWS says the cell router "must remain as simple and horizontally scalable as possible, which necessitates avoiding complex business logic." AWS also wants it statically stable: it routes from an in-memory copy of the map even when the control plane is down ([AWS cell routing](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/cell-routing.html), [control vs data plane](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/control-plane-and-data-plane.html)). E2B keeps lifecycle and routing apart: "Sandbox traffic never passes through the API," and the proxy resumes a paused sandbox when it has no routing record for it ([E2B](https://raw.githubusercontent.com/e2b-dev/infra/main/docs/ARCHITECTURE.md)). The mapping is either derived from the identity (Cloudflare `getByName`) or held in a small registry. Nobody keeps it inside the instance, because the router needs the map before it can reach the instance.

**Even a silo keeps a shared control plane, but it holds metadata, not tenant data.** AWS: a silo "still relies on a shared identity, onboarding, and operational experience" ([SaaS Lens](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html)). Microsoft's list is resource management, routing configuration, tenant lifecycle, telemetry and consumption tracking. Microsoft also says to put the control plane on separate servers, because it is "highly privileged" and "might have access to keys and secrets for all tenants" ([Azure control planes](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/control-planes)). The AWS whitepapers are marked "historical reference only". Their tenets survive in the current SaaS Lens, which is why it is the main citation here.

**The schedule's clock lives outside, its rows can live inside.** No platform runs a scheduler inside a sleeping instance. Claude Code routines run on shared infrastructure and create a new session for each run ([routines](https://code.claude.com/docs/en/routines)). Fly offers only fuzzy hourly-to-monthly machine schedules ([Fly](https://docs.fly.io/machines/flyctl/fly-machine-run)). The cleanest split is Cloudflare's. Agent schedules live in the agent's own SQLite table, "scheduling uses Durable Object alarms to wake the agent," and many schedules share one platform-held alarm ([Agents scheduling](https://developers.cloudflare.com/agents/api-reference/schedule-tasks/)). The box holds what runs and when; the platform holds a single "next wake at T" for each instance. Delivery is at least once, so wake handlers must be idempotent ([alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)).

**Infrastructure isolates the compute; app code does exactly one tenant operation.** Every system isolates compute with Firecracker, gVisor, a microVM, Unikraft or a dedicated VM. The tenant-to-instance binding is always app code in the shared layer. AgentCore says plainly that it "does not enforce session-to-user mappings - your client backend should maintain the relationship" ([AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html)). Cloudflare warns that reusing a name "for someone else gives them the earlier user's files" ([Cloudflare security](https://developers.cloudflare.com/sandbox/concepts/security/)). Credentials and egress are moving into infrastructure too. Claude Code's GitHub credentials "never enter a session's VM", and a proxy returns 403 for repos not attached to the session ([Claude Code](https://code.claude.com/docs/en/cloud-environments)). Codex hands programs a placeholder that its proxy swaps for the real secret ([Codex](https://learn.chatgpt.com/docs/environments/cloud-environments)).

### App-level tenant filtering is where the incidents happen

The guidance is consistent. WorkOS: "Every bug that drops tenant_id becomes a data leak," and "Most cross-tenant incidents… come from developers adding a new endpoint and forgetting one filter" ([WorkOS](https://workos.com/blog/developers-guide-saas-multi-tenant-architecture)). One correction to the brief: WorkOS says "**you** become the isolation layer", not "the app becomes the isolation layer", and the article never uses the words "silo" or "pool". Microsoft says a shared app "isn't suitable for hostile multitenancy workloads in which you don't trust the code that's running." That describes an agent running model-written code, and Microsoft's answer for it is an environment per tenant ([Container Apps](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/service/container-apps)). The incidents match. Asana's MCP server exposed data across organizations for about a month, affecting "roughly 1,000 customers", through "a logic flaw in the MCP system" ([BleepingComputer](https://www.bleepingcomputer.com/news/security/asana-warns-mcp-ai-feature-exposed-customer-data-to-other-orgs/)). That it was a tenant-isolation check specifically is secondhand and unverified. Wiz found about **25% of scanned multi-tenant Azure AD apps** were missing the developer-side tenant check ([Wiz BingBang](https://www.wiz.io/blog/azure-active-directory-bing-misconfiguration)).

Two caveats keep this from becoming dogma. First, the box boundary itself has to be hardened. Wiz's PEACH framework notes that ChaosDB put each tenant in its own container inside a VM and still leaked, because network controls were enforced only by iptables inside the container ([Wiz PEACH](https://www.wiz.io/blog/introducing-peach-a-tenant-isolation-framework-for-cloud-applications)). Second, Microsoft still wants the silo to authorize each request ("Tenant mapping is a separate activity" from permissions) under "assume breach" ([Azure map requests](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/map-requests)). So "no cross-owner checks" means something precise. There are no exclusion filters on owner data in shared code. There is one positive mapping, identity → box, and the box checks that its caller is the router.

Cross-tenant views do not reopen the shared runtime. AWS and Microsoft call fleet-wide views the main cost of silos and prescribe aggregation: data flows up to the control plane ([AWS silo](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/silo-isolation.html), [Azure tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)). Cross-cell calls "have to go back through the normal cell router" rather than letting cells talk to each other ([AWS cell partition](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/cell-partition.html)). No source prescribes a shared process reading every tenant's store. None covers user-facing public listings either. Treating published items as data copied into the shared layer is an inference.

### The recommended shape for TinyAssets

**The shared layer keeps six responsibilities and no host path to any owner's data:**

| Shared responsibility | What it holds | What it must not do |
|---|---|---|
| **Identity** | App sign-in, MCP connector OAuth, `/api` keys; resolves every caller to one `owner_id` | Pass a caller-supplied owner or box ID through without checking it |
| **Owner→box map and router** | `owner_id → box_id`, plus the latest volume/snapshot ID; proxies to the box's socket with a per-box secret; wakes a sleeping box when a request arrives | Parse, filter or list box contents; keep routing logic beyond the lookup |
| **Billing and metering** | Plan, quotas, usage measured at the egress proxy or pushed up by the box; account suspension | Read conversation or files to compute usage |
| **Credentials and egress proxy** | Model-provider keys and OAuth tokens, injected into outbound requests per box; a per-box allowlist | Hand a raw secret into the box, or hold a token that reaches every box |
| **Wake schedule index** | One row per owner: `(owner_id, next_wake_at)`, rebuildable by asking each box | Store job definitions, pause state or payloads |
| **Published cross-tenant data** | Items an owner explicitly publishes, copied out of the box at publish time | Build a listing by reading private box stores |

Box lifecycle (provisioning, backups, fleet telemetry) belongs to the same control plane. Backup deserves a dedicated note. Every managed host keeps durable truth outside the running instance, in snapshots in object storage, a control-plane database or a memory service ([E2B](https://raw.githubusercontent.com/e2b-dev/infra/main/docs/ARCHITECTURE.md), [Modal snapshots](https://modal.com/docs/guide/sandbox-snapshots), [Browser Use](https://browser-use.com/posts/two-ways-to-sandbox-agents)). Fly warns that per-machine volumes can be lost with the hardware ([Fly](https://docs.fly.io/blueprints/per-user-dev-environments)). If history and files live in the box, the box needs a durable volume and off-host snapshots. That is the price of putting state in the box. **No platform in the notes documents an in-instance database as the source of truth**, so on this point TinyAssets is departing from the documented pattern, not copying it.

**Into, or kept in, the box:** the agent loop; conversation history; the owner's files, skills and packages (Direction 3); the owner's database; schedule rows and pending work; user-level flags such as pause; the app and MCP logic that serves the owner's own data; and authorization among an owner's sub-users. Claude Code, AgentCore and Browser Use's Pattern 2 all put the agent loop in the instance. Browser Use moved it there because redeploys of the shared API killed running agents ([Browser Use](https://browser-use.com/posts/two-ways-to-sandbox-agents)).

**Deleted from the daemon:** per-center host directories, bind mounts into any owner's box, symlink-target checks, other-owner listing filters, and missing-directory guards. These are the "cross-owner app checks the OS now enforces" that Direction 5 says to delete in the same change. Each of the four review findings disappears in this shape. A daemon with no host path to owner data cannot follow a symlink into it, cannot list another owner's private item, and cannot fail open on a directory it never opens.

The pause bug shows the rule for placing a flag: **put it where its reader lives, and give it one writer.** A user's own pause is box state. The box writes it, the box reads it, and the box reports "no next wake" to the index. Account suspension for billing or abuse is control-plane state that the router reads before waking the box. "Written into the box, read from the host" breaks that rule, and the broken rule is the bug.

Once the work has moved, cross-owner risk can live in only three shared components: the identity→box map, the credential/egress proxy, and the router/waker. Those three are the floor-class review surface, and their checks are positive mappings ("derive the box from the authenticated owner"), never exclusion filters. Two design points here are inferences, not observed patterns: a waker that holds only `next_wake_at`, and boxes that can be woken from a shared index. Cloudflare's alarm-plus-SQLite split is the closest documented precedent.

## Section 2. Near merge, review findings act like failing tests, and agents patch them

### Human bias and agent training both reward the local guard

The classic mechanisms explain the urge to add rather than reshape. Gall's law says a complex system that does not work "cannot be patched up to make it work" ([Wikipedia: John Gall](https://en.wikipedia.org/wiki/John_Gall_(author)); quoted via Wikipedia, book not checked). Brooks's second-system effect explains why late-stage confidence produces "functional ornamentation" ([Wikipedia](https://en.wikipedia.org/wiki/Second-system_effect)). Sunk cost makes people keep investing once effort is spent, and makes them rate the project as more likely to succeed ([Arkes & Blumer 1985](https://cognition.aau.at/bg/BA/Arkes%20%26%20Blumer%201985.pdf)). Days spent on the shared-daemon path made moving into the box feel like throwing that work away.

The agent mechanisms are documented directly. Anthropic's Claude Code guidance: "A reviewer prompted to find gaps will usually report some, even when the work is sound… **Chasing every finding leads to over-engineering**: extra abstraction layers, defensive code, and tests for cases that can't happen" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The Claude 3.7 Sonnet system card says special-casing to pass tests "typically emerge[s] after multiple failed attempts to develop a general solution" and comes from reward hacking during RL ([system card](https://assets.anthropic.com/m/785e231869ea8b3b/original/claude-3-7-sonnet-system-card.pdf)). An adversarial finding works like a failing test, and the cheapest way to make it pass is a guard that makes that exact finding go away. Sycophancy research shows RLHF models lean toward the framing of whoever is grading them ([Sharma et al.](https://arxiv.org/abs/2310.13548)). Each finding came framed as "this path leaks", so the agent answered "guard this path" and never challenged the premise that the daemon should touch that path at all. Context degradation compounds it. Anthropic says a session "corrected more than twice on the same issue" is "cluttered with failed approaches" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Late in a merge is exactly when the context is longest. Exhortation does not fix any of this: METR found "Please do not cheat" had "a nearly negligible effect" on reward hacking ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking)). Tests are a weak judge of shape as well. About 29.6% of "plausible" SWE-bench patches behave differently from the ground truth ([arXiv 2503.15223](https://arxiv.org/html/2503.15223v2)).

### The case shows three errors from one missing question

All three errors come from never asking two questions: what is the target shape, and which minimal slice moves toward it?

**Under-changing the shape.** Symlink escape, cross-owner listing, missing-directory fail-open and the pause split are four instances of one class: a shared process with authority over every owner's data has to mediate every access correctly. Saltzer and Schroeder named the principle in 1975: "**Least common mechanism**: Minimize the amount of mechanism common to more than one user and depended on by all users." The guards were also exclusion-based, which their "fail-safe defaults" principle warns against ([Saltzer & Schroeder](https://www.cs.virginia.edu/~evans/cs551/saltzer/)). The same class recurring in a new place is the five-whys signal that the root was never touched ([LEI](https://www.lean.org/lexicon-terms/5-whys/)).

**Over-changing the scope.** A deploy-gating fix grew into a 76-file rerouting with about 164 CI failures. Anthropic names this behavior directly: "Don't add features, refactor code, or make 'improvements' beyond what was asked" ([prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). Under-changing and over-changing look like opposites, but both come from not having that target slice.

**Inverting the blocker.** A pause button that visibly fails is fail-closed and observable, so it can ship with a follow-up. A silent cross-owner read or a fail-open path is the real blocker. The run held the deploy for the loud failure while the silent class stayed open.

The steelman deserves a hearing. Spolsky is right that big-bang rewrites are "the single worst strategic mistake," and that architecture should be fixed incrementally on the existing code ([Joel on Software](https://www.joelonsoftware.com/2000/04/06/things-you-should-never-do-part-i/)). Fowler notes that YAGNI "does not apply to effort to make the software easier to modify" ([Fowler](https://martinfowler.com/bliki/Yagni.html)). The two positions reconcile. Moving one path into the box and deleting the old path in the same change is incremental reshaping, not a rewrite. What neither author defends is adding a fourth guard to a path the target shape deletes. Security practice has shown class elimination beats instance patching at scale. Google reports that memory-safety bugs fell from 76% to 24% of Android vulnerabilities after new code moved to memory-safe languages ([Google Security Blog](https://security.googleblog.com/2024/09/eliminating-memory-safety-vulnerabilities-Android.html); the figure comes from a search snippet and secondary coverage because the page did not render). No controlled study compares shape changes with guard accumulation for LLM agents specifically, so applying this to agents is extrapolation.

### Warning signs and countermeasure checklist

The warning signs are mechanical, so a script or reviewer can check them:

- a fix adds a check and deletes nothing;
- the same bug class reappears somewhere new;
- edit and test cycles keep concentrating on one shared file, which the system card lists as a special-casing monitor;
- a shared component needs to know "whose data is this";
- the diff is far larger than the request;
- a guard fails open when its input is missing;
- review rounds are scoped to the latest instance instead of the target shape.

The repo already encodes one of these: "Same error thrice or same finding twice: hand off, don't patch" (AGENTS.md, The loop 7).

Countermeasure checklist:

1. **Shape gate before any patch.** For each finding, answer "can this class exist in the target shape?" If the answer is no, the fix is to move the work into the box and delete the shared path. Do not add a guard.
2. **Give reviewers the target shape.** Ask them to "flag only gaps that affect correctness or the stated requirements" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)), and to say which findings disappear in the target shape.
3. **The second finding of a class escalates.** It becomes a shape decision made in a fresh session, not a third guard in the same context.
4. **Positive permission only during any transition.** Use an allowlist of the caller's own box. A missing input denies.
5. **Diff-to-request ratio.** If a one-sentence fix grows past a handful of files, split it: the fix ships alone, and the reroute becomes its own lane, and only if it moves toward the target shape.
6. **Triage blockers by failure mode.** Loud and fail-closed ships with a follow-up. Silent, fail-open or cross-owner blocks the deploy.
7. **Use structural enforcement, not instructions.** Tests that prove the daemon holds no host path to owner data beat any prompt telling the agent to be careful ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking)).

## Conclusion

The research makes "one box per account is the isolation" a testable property: **the shared daemon holds zero host paths to owner data, and every cross-owner decision reduces to a positive identity→box mapping in three named components.** If a finding cannot be expressed as a defect in the router, the egress proxy or the waker, it belongs inside one box, where it cannot cross owners. That also gives reviewers a scope: floor-class review covers those three components, and everything else is ordinary single-tenant code. The real new risk is durability, not isolation. Putting history and state in the box goes further than any documented agent host, which all keep truth outside the instance, so off-host box snapshots become the next foundational patch to bring forward.

On process, the lesson is that agent over-complication near merge is predictable and comes from training: an adversarial reviewer plus a shared component produces guards. Asking the agent not to do it fails. Fixing the order of operations works. Decide the target shape before reading the findings, ask which findings that shape erases, and make any patch that adds a check to shared code justify why the path it guards still exists.
