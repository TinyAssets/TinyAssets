## Context

Founder framing (2026-10-04, binding revision): users build and merge patches on **their own** connected platforms and build custom tools for any software or platform. Issues, pull/merge requests, pushes, merges, and comments are examples of consequential external writes, not a closed list. Agents, tasks, graphs, and their custom tools must share the same effect boundary. Subscription connections are the default; successful subscription-only review is a delivery requirement. The founder is an ordinary user whose patch intake is a receiver node other users send to, with no platform privilege.

Baseline inspected: `811b4dd3b18ef369433b48ebeb7a08c7c6be157e`, equal to this worktree's `origin/main`. These are proposed requirements, not shipped behavior.

### CLI and documentation evidence, rechecked 2026-10-04

Commands actually run locally, help/version only; no model, delegated agent, login, or account operation:

```text
claude --version
claude --help
codex --version
codex exec --help
codex --help
```

Versions: **Claude Code 2.1.289**, **codex-cli 0.160.0**. Help demonstrates flag availability, not successful enforcement in a production launch. Proposed argument combinations below were not executed. Empty values must be passed as actual empty argv elements, not shell quoting that Windows might discard. This revision ran no model calls or sub-agents and changed no product code.

**A — REFUTED as stated; the complete launch-proof argument is valid.** Local help and the [CLI reference](https://code.claude.com/docs/en/cli-reference) support `--tools ""`, strict empty MCP configuration, setting-source selection, and safe mode. Help explicitly preserves admin-managed policy in safe mode; `--bare` excludes OAuth authentication. These controls plus proof that *all* executable configuration is absent would qualify Claude as text-only. The false premise is that managed sources are exclusively host files.

The [managed-settings documentation](https://code.claude.com/docs/en/managed-settings#where-each-mechanism-stores-the-policy) identifies `/etc/claude-code/managed-settings.json`, `/etc/claude-code/managed-settings.d/*.json`, and `/etc/claude-code/managed-mcp.json` on Linux. A Linux container uses these paths **inside its filesystem**, including image layers and mounted configuration; the docs give no separate container path. Other sources include server policy, parent-supplied settings and helpers configured by managed policy. Windows registry/macOS MDM are not native Linux-container sources; the launch must not inherit a WSL/desktop/SDK policy bridge.

[Server-managed settings](https://code.claude.com/docs/en/server-managed-settings#platform-availability) can arrive using `CLAUDE_CODE_OAUTH_TOKEN`, including in a fresh config directory. They support hooks; noninteractive `claude -p` applies approval-requiring settings for that run. Startup fetch and later refresh are separate from the cache at `~/.claude/remote-settings.json`. Repository confirmation: `rg -n 'CLAUDE_CODE_OAUTH_TOKEN|CLAUDE_CONFIG_DIR' tinyassets/providers/base.py` finds subscription snapshot conversion to that token at lines 858-882. **Conclusion:** container ownership plus absence of local managed files is insufficient for this adapter's token path. A successful local scan must not certify remote-policy absence. Decision 1a defines the complete proof and a contained alternative so this correction does not become a blanket subscription ban.

**B — VERIFIED as a safety contract, not as current deployment behavior.** A reviewer whose tools cannot reach external effects or durable state is safe for this purpose: only its parsed verdict can affect the separately authorized write. Tools can corrupt scratch data or give a bad verdict, but that is not additional effect authority; text-only inference can also give a bad verdict. This is `contained`, never text-only. `codex exec --help` exposes sandbox/config/ephemeral controls, not all-tools-off. The [official command reference](https://developers.openai.com/codex/cli/reference) documents execution controls, not a guarantee that patch tools disappear. Re-fetched matching-tag [tool registration](https://raw.githubusercontent.com/openai/codex/rust-v0.160.0/codex-rs/core/src/tools/spec_plan.rs) with `Invoke-WebRequest -UseBasicParsing`: the `ApplyPatchHandler` registration tests environment presence and model patch support, independently of shell enablement. Thus disabling shell does not remove patch tools on this supported profile; this is not a claim about every possible future Codex build.

Read-only source inspection commands were `Get-Content tinyassets/providers/provider_jail.py`, `Get-Content tinyassets/providers/jail_seccomp.py`, and `rg -n 'def default_view|def jail_argv|def _network|def confine_launch|PROVIDER_LIMITS' tinyassets/providers/provider_jail.py`. Existing `default_view` (line 287) mounts owner data read/write; `_network` (664) and `confine_launch` (696) add the egress socket and optional engine relay even for a narrowed view. `jail_argv` (524) supplies namespaces and mount isolation; `jail_seccomp.deny_program` (117) supplies syscall restrictions. Neither seccomp nor an empty network namespace removes the proxy capability. Decision 1b specifies the required review profile using this machinery.

**Network qualification:** literally denying all communication to the entire subscription CLI also prevents remote inference. Deny all *general network and effect authority*, with a separately bounded inference-only transport. A general HTTPS proxy or provider-host allowlist is insufficient. That transport and credential separation must be implemented and proven as part of this change, not assumed to exist or replaced by an API-key requirement.

## Goals / Non-Goals

Goals: unblock subscription-only users with proven text-only or contained review; retain mandatory review; make cross-family choice owner-bound and auditable; preserve every receiver owner's later independent steps and visible recovery when a connection write fails.

Non-goals: product implementation in this lane, switching the conversation model, bypassing managed policy, reverse-engineering subscription inference endpoints, borrowing founder credentials, adding destination-specific effectors, automatically rewriting existing user workflows, and semantic duplicate detection in this delivery slice.

## Decisions

### 1. Accept two proven review tiers

Use a vendor-neutral, adapter-verified per-launch capability descriptor with tier, executable/adapter and image versions, configuration/mount/transport digests, proof version, and reason. Owner-authored metadata may nominate a candidate but cannot certify enforcement. The review purpose accepts `enforced_text_only` **or** `contained`; routing and direct adapter calls check the same descriptor. Preserve `ModelConfig.text_only` and `supports_text_only` as strict tool-free contracts for callers that require them. Add a distinct review-safety requirement to the server-owned purpose; do not label contained execution text-only merely to pass the current boolean check.

| Tier | Meaning | Eligible for required review |
| --- | --- | --- |
| `enforced_text_only` | Only bounded review text enters inference; no tools, MCP/apps, hooks, subagents, session continuation, or other executable extension can run or gain effect authority. Reject returned tool requests even beside a valid verdict. | Yes, with current owner authority and family evidence. |
| `contained` | Tools may run only within the review jail; no external effect or persistent tool mutation is possible. Only bounded verdict text is consumed. | Yes, with the full containment proof and owner authority. `supports_text_only` stays false. |
| `unsupported` | The launch's tool-free or confinement properties are unproven, incompatible, or stale. | No. Refuse before model launch. |

**Answer to the founder's earlier API-key question:** an owner-authorized API-key HTTP reviewer remains acceptable when the user has one, but is **not required**. HTTP retains its validated plain-text request/response contract, including rejecting unsupported extensions and tool requests; preserve source cost/privacy controls. Subscription-only success in both family directions is mandatory acceptance evidence, not a future upstream wish.

#### 1a. Claude qualifies as text-only under a complete launch-time proof

The controlled production container permits an enforceable local configuration boundary. For a pinned executable, the launcher must prove the following **before any Claude startup code or hook runs**, and bind the proof to the launched namespace and configuration:

1. Refuse if any managed file, drop-in directory, or managed MCP file listed above is present, symlinked, unreadable, or cannot be checked. Inspect the actual container/launch filesystem, not the Windows development host. Keep those paths absent and unwritable for the lifetime of the call, avoiding a scan/exec race. The current jail's system allowlist does not mount `/etc/claude-code`; verify the final mount manifest, install binds, and environment cannot reintroduce it.
2. Use a fresh private home/config and workdir, no project or ancestor settings, no inherited parent policy or remote-session environment, no persisted session, and an allowlisted environment. Pass actual argv elements equivalent to `-p --tools "" --mcp-config '{"mcpServers":{}}' --strict-mcp-config --setting-sources "" --safe-mode --disable-slash-commands --no-session-persistence`, with a non-bypass permission mode and pinned model. No resume, custom agent, SDK parent configuration, Chrome, account app, plugin, or tool bridge. Runtime conformance covers built-in plugins as well as user customizations.
3. Prove remote policy cannot introduce executable configuration for the **entire call**. A version-verified credential mode that does not fetch remote policy can qualify; record its server-attested credential category, not an owner label. Otherwise require a pre-execution policy admission/transport boundary that detects and refuses managed policy before the CLI can apply it, including refresh. An empty cache, a `doctor` result after startup, a network timeout, or one empty startup response without refresh protection is insufficient. Never suppress an organization's mandatory policy and then claim normal managed operation; refuse that text-only launch.
4. Attest the effective empty tool/extension surface, with fixtures that attempt startup hooks, policy refresh, tool calls and conflicting configuration. Changed binary, auth mode, image, mount, policy or proof generation invalidates eligibility. Returned tool requests invalidate a text-only verdict even if accompanied by valid text.

**Decision:** Claude `supports_text_only` may be true for this proven launch profile; it is not a blanket provider property. The existing OAuth-token adapter path has not established item 3. If text-only proof is unavailable, select a separately admitted **contained** Claude profile meeting 1b (including confinement of policy hooks from process start), or another eligible owner connection. This is normal tier selection before launch, not reclassifying a violated text-only run after the fact. If applicable organization policy requires authority the contained profile cannot provide, refuse that profile too.

#### 1b. Contained review guarantees and existing jail seams

Implement a review-only profile in the existing provider jail, bound by server-owned review purpose and owner admission. It must guarantee all of the following; a missing guarantee refuses launch rather than falling back to the ordinary profile:

| Guarantee | Required profile and existing seam |
| --- | --- |
| Input-only data view | Narrow `UniverseView`/`_validated_view` to an immutable, read-only review envelope, schema and trusted configuration. No owner workspace, `.runtime`, credential snapshots, source tree, run databases, other users, daemon sockets, host home or ambient sessions. Minimal verified read-only runtime binaries/libraries are necessary execution infrastructure, not additional user data. Validate symlinks, hardlinks, parent paths and mount sources; pin the input digest. |
| No durable writes | Use empty per-call tmpfs for workdir, home/config, caches and temp. No writable host bind, Git checkout, shared cache, output artifact ingestion or file sync. Tool-created patches remain scratch and are discarded. The controller persists only bounded verdict text, usage and safe provenance; logs are inert data, never commands or files to apply. |
| No general network | Preserve `jail_argv`'s `--unshare-all`; review `confine_launch` must skip `_network`, the checking egress proxy, proxy environment and engine relay. No raw outbound/DNS access, loopback service, arbitrary Unix socket, inherited connected descriptor, host namespace or general CONNECT tunnel. `engine_route=None` alone is insufficient because `_network` still adds egress. |
| Inference-only authority | Keep real subscription credentials outside the tool-visible filesystem, environment and process namespace, in a trusted transport broker under the owner's admitted binding. A per-call handle can authorize only this bounded review inference, its pinned model and remaining budget. The broker validates destination, method, request shape and limits; denies redirects, arbitrary headers/URLs, account actions, uploads, remote tools/apps/search, remote code execution and non-review endpoints. Even if a local tool reaches the handle, it cannot expand data scope, budget, storage or effect authority. No backend credential is returned in text/errors. Use supported CLI transport integration; no reverse-engineered subscription API. Ordinary HTTPS host filtering is not this broker. |
| Whole-process isolation | Keep private PID/mount/user/network/IPC namespaces and device isolation, with all hooks, subprocesses and tool helpers confined from first exec. Close inherited descriptors except audited input/output and narrow transport handles; no host app-server/remote-control connection. Fail closed without Linux/bubblewrap or successful probes. `launch_is_confined()` only reports scope, not this stronger proof. |
| Seccomp and resources | Load `jail_seccomp.program_fd`/`deny_program`, retain `PROVIDER_LIMITS`, sized tmpfs, owner usage limits, call timeout and bounded output. Prefer the default deny profile. If native Codex patch helpers need `nested_sandbox=True`, record that profile: it permits symlinks and new user namespaces, so explicitly prove nested mounts cannot widen the outer input/scratch boundary. Never silently relax it after a tool failure. No requirement that patch tools succeed. |
| Complete teardown | On success, error, timeout or cancellation, revoke the per-call transport handle, terminate and reap the entire PID namespace, then discard scratch before accepting the verdict. `owned_process` group cleanup alone documents a `setsid` escape limitation; prove namespace teardown closes that gap. Cleanup uncertainty invalidates the verdict and holds the write. |

Codex defense in depth: a fresh `exec`, `--sandbox read-only`, `--ask-for-approval never`, `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, an empty `--cd` directory and `--skip-git-repo-check`; disable MCP, apps, plugins, hooks, shell and web search using fields verified for the pinned version. These flags do not supply the OS guarantee. Contained local tool events may occur and are recorded safely; only the final schema-valid verdict is consumed. No tool event is dispatched by the platform, and an attempted forbidden operation cannot obtain approval or escalation.

The existing jail supplies most OS primitives, **not this review profile or inference broker**. Implementing and proving those is in scope for the future implementation of this change. The release criterion is successful subscription-only writes, not merely better hold messages. Failure of a proof fixture blocks promotion of that profile; it does not justify accepting ordinary jailed execution as contained.

### 2. Select a different family for the effect, not for the conversation

Derive the producing model/provider and lineage from server-owned invocation receipts for the work that produced the exact action/artifact, not the chat's current model or agent-supplied fields. An effect-only code node must carry the producing artifact/run provenance. Unknown provenance holds for repair rather than being relabeled deterministic. A server-proven deterministic owner-authored operation with no model producer records that fact explicitly and still receives review by an eligible known-family model. If several model families materially authored the proposed work, exclude all of them; this may require a third family.

Families are data in trusted model discovery/provenance, independent of adapter, access method, URL, or user label. Claude reached through HTTP remains Claude; GPT through another gateway remains GPT. Opaque or unverifiable aliases are `unknown` and ineligible. Extend the existing model metadata/receipt seam rather than hardcoding a two-vendor pairing or reusing `api:<protocol>` as lineage.

Enumerate only sources already connected and authorized for this command center and accepted for review data/cost scope. Prefer a different-family reviewer among candidates with either current `enforced_text_only` or `contained` proof; preserve the cross-family gate rather than silently substituting the author. Filter for model availability, privacy, owner budget, and unrevoked custody. Among eligible different-family candidates, use the owner's accepted review preference first, then existing stable candidate ordering; do not prefer a paid HTTP source merely because the subscription candidate is contained. No provider bootstrap or global role-chain fallback. A separate review child invocation consumes the existing run/request allowance and the reviewer's own account seat. Do not reuse the worker's account seat for a different provider or deadlock waiting while holding an unrelated seat.

Admission must recheck selected binding, credential generation, model family, and enforcement evidence immediately before dispatch. For capacity/transport failure, at most the existing two total review attempts may choose another already-admitted eligible candidate; no fresh budget or same-family substitution. An enforcement conflict holds immediately instead of trying a weaker profile. Conversation assignment and saved default remain unchanged. This is a review-specific path; do not repurpose the parallel judge ensemble or grant a general provider override to workflow code.

### 3. Bind review to one immutable effect and retain provenance

Extend the server-owned review purpose to bind owner, command center, run, exact destination connection/incarnation, operation, method/path, complete body/artifact digest, producing receipt(s), and rule/consent generation. The current structured action digest covers class/connection/operation/path, while evidence is truncated; it must not authorize a different body sharing that path. Preserve full submitted artifacts verbatim. If the bounded review envelope cannot represent material consequences, hold for inspection rather than pretend a truncated preview was sufficient.

Persist review attempt and outcome beside the run's existing invocation/effect receipts: requested and actual provider connection, executor, model, model family, **tier**, version/configuration/mount/transport/proof digests, producer identities, action digest, timestamps, usage, verdict/reason, teardown outcome, and safe failure code. Actual execution must be attested by provider telemetry or a proven enforced model pin; missing identity is explicitly unknown and cannot satisfy cross-family proof. A fallback's actual reviewer replaces no history. These fields are audit evidence, never authority. Project onto the owner-visible run detail; show `contained` honestly, never "tools disabled" for that tier. Redact credentials and raw provider errors. Persistence failure holds the effect.

At dispatch, recheck current owner/connection/rule authority and the immutable effect binding. `proceed` only clears this review; it never supplies consent or expands a grant. A valid `needs_approval` verdict goes to the existing owner consent flow, bound to this action. Owner approval of an unavailable/malformed/timed-out review does not manufacture a completed review. Changed content or authority invalidates the review and requires re-admission within current limits. Consequential external writes ignore old review-off settings; workspace/read-only exemptions remain.

### 4. Fail closed with an exact connection remedy

Keep `auto_review_unavailable`, but distinguish `no_cross_family_source`, `unknown_producer_family`, `review_safety_unproven`, `managed_policy_unproven`, `containment_unavailable`, `reviewer_authority_revoked`, `reviewer_identity_unknown`, and transient failure details. Budget exhaustion retains its existing separate stop. Surface an owner-visible run record and one deduplicated pending request per unmet requirement, not one approval request per retry. Remediation must identify the needed model family and either accepted tier. Owner-fixable connection grants go through Connections; a missing production isolation profile is an executor problem, not a request to buy an API key.

Examples derived from live available model metadata (display names/models must not be invented):

- Claude-produced work with an eligible Codex subscription: run contained GPT-family review and permit the exact write after a passing verdict and required consent. No API-key setup or extra hold is necessary.
- GPT-produced work with an eligible Claude subscription: run proven text-only review, or an independently proven contained launch when managed-policy absence cannot be established. Record the selected tier.
- A subscription profile fails its launch proof: explain the specific failed isolation/policy condition and preserve the unsent effect. Another already-authorized eligible profile may be selected before launch; never relabel a failed running profile or substitute an ordinary agent launch. HTTP is an optional eligible source, not the required remedy.
- An eligible owned source exists but its review grant is missing: name that connection/model and request the grant, not a new credential. If no concrete model is discoverable, report the exact family/capability needed and say no currently verified candidate is available.

Never recommend "approve anyway", turning review off, changing the conversation model, sharing the founder's account, or unconsented API spending. Connecting a new source requires the owner's normal grant, privacy, and spending acceptance. Recheck readiness after that flow; no blind replay of an uncertain external write.

### 5. Any receiver owner's run survives one connection-write failure

Use the existing runs database and `graph_deliveries` identity. Add generic `graph_delivery_operations` records keyed by `(delivery_id, operation_key)`, scoped to the receiving owner/command center, with kind (assessment, notification, external effect), receiver snapshot version, input digest, state, run/review/effect receipt references, attempt metadata, safe failure reason, next recovery action, and external reference when known. States distinguish pending, running, succeeded, held, failed-before-send, and outcome-unknown. Acceptance itself is sufficient for the inbox entry, even if no worker or operation row ever starts. Existing records lacking operation detail display `legacy_unknown`, never guessed success.

The owner-authored receiver graph persists the request first, then schedules independent later work through durable operation outcomes. A connection-write failure is a value the graph can route on, not a branch-killing exception. Later steps depending on success may remain pending with that dependency visible; independent assessment, internal notification and failure-handling steps must still run. In a patch workflow, neither assessment nor the receipt notification requires an issue URL. Assessment/provider failure has its own visible result and does not suppress the initial notification. Missing worker/provider capacity must still leave an inspectable received item. This is a reusable receiver/workflow primitive for any owner, destination and custom tool.

Existing graphs are not silently rewritten. Expose the outcome/dependency primitive and guidance so the owner's app agent can update its own receiver through the ordinary graph authoring path. Prove that upgrade on a normal owner's intake and the founder's intake before claiming this use case fixed. A graph that has not adopted independent processing still gets durable received/failed visibility.

**Where the receiver OWNER sees pending or failed deliveries:** add `read_graph target="deliveries"` as the owner-scoped paginated inbox, with authorized receiver filters, pending/held/failed state and stable cursors. Individual details extend existing `read_graph target="delivery" query=<delivery_id>` with operation outcomes and recovery. The receiver detail exposes "Received requests" to its owner; "Patch requests" is merely an owner-chosen label for a patch receiver. The existing `pending_requests` rail carries actionable holds. A normal user needs no maintainer status to inspect or retry their own deliveries. Existing explicit receiver administration grants may delegate access; repository membership alone grants none. Sender receipts remain coarse and reveal no assessment, other senders, receiver graph, or private destination credentials.

Add `write_graph target="delivery" operation="retry_operation"` with delivery ID, operation key, and expected operation version. Receiver authority, cancellation, connection, rules, current review, and consent are rechecked. Retry only the unfinished operation. Successful assessment/notification/filing stays completed; no whole-branch replay as a shortcut. A transaction/claim fence serializes retries. A known pre-send failure is retryable; timeout/crash after dispatch is `outcome-unknown` and requires provider-supported idempotency or read-only reconciliation before another send. If neither is possible, require an owner reconciliation decision; never invent exactly-once semantics. Outbound notifications are consequential writes and get the same review gate; the durable internal notice/inbox is available without that outbound path.

This proposal changes no consent to send to another owner and grants no new cross-user reads. Receiver processing uses that receiver's own credentials and limits, never the sender's, platform's, or a maintainer's ambient login.

### 6. Duplicate coverage is a follow-up, not retry safety

Follow-up scope: before filing, use the owner's authorized platform-neutral search/read operations to retrieve existing issues/requests, preserve candidate references, and let the assessment decide whether existing work actually covers the request. Covered requests link to that item; uncovered requests file; partial or unknown coverage stays explicit. A similarity match alone is not coverage. Search errors are recorded and do not silently drop intake. Race handling and an owner policy for unavailable search belong in that follow-up. Linking an internal record is distinct from posting an external comment, which still requires review. No GitHub search API is embedded in the generic contract.

## Risks / Trade-offs

- Native CLI changes can invalidate proof -> pin and attest the launch; accept either proven tier, recheck on change, and test subscription-only success before release. Hold only genuinely unproven/ineligible calls.
- The current jail has egress and persistent owner data -> a narrowed view alone is insufficient; require the review profile, credential/transport boundary and teardown proof in 1b.
- Family diversity is not a correctness proof -> retain owner rules, consent, exact effect binding, and the strict verdict parser.
- Model aliases and source catalogues change -> invalidate stale family/enforcement evidence; record actual model identity and hold unknowns.
- Another provider may incur cost or see private evidence -> select only accepted review scope under existing privacy and spend ceilings; never auto-connect.
- Notification can itself fail -> durable internal inbox and independent notification outcome survive; external notification uses the common gate.
- Unknown external outcome or concurrent retry can duplicate a write -> preserve per-operation claims, reconcile, and never auto-replay ambiguous attempts.
- Active changes overlap -> coordinate implementation with `select-agent-models`, `connect-cross-user-nodes`, `notify-owner-of-requests`, and `universe-agent-harness`; this artifact lane edits none of them.

## Migration Plan

1. Add review descriptors/provenance and delivery operation storage with owner-scoped projections. Backfill only known facts; old unknown outcomes remain unknown. Align account deletion/retention with existing run and delivery records.
2. Implement Claude launch proof and the contained review jail/transport profile; add review-only selection/admission accepting either tier and mandatory external-write enforcement. Apply across foreground, background, task, graph, custom tools and direct adapter boundaries. Gate capability promotion on current proof, not a provider-wide boolean.
3. Add receiver list and operation recovery, then have the owning app agent adopt independent processing in the intake graph. No automatic edits to user workflows.
4. Future implementation verification: targeted review/admission/receipt/delivery tests plus affected heavy tests and ruff; mutation checks only for cross-user/effect-authority guards. Any jail/process implementation requires `python scripts/linux_oracle.py`; a skip is not a pass. Test local/remote Claude policy injection and refresh, Codex patch attempts, network/socket/credential access, scratch discard and descendant teardown on success/error/cancellation. Text-only proves no executable extension; contained proves no escape, durable mutation or extra effect despite tools. Neither is established by help output. No native conformance launch was run in this proposal session.

Prove ordinary user-connected GitHub and at least one non-GitHub platform, custom tools, successful subscription-only writes in both producer-family directions with actual tier receipts, negative proof refusal, and a receiver write failure with visible later work and owner retry. API-key HTTP is an additional optional-path check. Sync specs only after implementation; do not archive a proposal as delivered.
6. Rollback disables new reviewer eligibility and operation dispatch while preserving records/inbox reads; it must not disable review, restore review-off bypasses, or replay operations. Restore prior schema readers only after verifying they cannot erase new state.

## Open Questions

1. Which supported subscription transport integration on the pinned production executors can enforce the inference-only broker contract while keeping credentials out of tool reach? The ordinary egress proxy does not suffice; this is an implementation proof obligation, not an optional HTTP-key prerequisite.
2. Can the production Claude authentication mode prove absence of remote policy before execution and throughout the call? If not, deliver its contained profile; do not wait for upstream all-tools-off changes or certify a file-only scan.
3. What exact production image/CLI versions and Codex seccomp profile pass the adversarial Linux conformance fixtures, including nested sandbox and teardown? Local Windows help versions are not production attestations.
4. When should the separate semantic duplicate-coverage lane be prioritized? Coverage remains deferred; retry idempotency is required now.

Resolved: either proven tier satisfies review; API-key HTTP is acceptable but optional; the receiver owner is any user; the founder has no special path. Product implementation, production proof and deployment remain future work, not claims made by this spec revision.
