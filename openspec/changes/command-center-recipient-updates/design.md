# Design

## Context
Component copies pin the full normalized source plan and a digest of its public definition. Activated pins record recipient target IDs. File-package versions use author/name/version, but names cannot establish a stable component publication lineage. The pure planner is connected through authenticated registry, consent and executor adapters; client-provided records are never authority.

## Goals / Non-Goals
The planner computes reviewable updates and guards owner data. It performs no I/O, model calls, publication, installation, consent execution, storage migration or automatic scheduling.

## Decisions
- Immutable releases bind stable publication ID, author, exact definition ID/digest, parent, sequence, summary and complete component contract. A server registry must authenticate publication ownership and persist these records append-only. Hashes prove consistency, not authorization.
- Components have stable keys, kind, source digest, exact dependency digests, capability requirements and privileged-effect status. Unknown kinds and privilege changes fail closed.
- Adoptions retain each component's source release and source baseline separately from its remapped recipient target and installed digest. Selective adoption therefore reports mixed versions honestly.
- Caller-supplied observations and transformed candidates come only from authenticated server adapters. They are immutable snapshots for planning. Every planned write carries its exact expected current digest; execution must re-read under the same recipient lock/transaction before each mutation and atomically persist progress. This module is not an executor or a permission check.
- Three-way comparison preserves local-only edits, blocks divergent changes and local deletions, and detects dependency mismatches across selected AND retained components. Selection never silently expands to dependencies. Source removals require recipient resolution rather than deleting recipient data.
- Automatic policy is per adoption, off by default, and restricted to accepted capabilities. New components, privileged effects, unresolved dependencies/conflicts and missing source stop it. Plans never enable automations and require preserving existing runtime state.
- Legacy provenance uses only an activated platform pin whose source definition/plan digest and complete recorded target mapping validate. It establishes exact prior source, not a release series. Explicit linking to an authenticated release record is a later recipient decision; no author/name or content-similarity enrollment.

## Risks / Trade-offs
- Pure records cannot authenticate ownership → registry/API adapters must authenticate and use platform records, never accept a client-provided verified flag.
- In-place execution can race → plans contain digest preconditions; the connected executors recheck them under store write reservations and persist durable receipts.
- Exact dependency hashes can block compatible updates → explicit recipient selection is preferable to silently changing dependencies.
- Unknown effects may be omitted by publishers → capability declarations must be derived/validated by trusted adapters, not treated as an execution grant.

## Migration Plan
The planner, registry, owner consent, version browsing and service executor ship together. New adoptions are recorded from activated pins; legacy pins require exact validation and explicit release linking. Existing installations remain unchanged until their owners explicitly accept a replacement or enable presentation updates.

## Concrete manual UI executor
The first connected callable adapter is limited to existing component-system UI replacements. `record_install(universe_id, request_id)` loads a real activated owner-scoped pin, validates its immutable source, reconstructs remapped UI content and requires an exact match before registering a clean baseline. Existing altered legacy screens are conflicts, not automatically linked. Agent templates use `plan.agent_templates` and `progress.agents`, coordinated with the public-template lane.

Two metadata tables live in the same `.tinyassets.db` as `universe_app_ui`. They retain hashes/IDs, not UI/script/source bodies. Each adoption has at most one pending consent, replaced by a fresh preview; the latest completed request digest lives on its adoption for retry. The retained immutable original install pin remains the evidence for copied workflow, agent and automation targets.

`preview_update` pins a server-derived exact-source/read-set plan. `commit_update` requires a matching request/digest and explicit accepted/declined decision, reserves the UI bytes using existing storage accounting outside the database lock, then rechecks ACL ownership, source availability, adoption/UI revision, source and current hashes, and dependency configuration inside `BEGIN IMMEDIATE`. UI replacement, baseline, receipt and request consumption commit together. Existing component and asset validators run; private/unowned assets are never fetched. Quota reservation is released on rollback and committed after the database commit, matching existing UI accounting semantics. A post-commit accounting failure is recoverable through the stored applied receipt; it cannot cause a second screen write.

A manually selected same-author definition is explicitly a user-selected replacement, not a publisher release. The response identifies the new UI definition and the original retained component definition. Any changes to workflows, automation specs, agent templates or UI reference bindings refuse; additions/deletions need a future explicitly supported plan. Private dependency content is preserved and fenced in the preview read set; these observations do not falsely attest it still equals the publisher baseline.

Route registration, trusted owner consent UI and the post-install hook connect the adapter. Author-bound release browsing and opt-in presentation execution are also integrated. Broader component updates and conflict resolution still require a future supported plan.

## Retained automation write fence
Independent review of `44c9514e` found that retained automation IDs appeared in consent but actual automation rows were absent from its read set. Retirement after preview therefore incorrectly allowed a UI update. The repair attaches the existing trusted-base `.automations.db` before `BEGIN IMMEDIATE` and reads its actual recipient automation rows through that same connection. SQLite's write reservation spans attached databases, so existing `AutomationStore` transactions cannot retire/reconfigure a dependency between its final check and UI commit. Missing database/schema or missing, retired, foreign-owner/home or redirected workflow rows refuse. Zero-automation stores do not create an automation database.

The dependency hash covers scheduling/event/input configuration, identity, owner/home, desired state, revision and retirement. Run timestamps, result counters and last-run IDs are observational and excluded. No SQL writes target the attached database: the UI/baseline/receipt remain the sole main-database atomic mutation. This explicitly does not claim multi-file atomic writes in WAL mode; SQLite documents that limitation at https://www.sqlite.org/lang_attach.html . The real competing-writer test traces `AutomationStore.retire` reaching `BEGIN IMMEDIATE`, verifies it remains blocked inside the final UI transaction, and confirms it can retire only after observing the committed UI revision. Rollback releases both reservations.

## Explicit publication series and recipient presentation policy
`command_center_release_series` and `command_center_update_policy` provide publisher/recipient store hooks and eligibility, connected to publication, installation and trusted owner controls. Release capture derives identity hashes from the validated selected UI/workflow/automation/template sources, records an explicit stable series ID and exact current parent, and supplies exact consent text. Identity hashes stay publisher-private. The post-publication hook accepts only a real activated publish pin whose stored action and displayed tab include that release link, with matching author/home, normalized immutable public definition and stable identities. Append and series-head advancement share the existing main-database transaction; keys remain reserved across all historical releases, including removals. Names never establish lineage. Summaries use the existing publication secret scanner.

Recipient policy is separately previewed/confirmed and defaults off. Its stored grant binds owner/home/adoption, adoption revision and transformed baseline, exact registered current release/series, and intact dependency read set under the attached automation fence. Policy consent is revisioned and replay-safe; a previous opt-in cannot undo a later opt-out. Opt-out remains possible after private edits or source withdrawal. Mixed manual replacements stay outside automatic eligibility unless a separate explicit link verifies the actual UI definition and all retained components against the selected registered release.

The first policy is named `presentation-updates-v1`: eligibility requires byte-identical script, markup, libraries, assets, references and external origins, plus byte-identical retained components. Only UI name/style differences qualify. A conservative CSS resource/escape/at-rule filter requests review; it is not an authoritative CSS parser or a network permission boundary, and the existing renderer CSP remains authoritative. Conflicts, changed/private dependencies, missing sources, new components, new executable content or new permissions return `requires_decision`, never partial application. Checks never apply UI content, schedule work, resume automations or mint an authenticated owner. Publisher consent/hooks and recipient consent UI are connected; eligible accepted grants are applied by the separate executor through service maintenance as described below.

## Stored-grant presentation executor and service activation
`command_center_update_executor.apply_next` is an internal data operation, not a human-consent or model API. It reloads an accepted, digest-bound per-adoption grant, selects the next contiguous registered release and preserves the original accepted snapshot/request/digest. A separate `snapshot.progress` records the installed release; automatic application increments the policy revision without fabricating a human acceptance. A no-content release advances source progress with a receipt without rewriting the UI. A blocked intermediate release is not skipped.

The final transaction reserves writes in main plus trusted existing automation, workflow-version, package-pin, storage-ledger and account-tier stores. `HeldReads` routes existing source/template/nested-workflow validators through this connection; it initializes no schemas or independent writers. Main ACL/account ownership/home/tombstone, source/lineage/pin targets, dependencies, complete library, baseline and policy revision are rechecked. Only main is written: UI, adoption, policy progress and durable receipt/outbox commit together. No model/provider calls, actor impersonation, grants, retained-component writes or automation resume occur.

Storage reservation runs outside the held transaction. Existing quota/account resolvers are initialized outside locks, captured before reserve, then rerun as reads under the final input-store reservations; their output and source metadata must still match. The exact unexpired reservation and complete measured usage are checked before and after the bounded SQL writes. A missing measurement causes an explicit retry requirement rather than a guessed allowance. Accounting settles after main commit; a failure remains an applied receipt with pending debt. Missing/zero-row accounting settlement requires successful real measurement. Durable receipts make duplicate preparers and retry safe, releasing only their own unused reservation.

The executor module imports no scheduler. `universe_server` calls `command_center_update_maintenance.tick` on every existing maintenance cycle, after the loop's 300-second sleep. Each tick checks process cloud admission before storage access, holds the service writer/reset barrier, and sweeps at most ten pending settlements and ten policies with separate cursors. Settlement retries remain independent of opt-out and new releases. Owner routes and trusted controls expose saved preference separately from worker availability, sanitized blocked/retryable reasons and pending-settlement counts. Each bounded sweep isolates failures per item. WAL multi-file atomic commits are not claimed.

## Publisher evidence and account deletion
Consent pins retain the private link because post-publication registration validates its exact source identities, publisher home and displayed consent. Each new pin binds `owner_id` from the authenticated consent caller. Existing release pins acquire that owner from their platform-written `action.release_link.author_id`, never from the publisher's current home. Account deletion explicitly inventories `.command-center-packages/packages.db` and performs this migration before deleting pins by owner; legacy pins without owner evidence retain home-based cleanup. An explicitly owned peer pin survives even when it names the deleted account's home. Public package versions, blobs and release history remain intact.

Public release IDs hash only the immutable public record: author attribution, series/parent, definition, sequence, summary and component digests. Private source identity hashes, publisher home and publication request ID live in `command_center_release_evidence`, keyed by `owner_id`; the mutable series ownership/head row also uses `owner_id`. The existing schema-derived account deletion removes both private tables by principal, even with a changed or absent home. Public history is retained unchanged and remains hash-verifiable; recipient adoptions, grants and receipts belong to their own owners. Stable-key checks load private evidence for every historical release and refuse missing evidence. A retained public series cannot be recreated after its publisher ownership row is erased. This corrects the new, unshipped release storage contract before deployment; private fields are never redacted inside a hashed public record.
