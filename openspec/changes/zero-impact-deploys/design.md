## Goals / Non-Goals

**Release invariant:** a compatible planned deploy, rollback, or release reconciliation must not cause a user-visible failed send, lost/duplicated action or reply, interrupted turn, dropped scheduled/background job, broken connector session, or page requiring manual reload. Accepted work keeps its identity and authorization. Temporary pending/reconnecting state is allowed; a deploy-induced error or manual Resend requirement is not.

The invariant is enforced by refusing unsafe release transitions, not by asserting that every arbitrary operation can be resumed. Declared schema-changing maintenance windows follow D11 and are outside this zero-impact claim. Explicit operator force is reported as interruption, never zero-impact. Hardware loss, network partitions outside the service, and independent provider failures retain truthful failure semantics. Disk exhaustion must never produce a false durable-accept acknowledgement. A single host cannot provide host-failure redundancy. No new paid infrastructure, provider-specific recovery, platform LLM, or change to consent policy is proposed.

## Decisions

### D1. Stable ingress and bounded single-host overlap

Keep `https://tinyassets.io/mcp`. The local gateway is D11's replaceable frontend role: auth, routing and streaming, without execution ownership. Acceptance, MCP session bindings, JSON-RPC mappings and reply cursors live in an independent shared durable journal, not authoritative process-local gateway state. The outbox pump holds S8b's platform lease. Old frontends retain open streams until completion; new ones attach via persisted identities. Warm candidates read-only on distinct private ports without reconciliation, migrations or provider children. Reuse the host mutation lock.

`deploy/compose.yml` gives the daemon a 4 GiB limit on the documented 8 GB droplet. Two unchanged 4 GiB limits are forbidden. Measure actual MemTotal H and enforce `sum(owner-generation limits) + sum(gateway/frontend limits) + sum(tunnel limits) + OS/other-service reserve + safety headroom <= H`. Count all old owners and provider descendants and all overlapping gateway/tunnel processes. Initial fixture budget, conditional on at least 8 GiB usable memory: old owner 3 GiB + candidate 2 GiB + aggregate gateways/frontends 512 MiB + aggregate tunnels 256 MiB + OS/other services 1 GiB + safety headroom 1.25 GiB = 8 GiB. This is proposed, not measured production capacity; smaller MemTotal needs smaller validated caps or no overlap. Verify effective Linux cgroups and `oom_score_adj`: runtime/provider children 500, gateways/tunnels -500. Priorities supplement reserves, never permit oversubscription.

Never lower a live limit below measured usage plus validated burst headroom. Establish safe caps before rollout; insufficient capacity defers candidate startup with old admission open. Use **one shared `provider_admission` limit across both generations**, through S4's host admission authority and D11/S9 shared account-seat accounting. Old children retain tokens until proven exited; warm-up gets none; startup cannot reset counts. Admit only when shared count and aggregate memory headroom permit. Test concurrent old/new acquisition and crash reconciliation. Budget CPU, disk, queue, SQLite and connections too. At most two resident owner release generations fit this initial host plan (D3); stragglers delay retirement, not unrelated key moves.

Only after the task-1 harness exists and candidate traffic proof passes may production ingress change. Ingress updates themselves use socket/listener inheritance with old connections drained by the old gateway, a shared durable queue and compatible session state. Tunnel updates preserve an overlapping local tunnel process and existing connections until retirement is safe. If either component cannot prove listener/connection continuity, its update is blocked. For bootstrap, bind the gateway to a new loopback port and proxy to the still-serving daemon on 8001; change the dashboard-managed tunnel ingress to that new port only after its readiness proof. Preserve existing tunnel connections, verify propagation with continuous traffic, and immediately run `python scripts/mcp_public_canary.py --assert-handles`. If connection-preserving reconfiguration cannot be proved in the fixture, defer bootstrap. Do not claim the guarantee before this transition passes.

### D2. Durable acceptance and reply outbox

Give the replaceable frontends a shared durable ingress journal in a separately versioned storage root outside the runtime layout-lock domain. It owns acceptance/delivery only; existing admission storage and owner leases remain the sole execution authority. Import envelopes into runtime admission under a stable ingress ID: commit a unique admission-to-ingress mapping before acknowledging import; retry an interrupted import by lookup, never by creating another run. Persist outgoing receipt events before acknowledging journal transfer, likewise deduped by ingress ID and sequence. App request_key is the existing `client_send_id` from #4490, preserved through conversation_store.py, agent_steering.py, api/status.py and receipt reconciliation, never a second client identity. Proposed logical fields: authenticated principal ID, target command center/thread, operation, client_send_id for app sends (merged #4490), payload digest, exact payload/blob references, accepted sequence/time, authorization provenance, run/turn ID, state and receipt. A transaction enforces uniqueness of `(authenticated_principal_id, target_command_center_id, thread_id, operation, request_key)` and binds its digest. Principal means the authenticated user/service identity, never the shared universe actor. Every receipt/cursor read requires that principal match and current target access. Same key/different payload is a conflict; different principals never share a dedupe record. Authenticate and apply existing size/rate/storage rules before commit. Do not persist bearer credentials. Revalidate revocation/current authority at execution and result reads.

Commit payload and replayable admission atomically before success/202; no 202 means 'stored only in RAM'. Preserve upload bytes verbatim. Persist output events with monotonic per-request sequence and terminal receipt before publishing them. Ack loss returns the same receipt on retry; client disconnect detaches a subscriber, not the work. A cursor can replay missing events without repeating actions. Keep nonterminal rows; retain terminal identity tombstones at least through the declared client retry window and reject expired keys rather than silently execute them again. Coordinate blob and conversation retention with the existing custody policy.

App sends, approval answers, webhook deliveries, connector mutations and generated replies all enter this contract. Adapt synchronous protocols at ingress: maintain the response/SSE transport with heartbeats during worker handoff; only use asynchronous receipts where the client protocol supports them. A generic 202 is not a valid replacement for an MCP tool result. Only a key actually changing owners queues; busy keys stay admitted to their old owner. Preflight moving-key activation bounds before releasing its lease.

### D3. Per-command-center idle-instant handover

This lane folds deploy-continuity detail into the existing architecture, not a competing ownership design. Exact authorities: `openspec/changes/target-architecture/design.md` section D11, "Uptime: per-command-center execution owners behind replaceable frontends", particularly "The control plane splits into two roles", "Atomic fencing", "Owner handover, per command center: a turn runs until it finishes", and "Schema-changing cutovers"; D5, "Owner-generation fencing of effects: an acknowledged barrier"; S8, "Command-center owners + platform owner + frontends, the leases, the always-on duties, deploys", including S8a `execution-owner-lease` and S8b `control-plane-scheduler`.

S8a owns leases, reconciliation and fencing; S8b owns platform duties. This lane supplies durable ingress/replies, client integration and S8's traffic proof without duplicating their mechanisms. D11's S4 prerequisite for isolated per-command-center idle proof must land before per-key moves or a second writer is enabled. Phase-1 whole-process waiting is transitional behavior, not this guarantee.

Persist release digests, compatibility, budget and per-key phases: `serving-old -> idle-fenced -> lease-released -> successor-barrier -> serving-new`. Release phases are `candidate-ready -> migrating-keys -> serving-new-with-stragglers -> retired-old`. There is no global admission hold or checkpoint-transfer phase.

Follow D11/S8a: `BoxProvider.try_fence_idle` proves idleness atomically against new starts; release the key's lease in the transaction that sees it idle. A racing start either belongs to the old owner and prevents the move or queues only for that key after its fence. Never close admission on a busy key. Idle centers move immediately; native/long turns keep their old owner, workspace and admitted version until completion. Do not SIGTERM to initiate drain.

The successor acquires generation+1, advances every owner-store fence and completes the acknowledged broker/boxhostd barrier before reconciling or serving that key. Never reconcile keys still held by the old process. Reuse kernel-backed run guards; TTL cannot steal live work. Preflight measured activation before release. Unconfirmed fencing blocks that key's activation and pages, without closing other centers' admission. Controller restart reconciles durable phases and leases rather than guessing ownership.

The platform lease moves separately under S8b, recovering claims/outbox without waiting for user turns. Retire old processes only after their last key, child, receipt and stream finish. Stragglers delay retirement, not the release's other key migrations. Honor D11's two-generation ceiling per center and default two-hour lingering-owner alarm. Under the initial two-generation host budget a later owner release cannot spawn a third generation: leave affected keys on their current owner with update pending; compatible frontend updates may proceed within budget.

### D4. Old-owner stragglers and at-most-once effects

Planned deploys transfer no live turn or provider checkpoint. Old owners finish stragglers with their workspace, conversation, approvals, budgets and output cursors intact. Existing `SqliteSaver` and reused LanceDB connections remain unchanged. No unavailable continuity branch or snapshot contract is a dependency; merged #4493's history/workspace visibility is not a transfer protocol.

Reuse effect-intent identity: `planned` dispatches only with proof of no prior dispatch; `confirmed` returns its receipt; `sent`/`unknown` never blindly redispatch. **Check generation in the same `BEGIN IMMEDIATE` transaction that marks an effect `sent`, before the remote call**, reading the command-center fence row under the write lock. Post-call CAS is not fencing. Dispatch carries `(command_center, generation)`; D11/D5's broker and every `boxhostd` persist the advanced generation, refuse older requests and acknowledge fencing/cancellation of older in-flight operations before successor activation. This closes the local-commit-to-delayed-dispatch gap.

An effect without that enforcement boundary cannot cross an owner move: retain the old executor until outcome and idleness are proven. Local transactions cannot resolve remote ambiguity; retry requires a proven vendor-neutral idempotency/receipt-query contract. Independent crashes leave truthful held/unknown outcomes. Test a paused old executor between `sent` commit and remote dispatch: the acknowledged barrier must reject its stale call.

### D5. Open pages recover without losing user state

Handshake on boot, focus, reconnect and response metadata with build ID, API protocol range, release generation and stream cursor. A build mismatch alone need not reload a compatible page. Retain old immutable assets through supported session lifetime. On transport loss, query the durable request receipt and resume events automatically with #4490's original `client_send_id`; do not create a second turn. No resend offer while delivery is uncertain. Only confirmed not-delivered state may retain existing explicit retry behavior; deployment proof cannot require it.

Persist owner/thread-scoped draft, uploads, selection, pending request ID and cursor before replacement. Restore after login/owner verification; clear cross-account state. Build on merged #4497 (`c7c037ea0a`), `openspec/specs/command-center-recovery/spec.md`, requirements "Recovery survives application failure", "Recovery preserves private drafts", and "Stale module URLs resolve". Preserve frame remount first, then reload with a two-page ceiling, independent shell controls, owner/home/addressed-agent-scoped draft restoration and non-cacheable stale-module redirects. Extend that implementation rather than inventing another recovery bootstrap. Test automatic recovery as success; repeated candidate failure triggers safe rollback with drafts/receipts intact. Manual reload is not a passing compatible-deploy outcome.

### D6. Scheduled and background work is part of the same ledger

Persist schedule occurrence identity `(trigger, due_at, revision)` and event identity before enqueue. Atomically associate claim with durable work, or use a recoverable outbox that can resolve an interrupted claim-to-enqueue sequence. Reconcile outstanding claims against actual run ownership, not elapsed time alone. Preserve the schedule's timezone/misfire/coalescing policy; deploy does not silently advance last-fired past an unexecuted occurrence.

Inventory every startup task, thread, queue consumer, delivery worker, reconciliation job and provider child. Each registers durable resumable work or drains to completion before retirement. Persist legacy scheduler events before placing wake hints into the in-process queue. Under S8b, reconcile durable claims by their original identity and re-enqueue pending events once; running user work finishes on its old owner. Use a generation fence for scheduler leadership; candidate warm-up must not fire schedules or settle the old runtime's live rows.

### D7. MCP and connector compatibility

The shared journal owns MCP session-to-principal binding, in-flight JSON-RPC request mapping, negotiated protocol version and event replay. JSON-RPC IDs are session-scoped, not globally unique idempotency keys. Mutating calls need a durable operation identity bound to authenticated principal, session and payload; supported reconnects reuse it. Existing explicitly non-idempotent tools are never blindly retried on a guessed identity. Legacy sessions stay pinned/drain through the gateway until their result is delivered. A release cannot retire a session it cannot resume safely; retain that frontend until delivery instead, without blocking other centers.

Keep tools/initialize contracts and authorization checks compatible across overlap. Internal upstream resets trigger receipt lookup and reattachment, not a client-facing 520/502 or a duplicate tool call. Measure actual Claude.ai and ChatGPT call/idle timeouts in the harness and record client versions and observed limits. Heartbeats do not prove absolute timeouts are extended. Handover plus reply latency must fit the shortest demonstrated supported timeout; missing evidence blocks that transport continuity claim. Test actual supported connector transports; preserve cancellation separately from disconnect. Retry budgets use backoff/jitter, but network retries are not the source of truth for whether a mutation ran.

### D8. Pipeline, rollback and schema compatibility

Replace the best-effort wait-plus-recreate path with the persisted transition controller. Normal deploy, manual dispatch, reconcile, rollback and host recovery share it. Keep existing digest ancestry, bundle validation, constrained probes, public MCP/app canaries and receipt assertions. Unknown health/drain/ownership means defer; no emergency flag may silently claim zero-impact after killing accepted work.

Only already-compatible schemas/protocols may overlap and roll back. **Schema-changing cutovers are declared maintenance windows**, extending exclusion to both frontends, owners, `boxhostd`, Litestream and backup workers. Expand/contract migrations also use their declared schema-change path. The independent acceptance journal does not authorize hidden migration behind a global hold. Contraction waits until old binaries/sessions are ineligible. Never restore an old database snapshot over newly accepted work. Maintenance and explicit force are separately reported, never labeled zero-impact.

Before readiness failure, keep old service intact. After keys move, rollback moves only idle keys through the same barrier to a compatible binary; new-generation stragglers finish there. Never steal uncertain owners. Controller crash/cancellation reconciles persisted per-key phases under the host lock. Record queue age/count, key/lease generations, active routes/images, timings, budget, probes and rollback evidence.

- Shared SQLite/LanceDB/workspaces require S4/S8 writer isolation and real Linux locking proof.
- Remote unknown effects remain unknown after independent crashes; a local ledger cannot promise remote completion.
- Shared acceptance enlarges custody, authorization and disk-retention obligations.
