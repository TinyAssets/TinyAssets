## Context and scope

The bubble is permanent emergency/control plumbing; Muse models its interaction. At `95508ecdc0`, the app polls a request rail, redirects OAuth and relays answers via `sendTurn`. Extend those seams with inline connect and approval that executes. Connections remain generic data, never provider code. Keep the existing request/status refresh transport; SSE and a general request-error schema are separate lanes.

## Interaction and authority

Place requests beside their originating turn (background requests in the initiating agent's thread). Connect shows plain-word scope and Connect / Not now. Approval shows summary, editable draft, Approve / Edit / Deny and once / this task / always, default once. Edit returns a fresh preview without execution. Other connect entry points focus this card; the rail becomes read-only history. Secrets never enter transcript messages. Failure preserves the request/draft with Try again / available alternative / skip. Not now defers; denial/skip records an explicit outcome.

For ask_first, the trusted dispatcher stores `{version:1, executor, arguments, subject, connection_revision, consent_digest, policy_digest, expires_at}`. Executor is an existing generic operation; arguments are validated non-secret inputs; subject pins authenticated owner/home, initiating agent/binding revision, task ID/generation, conversation and turn. Hash RFC 8785 canonical JSON with SHA-256; pin referenced file/body versions and digests without changing transmitted bytes. The server renders the summary, destination, draft, attachments, scope and identity from this protected envelope and pinned payloads. Agent prose is separately labeled context, never the approval preview or editable authority. Missing/inconsistent protected data requires a fresh preview and disables approval.

Approve claims the displayed revision/hash and executes server-side through current ordinary enforcement: isolation, custody, grants, consent, initiating-agent rules and owner-configured review. Edits or changed authority/policy require a fresh preview. No agent retry turn. Only owner rules choose ask_first; do, hand_off and do_if_preapproved retain their meanings. Defaults remain editable. Authenticating an owner decision creates no platform-mandated approval gate; cross-user isolation remains the fixed policy floor.

### Interactive owner approval

Only the owner's signed-in first-party web app or native app's protected first-party approval view can approve. Custom layouts, universe content, runtime agents, CLI and chatbot/MCP connectors, even with the owner's bearer, are not interactive owner sessions. Introduce a distinct server session established by verified interactive owner sign-in; an API/MCP bearer cannot mint, upgrade into or refresh it. Web uses a Secure, HttpOnly, SameSite cookie plus origin/CSRF checks on a protected app origin inaccessible to custom layouts. Native uses an interactive-login session credential in OS-protected storage exposed only to the first-party view, never the agent bridge.

The protected preview endpoint issues an opaque single-use approval token bound to session ID, owner/home, request ID, revision/hash, selected scope/predicate and task generation. Expiry is five minutes or session/request expiry, whichever comes first. Scope/draft changes require another preview/token. Approval requires the same live session and token; origin headers, surface labels and readable hashes are insufficient. Token hashes and consumption metadata live with the protected request decision and are consumed atomically with its claim. Tokens never enter MCP reads, transcripts, URLs or events. Logout/account switch invalidates outstanding tokens; another owner device signs in and obtains its own preview/token. Closing a UI does not revoke an already committed decision.

All answer aliases, retries that can dispatch an effect, and scope-rule writes enforce this boundary. Bearer-only callers cannot approve or loosen rules to bypass it. Automated clients can request/read work and act under existing owner-granted rules. This restriction authenticates who made an approval; it does not make an otherwise autonomous action ask first.

### Scopes and policy digest

Once is a decision consumed by one execution reservation, not a Rules row. Task and always extend the existing `rules` table with visible, revocable preapproval rows for the displayed agent/connection/operation/destination predicate. Task also pins task ID/generation and expiry; always persists until revoked or superseded. Wider scopes allow draft changes only within that predicate and existing consent. Deny creates no grant. Existing deposit consent and don't-ask-again semantics remain, but cannot substitute for a bound action decision.

A valid once decision or matching active task/always grant counts as preapproval for `do_if_preapproved`. For ask_first it satisfies the owner's scoped approval; hand_off still hands off and do acts directly. Missing preapproval retains the existing do_if_preapproved refusal/handoff behavior, without inventing an ask-first policy. Later applicable owner policy edits invalidate old grants. Revocation, binding and consent changes win; never substitute the selected agent or main.

The policy digest hashes only matching behavior rules (including revisions and precedence), applicable operation classification and owner review settings. Exclude ALL preapproval grant rows and individual decisions, not merely the new grant. At dispatch, recompute this digest and compare it with the approved envelope for every decision, including once, and with the issuing digest for any task/always grant. Separately validate a grant's revocation, scope and expiry. A mismatch invalidates the un-dispatched approval/reservation: refuse dispatch and require a fresh preview under current policy; never reinterpret the old decision as permission under the new rule. Approving A in any scope therefore cannot stale B. A behavior-policy edit matching B does stale B; unrelated edits do not. A broad grant never silently consumes another already pending card; that card still needs its displayed decision or an explicit fresh preview under changed policy.

## Task identity and expiry

Use the protected `activities` record as task identity. Background work uses its activity ID; each scheduled/automation occurrence uses its own run activity, never the recurring schedule ID. For an app/MCP chat without an activity, create a continuation-only activity at admission of the originating owner turn, bound to server owner/home, agent, conversation and turn IDs. It consumes no extra runner seat and is not a second background job. Requests and continuation turns inherit it until the original work ends; unrelated owner turns get new tasks. Client-supplied IDs cannot join another task. A connector without stable conversation identity binds to its server-recorded originating invocation; missing continuation context holds visibly rather than guessing.

Task ends on original-work completion, cancellation, addressed Stop or recorded expiry; a turn waiting for an answer does not end it. At admission record absolute task expiry (editable starter owner setting: 24 hours). Each preview records an execution deadline (editable starter setting: 30 minutes), capped by task expiry. Show deadlines in the card and bind them into the action. Changed duration settings apply to new tasks/previews, never silently extend an approval. Check expiry at preview, claim and immediately before dispatch.

Termination increments task generation and invalidates pending approvals, un-dispatched reservations and task grants. Addressed Stop applies to the addressed agent's affected work, not another agent. Resume after termination requires a fresh task generation, preview and owner decision; an always rule may survive but cannot resurrect a cancelled card. Already-sent effects cannot be unsent: retain their receipt/unknown outcome and reconcile without fresh blind retry. Expired/cancelled cards stay visible with a reason and re-preview option.

## Storage and transaction contract

Reuse existing tables; do not create `request_controls`, `scoped_approval_rules` or `request_events`. Move the existing pending-request tables into protected `.agent-sessions/<universe>/agent-activities.db`, outside agent-writable storage, alongside reservations and wakes. Keep `rules` in `rules.db`. JSON/text fields are TEXT, counters INTEGER, timestamps UTC epoch REAL.

| Existing table | Extension and sole authority |
|---|---|
| `pending_requests` and existing item answers/suppressions/unmutes | Add revision, context_json, action_sha256, policy_digest, expires_at, decision_json, effect_intent_key; protected action_json stores the validated envelope. Status owns request disposition, including deferred/expired/cancelled; no second stored request phase. |
| `activities` | Add task generation/expiry and a continuation-only foreground origin; retain owner/agent/session provenance and task lifecycle. |
| `effect_intents` | Reuse intent_key, wire_digest, receipt/resolution and planned/sent/confirmed/failed/unknown/owner_resolved states. Add request ID/revision and decision reference, with UNIQUE(request ID, approved revision). No duplicate reservation/uncertainty state in requests. |
| `activity_events` | Add UNIQUE dedupe key, request ID/revision, sanitized payload, wake-required, admitted-turn/attempt reference and processed-ack (terminal continuation result reference and timestamp). Reuse (activity_id, seq). This protected row owns coordinator dedupe and processing acknowledgment. Existing delivered remains presentation delivery, distinct from admission and processing. |
| `rules` | Add record kind (behavior/preapproval), destination predicate, scope (task/always), task ID/generation, expiry, issuing decision ID UNIQUE, issuing policy digest, agent binding/connection revision/consent digest and revocation state. Extend uniqueness to distinguish scopes/predicates while preserving legacy behavior precedence. |

API phase is derived from request disposition and its effect state (sent = executing, unknown = uncertain), never stored as a parallel lifecycle. Results come from effect receipts; ordinary answers from request/item records. Once decisions appear in card history, not the Rules list. Decision metadata records actor/session reference (never its secret), choice, scope, revision/hash, predicate and time. Actions contain credential references only; results/events are sanitized.

The server-side owner-control coordinator owns one exclusive lock keyed by owner/home, enforced across all workers serving that owner. Request mutations, grant finalization/recovery, behavior-rule edits, revocation, Stop, dispatch authorization and migration cutover all acquire this same lock; independent process-local locks are insufficient. Hold it across the ordered activity-store/rules.db steps, without claiming a cross-database transaction. Losing ownership fences further writes/dispatch; a replacement acquires the lock and reconciles unfinished decisions before allowing new dispatch.

In one activity-store transaction consume the token, CAS request revision/status/task generation, record the decision, reserve `request_id:approved_revision` and append the event. Once needs no rule write. Task/always materialization in rules.db is a separate idempotent step keyed by decision ID, NOT a cross-database atomic commit. Until it succeeds and the activity-store decision is marked finalized, its grant is unusable and the planned effect cannot dispatch. Under the owner-control lock, recovery revalidates current policy digest, task/generation/deadline, session, binding, consent and revocation, then finds or inserts the grant by decision ID and finalizes the decision. Recovery retries only these metadata steps, never an external effect. A mismatching existing grant or invalidated decision stays inert, is recorded as invalidated and requires re-preview; never overwrite later owner edits or recreate revoked grants. Grant readers require the finalized issuing decision. Crashes leave recoverable decisions or inert grants, never executable partial approval.

Immediately before dispatch, under the owner-control lock shared with policy edits and Stop/revocation, recheck finalized decision, deadlines, generation and ordinary enforcement, and recompute/compare the applicable policy digest for once as well as task/always. If a once-approved ask_first action now matches hand_off, refuse that reservation and require a fresh preview; do not send it. Only after all checks pass mark the intent sent before releasing dispatch. Reuse the key for receipts/provider idempotency. Duplicate answers return current state. A possibly completed effect stays unknown: retry needs proven non-execution or supported idempotency and still-valid authority. Commit effect result, request completion and wake together in the activity store. Failed/deferred/uncertain work stays visibly unresolved. Account deletion removes the protected records through existing cleanup.

## Continuation and boot recovery

The common answer path records one sanitized logical outcome/wake per committed answer: approval wakes on execution result, ordinary/item answers on their answer, OAuth on deposit success. Duplicate answer/result commits reuse that event. Route to the saved agent/task/conversation through existing turn coordination; serialize with live work and deduplicate through processing, not merely admission. Remove the page relay. Connection success yields one-line confirmation and continuation of the original task without another prompt. Missing context/power stays visibly pending. Terminated tasks get no automatic continuation or dispatch; retain their unprocessed wake visibly held for fresh owner resumption, never acknowledge it as processed just to remove it.

Before new dispatch on EVERY boot, sweep unfinished decisions, planned/sent/unknown intents and ALL wake-required activity_events without a processed-ack, including admitted turns interrupted by a deploy or reported done by a coordinator shutdown journal. Reconcile grant finalization, preserve uncertain effects, invalidate expired/stopped work and re-deliver eligible wakes using `(owner, activity_id, seq)` as the durable dedupe key. Repeat during runtime recovery and when power/context returns, until processing is acknowledged. A live attempt retains its turn reference; after fencing an abandoned attempt, re-admit the same logical wake with a new attempt reference. Admission or a journal's generic done/failed flag is not proof of processing.

The authoritative dedupe record is the wake's protected activity_events row in `agent-activities.db`, not the coordinator's progress journal. Claim/update its attempt reference durably before execution and permit only one live attempt per key. In one activity-store transaction, commit the terminal continuation result (or its durable reference) and CAS the processed-ack for that key; a fenced attempt cannot commit. A retry after this transaction observes the acknowledgment and returns the existing result without another continuation. A crash before it leaves the wake eligible for recovery, including a terminal turn whose acknowledgment never committed. This gives exactly one committed processing result per answer; interrupted computation may retry, and all external-effect replay safety still comes from effect_intents and reconciliation, never the wake dedupe key.

Retain every unprocessed wake, its payload and dedupe/attempt record beyond ordinary event trimming (including MAX_EVENTS), even when already admitted; presentation delivery cannot acknowledge processing. After acknowledgment, retain the dedupe/processed tombstone for at least as long as the originating answer/request or any admission/recovery reference can be replayed, and delete it only after those sources and attempts are retired. Dedupe therefore outlives the wake payload. Retain unresolved decisions/intents as well. Reuse activity_events for foreground and background outcomes; automation_events keeps its scheduler role. No third event log.

## Server-completed OAuth, web and native

Reuse `/app/model-connect/{operation}` and `/app/model-callback/{flow}`. Every new inline Connect first opens a top-level TinyAssets hop in the popup/system browser. Before generating provider state or redirecting, that hop authenticates the owner's interactive browser session and checks it owns the initiating request/home. Native flows establish this session by interactive sign-in in that system-browser context if absent; a launch URL or native/API bearer cannot establish it or transfer another session's flow. Bind the state at creation to that exact browser session ID and owner/home (and the initiating native session where applicable). Never rebind an existing flow to a session supplied at callback.

Generate PKCE on the SERVER and store the verifier encrypted through existing credential custody; the existing flow row holds only ciphertext/reference. Extend it with server-completion mode, custody reference, initiating browser session reference, flow-cookie binding digest, request revision/digest, task generation and completion/deposit state. Bind state handle digest, owner/home, issuer, redirect URI, client, consent and existing ten-minute flow expiry. The hop sets a flow-specific `__Host-` cookie, Secure, HttpOnly, SameSite=Lax, Path=/, no Domain, with expiry capped by the flow; its opaque server-validated value binds the state digest to that same session. Separate flow cookies permit concurrent flows. The owner-session cookie used here is also Secure, HttpOnly and SameSite=Lax; use a top-level GET callback so both cookies accompany the provider redirect. Only the authorization URL/challenge reaches the provider; neither popup nor system browser needs a verifier or app bearer.

The provider redirects to the callback route's SERVER handler, replacing shell-only completion for server-custody flows. Before claiming state or exchanging a code, require BOTH the callback request's live owner-session cookie matching the exact initiating browser session and its matching flow-binding cookie. Verify unexpired one-time state, issuer, code, owner/home and all stored bindings, including request/task/consent and any initiating native-session revocation. A persisted session that is still valid elsewhere is insufficient. Missing/mismatched cookies, another browser (even signed in as the same owner), logout or account switching refuse exchange/deposit/wake; state possession alone never authorizes completion. Recheck session validity and bindings before deposit, serializing with session revocation/account switching. The deposit destination comes only from the immutable initiating owner/home, never callback parameters or a replacement session.

The callback page itself carries the owner's browser session and flow cookie, so web popup and native system browser complete with the parent closed or native app suspended; closing/suspending alone is not logout. No app bearer, postMessage, native deep-link return or client complete call is needed for exchange, deposit or wake. Opening a copied provider authorization URL in a different browser cannot deposit anyone's provider credential into the initiating owner's vault. Clear the flow cookie on success, terminal failure or expiry.

Claim callback state durably before exchange to prevent duplicate redemption. Deposit through existing vault custody and persist an idempotent completion receipt keyed by flow; then commit request completion plus wake. Do not assume flow/vault and activity stores are atomic: boot/runtime recovery scans deposited-but-unacknowledged receipts and repeats only the idempotent request/wake commit. A crash with uncertain redemption/deposit holds visibly for reconciliation or fresh sign-in, never invented success. Delete verifier custody on success, terminal failure or expiry; retain only sanitized recovery receipts. Callback pages never reflect codes/secrets; redact code/state in logs, use no-store/no-referrer and strip callback parameters before rendering. Optional exact-origin messages carry only an opaque flow reference and refresh UI.

Blocked/closed/failed sign-in keeps the card pending with retry/alternative/skip. Replay, expiry and account switching cannot bind another request. Existing client-PKCE flows stay explicitly tagged and cannot be treated as server-completable; new inline flows always use server custody. No provider-specific routes or full-page app redirects. Existing private key deposit remains available where supported; Google/LinkedIn coverage waits for directory/registration follow-up.

## Migration and risks

The owner-control coordinator acquires its owner/home lock, persists a migration-in-progress marker and drains already admitted request mutations before taking the source snapshot. During this pause, new `ask`, answers/edits, approval/retry/grant mutations and new bound dispatch/resumption are refused with an explicit retryable migration-unavailable result; they are neither queued nor acknowledged successful and create no partial request/decision/wake. Ordinary reads use the last authoritative store. Already-sent effects and OAuth deposits retain their existing durable receipts for post-cutover reconciliation; do not claim they were cancelled or lose their outcomes. If old writers cannot be stopped, keep the owner paused and do not cut over.

Copy all pending-request tables to the protected activity store idempotently, preserving legacy requests/items/answers/suppressions/unmutes verbatim. Verify row IDs/counts/content against the quiescent source; commit the verified copy and authoritative cutover marker together in the destination transaction before enabling protected writers. All APIs consult that marker and then use only the protected copy; the old file is retained as migration backup, never a live projection/authority. Before cutover, interrupted/failed verification keeps the pause active and resumes from the unchanged source. After cutover, restart uses only the protected destination, reconciles unfinished decisions/grants and retained receipts/wakes under the owner-control lock, then lifts the pause. It never recopies the stale backup over newer protected state or accepts legacy writers. Failures remain visibly retryable while paused, with no automatic fallback to the legacy store.

Backfill only verified provenance, hold unlinked continuation and require newly bound previews for legacy approvals. Legacy prose cannot become a trusted preview. No original store is deleted without verified recovery provenance. Rollback pauses bound execution/resumption and preserves protected records; it may serve the protected store only with compatible handlers, otherwise stays paused for forward recovery. Never restore dual writers or bypassing legacy approval handlers.

External APIs cannot promise exactly-once effects; reconcile uncertainty before retry. Reuse addressed-agent-control-provenance and fail visibly on missing context rather than borrowing main's rules. This is a proposal-only revision; implementation and live acceptance remain future work.
