## Interaction and authority

Place requests beside their originating turn (background requests in the initiating agent's thread). Connect shows plain-word scope and Connect / Not now. Approval shows summary, editable draft, Approve / Edit / Deny and once / this task / always, default once. Edit returns a fresh preview without execution. Other connect entry points focus this card; the rail becomes read-only history. Secrets never enter transcript messages. Failure preserves the request/draft with Try again / available alternative / skip. Not now defers; denial/skip records an explicit outcome.

For ask_first, the trusted dispatcher stores `{version:1, executor, arguments, subject, connection_revision, consent_digest, policy_digest, expires_at}`. Executor is an existing generic operation; arguments are validated non-secret inputs; subject pins authenticated owner/home, initiating agent/binding revision, task ID/generation, conversation and turn. Hash RFC 8785 canonical JSON with SHA-256; pin referenced file/body versions and digests without changing transmitted bytes. The server renders the summary, destination, draft, attachments, scope and identity from this protected envelope and pinned payloads. Agent prose is separately labeled context, never the approval preview or editable authority. Missing/inconsistent protected data requires a fresh preview and disables approval.

Approve claims the displayed revision/hash and executes server-side through current ordinary enforcement: isolation, custody, grants, consent, initiating-agent rules and owner-configured review. Edits or changed authority/policy require a fresh preview. No agent retry turn. Only owner rules choose ask_first; do, hand_off and do_if_preapproved retain their meanings. Defaults remain editable. Authenticating an owner decision creates no platform-mandated approval gate; cross-user isolation remains the fixed policy floor.

### Interactive owner approval

Only the owner's signed-in first-party web app or native app's protected first-party approval view can approve. Custom layouts, universe content, runtime agents, CLI and chatbot/MCP connectors, even with the owner's bearer, are not interactive owner sessions. Introduce a distinct server session established by verified interactive owner sign-in; an API/MCP bearer cannot mint, upgrade into or refresh it. Web uses a Secure, HttpOnly, SameSite cookie plus origin/CSRF checks on a protected app origin inaccessible to custom layouts. Native uses an interactive-login session credential in OS-protected storage exposed only to the first-party view, never the agent bridge.

The protected preview endpoint issues an opaque single-use approval token bound to session ID, owner/home, request ID, revision/hash, selected scope/predicate and task generation. Expiry is five minutes or session/request expiry, whichever comes first. Scope/draft changes require another preview/token. Approval requires the same live session and token; origin headers, surface labels and readable hashes are insufficient. Token hashes and consumption metadata live with the protected request decision and are consumed atomically with its claim. Tokens never enter MCP reads, transcripts, URLs or events. Logout/account switch invalidates outstanding tokens; another owner device signs in and obtains its own preview/token. Closing a UI does not revoke an already committed decision.

All answer aliases, retries that can dispatch an effect, and scope-rule writes enforce this boundary. Bearer-only callers cannot approve or loosen rules to bypass it. Automated clients can request/read work and act under existing owner-granted rules. This restriction authenticates who made an approval; it does not make an otherwise autonomous action ask first.

### Scopes and policy digest

Once is a decision consumed by one execution reservation, not a Rules row. Task and always extend the existing `rules` table with visible, revocable preapproval rows for the displayed agent/connection/operation/destination predicate. Task also pins task ID/generation and expiry; always persists until revoked or superseded. Wider scopes allow draft changes only within that predicate and existing consent. Deny creates no grant. Existing deposit consent and don't-ask-again semantics remain, but cannot substitute for a bound action decision.

A valid once decision or matching active task/always grant counts as preapproval for `do_if_preapproved`. For ask_first it satisfies the owner's scoped approval; hand_off still hands off and do acts directly. Missing preapproval retains the existing do_if_preapproved refusal/handoff behavior, without inventing an ask-first policy. Later applicable owner policy edits invalidate old grants. Revocation, binding and consent changes win; never substitute the selected agent or main.

The policy digest hashes only matching behavior rules (including revisions and precedence), applicable operation classification and owner review settings. Exclude ALL preapproval grant rows and individual decisions, not merely the new grant. Separately validate a grant's revocation, scope, expiry and issuing policy digest at execution. Approving A in any scope therefore cannot stale B. A behavior-policy edit matching B does stale B; unrelated edits do not. A broad grant never silently consumes another already pending card; that card still needs its displayed decision or an explicit fresh preview under changed policy.

## Task identity and expiry

Use the protected `activities` record as task identity. Background work uses its activity ID; each scheduled/automation occurrence uses its own run activity, never the recurring schedule ID. For an app/MCP chat without an activity, create a continuation-only activity at admission of the originating owner turn, bound to server owner/home, agent, conversation and turn IDs. It consumes no extra runner seat and is not a second background job. Requests and continuation turns inherit it until the original work ends; unrelated owner turns get new tasks. Client-supplied IDs cannot join another task. A connector without stable conversation identity binds to its server-recorded originating invocation; missing continuation context holds visibly rather than guessing.

Task ends on original-work completion, cancellation, addressed Stop or recorded expiry; a turn waiting for an answer does not end it. At admission record absolute task expiry (editable starter owner setting: 24 hours). Each preview records an execution deadline (editable starter setting: 30 minutes), capped by task expiry. Show deadlines in the card and bind them into the action. Changed duration settings apply to new tasks/previews, never silently extend an approval. Check expiry at preview, claim and immediately before dispatch.

Termination increments task generation and invalidates pending approvals, un-dispatched reservations and task grants. Addressed Stop applies to the addressed agent's affected work, not another agent. Resume after termination requires a fresh task generation, preview and owner decision; an always rule may survive but cannot resurrect a cancelled card. Already-sent effects cannot be unsent: retain their receipt/unknown outcome and reconcile without fresh blind retry. Expired/cancelled cards stay visible with a reason and re-preview option.

API phase is derived from request disposition and its effect state (sent = executing, unknown = uncertain), never stored as a parallel lifecycle. Results come from effect receipts; ordinary answers from request/item records. Once decisions appear in card history, not the Rules list. Decision metadata records actor/session reference (never its secret), choice, scope, revision/hash, predicate and time. Actions contain credential references only; results/events are sanitized.

In one activity-store transaction consume the token, CAS request revision/status/task generation, record the decision, reserve `request_id:approved_revision` and append the event. Once needs no rule write. Task/always materialization in rules.db is a separate idempotent step keyed by decision ID, NOT a cross-database atomic commit. Until it succeeds and the activity-store decision is marked finalized, its grant is unusable and the planned effect cannot dispatch. Recovery retries only grant finalization. Serialize finalization with owner policy edits/revocation and recheck policy/task/session then; invalidated decisions require re-preview. Never overwrite later owner edits or recreate revoked grants. Grant readers require the finalized issuing decision. Crashes leave recoverable decisions or inert grants, never executable partial approval.

Immediately before dispatch recheck finalized decision, deadlines, generation and ordinary enforcement under the same owner control serialization as Stop/revocation, then mark the intent sent before releasing dispatch. Reuse the key for receipts/provider idempotency. Duplicate answers return current state. A possibly completed effect stays unknown: retry needs proven non-execution or supported idempotency and still-valid authority. Commit effect result, request completion and wake together in the activity store. Failed/deferred/uncertain work stays visibly unresolved. Account deletion removes the protected records through existing cleanup.

## Continuation and boot recovery

The common answer path records sanitized outcomes: approval wakes on execution result, ordinary/item answers on their answer, OAuth on deposit success. Route to the saved agent/task/conversation through existing turn coordination; serialize with live work and deduplicate at admission. Remove the page relay. Connection success yields one-line confirmation and continuation of the original task without another prompt. Missing context/power stays visibly pending. Terminated tasks get no automatic continuation or dispatch; retain results and offer fresh owner resumption.

Before new dispatch on EVERY boot, sweep unfinished decisions, planned/sent/unknown intents and activity_events needing a wake without an admitted-turn reference. Reconcile grant finalization, preserve uncertain effects, invalidate expired/stopped work and submit eligible wakes using `(owner, activity_id, seq)` as the coordinator's durable dedupe key. Record the turn reference only after durable admission. A crash between admission and marking retries the same key and receives the same turn. Repeat during runtime recovery and when power/context returns. Retain unadmitted wakes and unresolved decisions/intents beyond ordinary event trimming (including MAX_EVENTS); display delivery cannot mark admission. Reuse activity_events for foreground and background outcomes; automation_events keeps its scheduler role. No third event log.

## Server-completed OAuth, web and native

Reuse `/app/model-connect/{operation}` and `/app/model-callback/{flow}`. For new inline flows, authenticated interactive Connect generates PKCE on the SERVER. Store the verifier encrypted through existing server credential custody; the existing flow row holds only ciphertext/reference. Extend that row with server-completion mode, custody reference, initiating session reference, request revision/digest, task generation and completion/deposit state. Bind state handle digest, owner/home, issuer, redirect URI, client, consent and existing ten-minute flow expiry. Only the authorization URL/challenge reaches the popup/system browser; neither needs a verifier or owner bearer.

The provider redirects to the callback route's SERVER handler, replacing shell-only completion for server-custody flows. It validates unexpired one-time state, issuer, code and stored bindings, retrieves the verifier and exchanges the code itself. The narrowly scoped callback authenticates through bound state and persisted initiating session; it requires no app bearer. Check that session was not revoked/account-switched and request/task/consent remain current. Web popup and native system browser use this identical path with parent closed or native app suspended. Closing/suspending alone is not logout. No postMessage, native deep-link return or client complete call is needed for exchange, deposit or wake.

Claim callback state durably before exchange to prevent duplicate redemption. Deposit through existing vault custody and persist an idempotent completion receipt keyed by flow; then commit request completion plus wake. Do not assume flow/vault and activity stores are atomic: boot/runtime recovery scans deposited-but-unacknowledged receipts and repeats only the idempotent request/wake commit. Blocked/closed/failed sign-in keeps the card pending with retry/alternative/skip. Replay, expiry and account switching cannot bind another request. ## Migration and risks

Under a per-owner write pause, copy pending-request tables to the protected activity store, verify row IDs/counts/content and write a cutover marker before enabling new writers. All APIs then use only the protected copy. The old file is retained as migration backup, never a live projection/authority; interrupted copying resumes idempotently before cutover. Preserve legacy requests/items/suppressions verbatim. Backfill only verified provenance, hold unlinked continuation and require newly bound previews for legacy approvals. Legacy prose cannot become a trusted preview. No original store is deleted without verified recovery provenance. Rollback pauses bound execution/resumption and preserves protected records; never restore dual writers or bypassing legacy approval handlers.

External APIs cannot promise exactly-once effects; reconcile uncertainty before retry. Reuse addressed-agent-control-provenance and fail visibly on missing context rather than borrowing main's rules. This is a proposal-only revision; implementation and live acceptance remain future work.
