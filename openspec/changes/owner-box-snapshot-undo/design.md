## Context

Binding basis: `../owner-daemon-in-box/research.md`, design T1-T10, C1/C2/C10 and C14/C15; registry N6/S27/N10. One opaque volume holds owner state; shared lifecycle knows volume/snapshot IDs, never content paths. N6 adds callers, not a second snapshot engine.

## Founder decision (2026-10-23)

Undo points are automatic sleep snapshots plus owner-requested checkpoints ("save a restore point"). No per-turn or per-session checkpoints and no pause between messages for N6. C2's existing 24-hour durability stop remains unchanged. Use the existing seven-snapshot retention, not a separate undo archive or turn pin.

## Decisions

1. **Triggers and handoff.** Ordinary C2 sleep already publishes an undo point. An explicit owner checkpoint closes in-box work admission, drains running work (or waits for existing owner cancellation to finish), then requests the same graceful sleep: flush, exit, clean unmount/detach, immutable copy, upload/readback verification and publication. A failed publication stays retryable under the existing lifecycle intent; the app reports failure/pending, never a usable point. Ordinary messages and scheduled turns do not request checkpoints. App confirmation/status and queued work remain in-box; shared lifecycle carries only opaque IDs.
2. **One catalog.** List retained C2 snapshots by ID/time. Keep the latest seven plus existing supported platform recovery references. Manual checkpoints and the pre-restore sleep snapshot occupy ordinary slots; neither gets a permanent pin. Protect a selected restore source only for the pending lifecycle operation, using existing recovery-reference protection, so publishing the current state cannot prune the selected source. Release that operation reference after completion. No pre-turn association, turn-checkpoint pin or turn semantics in shared code. Later retention may remove a redo point; show only retained choices.
3. **Exact restore authority (N10).** Proposed protected action `POST /app/owner/restore` follows N10's owner-session route: browser confirmation of snapshot ID + expected volume generation -> router authenticates the owner, checks same-origin JSON and `owner_sessions.require`, derives owner identity and forwards the opaque fields plus session proof on its protected broker channel -> broker revalidates the live owner-session proof against that owner (the same N10 session authority used by `PolicyStore._session`), admission, retained snapshot ownership and expected generation under the owner lifecycle lock -> existing `VolumeLifecycle.restore(owner, snapshot_id)` -> existing boxhostd/`OwnerVolumes` opaque executor. This is a proposed route, not an existing implementation claim. The route does no owner-data lookup; UI and approval-request meaning stay in-box. Session proof is never forwarded to the box. Box-channel calls, agent proposals, caller-supplied owner IDs and forged/stale confirmations cannot authorize restore; the agent may only raise a Needs you request. The broker receipts the protected action. N10 authority must be proven before implementing this caller.
4. **Preserve current state first.** Under that same serialized restore operation, close admission, drain/cancel running work and complete ordinary sleep. Publish and verify the pre-restore sleep snapshot BEFORE installing the selected older image or superseding the pending snapshot intent. Persist this ordering in the existing lifecycle work so a crash resumes it. Publication/storage failure leaves the current image intact and reports pending/failure; it must never fall through to restore. Then invoke ordinary C2 restore, commit the new volume generation before restart and retain the pre-restore point in the same catalog. The confirmation says: "Restore the whole box to TIME? Later files, chat/history, skills, packages and schedules will rewind. Your current state is saved as a restore point first, available until normal retention removes it. External sends, purchases and publications cannot be undone." Identity, admission, credentials, billing, spending and N5 policy remain current.
5. **Interactive requests across restore.** Before shutdown, the in-box handler completes waiting app/MCP calls whose turns cannot finish with an explicit `interrupted_by_restore` result and old operation ID/generation. Running turns drain or finish owner cancellation; no request is held across upload or restart. A dropped transport is an unknown outcome, never permission for automatic replay. The client reconnects for current status; old-generation requests refuse, and retrying work requires explicit owner resubmission with a fresh ID. The router only forwards or reports transport unavailability; it never stores turn payloads or reconstructs responses. Explicit checkpoint status likewise reconnects after sleep; it does not keep a router-held interactive call alive.
6. **Resume after rewind.** The restored box validates its databases, invalidates restored pending approvals, and pauses restored queued turns/schedules before admitting work. Nothing restored executes until explicit owner resumption with fresh-generation IDs; previous-generation operations refuse. New requests during restore receive unavailable/retry status, never queue in shared services. Record the restore result in-box after validation. Undoing the undo selects the retained pre-restore snapshot through the same protected flow, saving current state first again.

## Storage fit (C10 and the 5 GiB free tier)

The free owner keeps the existing 5 GiB volume ceiling; N6 neither shrinks it nor adds a second quota. At full incompressible capacity, seven images represent about 35 GiB off-host (plus compression framing), exactly the existing C2 baseline. Sleep points add zero N6 snapshot bytes or transfers. Manual checkpoints replace ordinary retention slots, not seven extra copies; publication temporarily needs an eighth image (about 40 GiB total), then ordinary pruning. Existing platform recovery pins and the temporary restore-source reference must also be counted; no assumption that compression or reflinks eliminate worst-case bytes.

C10 already budgets at most 100 GiB local volume ($10/month) plus $5 Spaces within the founder's $15/month fleet cap (`../owner-daemon-in-box/design.md`, C10). For one full free-tier owner, conservatively reserve 5 GiB live + 5 GiB immutable copy + 5 GiB compressed staging + 5 GiB restore staging (about 20 GiB plus overhead); remote peak is about 40 GiB plus existing recovery pins. [Spaces pricing](https://www.digitalocean.com/pricing/spaces-object-storage) includes 250 GiB storage and 1 TiB outbound transfer for $5/month (checked 2026-10-22). A full owner's 40 GiB publication peak fits that included storage; 30 daily full-image readbacks use about 150 GiB/month, leaving about 874 GiB for manual checkpoints, restores and other fleet traffic before overhead. These are fleet-shared allowances, not per-owner entitlements; existing backups and pins consume the same headroom. Thus N6 reuses C2's steady-state storage and C10's capacity envelope; it does not promise that unlimited full owners fit $15. Before an explicit checkpoint or restore, existing storage capacity accounting must cover the fleet's local staging, remote retained/pinned/temporary bytes and upload/readback transfer cost within that cap. If headroom is insufficient, refuse the optional action visibly before replacing current state; never expand spending, prune a supported reference or shrink 5 GiB. Normal C2 failed-snapshot retry remains unchanged. Repeated owner requests are serialized/coalesced while pending, not a per-message upload loop.

## Shared surface and proof

Before fixing a finding, ask whether its class exists in T1-T10: turn checkpoint orchestration/pins do not belong in shared code and are removed from this design; broker restore authority, opaque lifecycle ordering and egress authority do. Shared changes are confined to N10 protected transport and the existing `tinyassets/broker/volume_lifecycle.py`/`owner_volumes` intent and recovery references. `boxes/volumes.py` and the off-host format remain the one S27 executor. No shared owner scheduler, history copy, content scanner or host path to owner data.

Planned **`box-snapshot`** proof: `tests/test_owner_volume_structure.py` proves one lifecycle/executor and no shared turn pin; `tests/test_owner_volume_lifecycle.py` covers publish-before-restore, failure/restart ordering, selected-source retention, concurrent wake, deletion and headroom refusal. `tests/test_owner_volumes_proof.py` uses the disposable Linux mount venue for full-volume restore and no shared traversal. N10/in-box acceptance covers forged box calls, stale sessions/generations, waiting interactive calls, current-state recovery, paused restored queues and unchanged platform authority. Measure sparse/full 5 GiB peak local/remote bytes and transfer costs against the existing C10 fleet budget; no production access is required for this spec round.

## Implementation gate

C6 registry close-out, C1/C2/S27 recovery proof and N10 protected authority precede implementation. Use the settled sleep/manual trigger and seven-snapshot retention; capacity measurements verify the existing envelope, not defer the trigger decision. Rollback may hide Undo but preserves recovery references. The undo caller, publish-before-restore ordering, and in-box settlement are implemented here. Task 1.1 and acceptance 3.1 stay open: live 5 GiB measurement, floor review, naive-owner undo after deployment, and the delta sync are not claimed. As-built specs remain unsynced.
