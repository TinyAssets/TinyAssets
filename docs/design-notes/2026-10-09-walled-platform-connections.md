## Decision

**Keep the proposed end state. No verified product or standard solves all OAuth problems or guarantees one-tap access to an unanticipated, uncooperative platform.** Browser use removes the need for an API client registration *for that browser workflow*; it does not remove the site's login, anti-automation controls, account restrictions or authority over access. Discovery removes configuration only where the service supports it.
The meaningful improvements are **reuse an existing session**, **protected password-manager filling**, **a single interruption with automatic continuation**, and eventually **WebMCP inside the authenticated browser**. Local session reuse is often smoother today, but making it mandatory violates zero-host uptime. Enterprise delegated authorization can remove repeated consent inside a cooperating trust domain; it cannot unlock consumer TikTok/LinkedIn/X. [P3–P12, S1–S9]
The user's platform account, developer registration, bill and quota remain theirs. No TinyAssets social app of record, shared API project, integration aggregator or per-platform platform code. Agent-written skills/extensions may describe site workflows; the browser/auth primitives stay generic.

## Counting honestly

Start after the user has installed/signed into the agent and submitted their task. Count extra clicks/taps to connect; opening the assistant and submitting the task are excluded unless explicitly stated. **L** = the site's login controls, account picker, autofill/biometric confirmation, MFA and CAPTCHA; **A** = additional site-access/action approvals; **S** = installation/developer setup. These are not zero and have no universal upper bound. Text entry and waiting are additional effort. “0” means no *connection* taps with an already valid, permitted session, not zero action approvals.
Where docs name every wrapper control, a formula is exact for that documented branch. Where they omit controls, **≥** is a lower bound; **?** is unknown. Do not advertise a total by silently dropping L/A/S. A successful login proves authentication, not that posting, uploading or messaging will work.

## Standards and techniques: what they actually remove

| **Transaction Tokens -11**, WG draft, July 30 2026 [S3] | Preserve user/workload/request context through a transaction inside a trust domain. | Not OAuth access tokens or login credentials; no first-connection UX improvement on an external site. **Defer**, useful only if internal multi-service delegation needs it. |

## Adopt / adapt / avoid and recommended end state

1. **Adopt the browser-first request**: “Connect LinkedIn” or an unknown URL produces one origin-labelled **Sign in** action in the task. Open directly in owner takeover, not view → take control → another login screen. Keep the task waiting durably and resume automatically after verified success; no “continue” chat message. Existing valid permitted session: **0 connection taps**. First sign-in: target **1+L+A**; fallback explicit Return control makes **2+L+A**. These are design targets, not shipped or competitor measurements.
2. **Adapt secure autofill**: native owner form can use OS password manager and send credentials only to the bound remote browser. Best supported saved-login case: **1 opening tap + 1 autofill/approval gesture**, plus any site submit/MFA and biometric operation; don't call it universally two taps. Distinguish “session remembered” from “password stored,” show account and origin, and offer revoke/clear in one connection entry. Passwordless-only remote sites need a tested supported ceremony, not a fake success state.
3. **Keep structured connections**: self-describing OAuth remains an available efficient route with existing generic discovery, PKCE/callback and refresh. Target **1 Connect + provider consent/account/MFA**, **0** after a valid reusable grant. If registration is missing, explain it once and offer browser sign-in or optional owner's developer app. App creation/review/credit purchase is **S+L+A, variable and potentially unavailable**, never a one-tap claim. User pays platform directly; no hidden TinyAssets fallback key.
4. **Adapt optional local attachment** for users who already have a trusted session or sites that reject cloud browsers: after one-time S, **0–1 connection permission taps+A**, otherwise L. Label device required and preserve the cloud default for every user with no host online. A phone can request local work, but cannot keep an offline desktop's browser running. No mandatory proprietary cloud-browser provider.
5. **Preserve custody and recovery** in `browser-login-custody`: owner-isolated broker profile inaccessible to agent shell, opaque handle, origin/account binding, suspended agent input/observation/traces during login, durable completion, cancel/revoke/account-switch fencing. Cookies are reusable credentials even without saved passwords. Persist them only in owner custody with deletion/backup policy; session refresh differs from OAuth refresh. Expiry returns to the same request; CAPTCHA/MFA goes to the owner; detection/block is an honest blocked state, not repeated retries or stealth claims.
6. **Avoid borrowed authority**: shared developer apps/quotas, connector aggregators, reverse-engineered private APIs as a platform promise, copied cookie jars, autonomous collection of the user's OTP inbox, or claims that signing/SSO/payment standards override site policy. Do not copy Muse's platform-owned Sentinel model (ADR-006), Lindy's workspace-wide credentials, or Grok's all-Bots-share-everything as isolation requirements. Browser sign-in grants account access; action approval remains a separate, user-controlled decision.
