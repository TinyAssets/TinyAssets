# Harness architecture audit: make composition executable

Date: 2026-10-11. initial_provider: codex. Independent research; the concurrent Claude study/branch was not read. Recommendations, not accepted replacement ADRs. Product code and owner workflows are unchanged.

## Judgment

**The missing primitive is an owner-bound, explicitly model-selected invocation that every caller can compose.** Four tools and a common tool schema do not create that primitive. Today a request can enter a native vendor harness, our HTTP agent loop, a graph prompt, an agent-marked graph prompt, or an authenticated HTTP effect. These share parts of admission/accounting but have different selection, continuation and tool semantics. Calling a workflow “Codex review” establishes none of them.

The correct repair is to finish owner isolation and collapse those semantic paths, then expose invocation through `ta` to user-authored packages. Do not add a platform cross-family-review operator. Keep the accounting refusal: it correctly stops an unaccounted model request. Remove the architectural reason a legitimate caller needs to encounter it.

Most requested October 10 repairs are genuine cutover bugs, not evidence that users should implement sandbox plumbing. The stronger band-aid evidence is duplicated execution, partially connected customization APIs, and fixed product behavior above the floor. The founder's app is finding integration failures that launch fixtures and schema tests did not exercise.

## 1. What pi actually makes composable

| Layer | Concrete primitives | What the builder owns |
|---|---|---|
| `pi-ai` | `createModels`, provider registration, model lookup; `stream`/`complete` and `streamSimple`/`completeSimple`; serializable messages, tool schemas/calls/results, abort signals, normalized usage and cost. [P2] | Select a model object for each invocation; supply context and tools. Protocol differences stay below the API. |
| `pi-agent-core` | `Agent`, injectable `streamFn`, state/messages, tool execution, event subscription, `transformContext`, `convertToLlm`, `prepareRequest`, `finishTurn`, steering/follow-up queues, cancellation. [P3] | Build a harness without adopting the CLI or its UI; substitute context and execution behavior. |
| Coding-agent SDK | `createAgentSession`, `SessionManager`, settings, resource loader, model runtime, tool set, compaction, events; persistent JSONL session tree with active branch and forks. [P5] | Replace individual dependencies or the whole resource loader; use the same sessions in another application. Session storage, not a mutable UI transcript, is authoritative. |
| Extensions | TypeScript modules; tools, commands, flags, shortcuts, providers, MCP servers, virtual models, events, messages and durable custom entries. `context` transforms context; `tool_call` can modify/block; custom tool results separate model content from UI details. [P4] | Implement workflows, delegation, memory strategies, review policies and custom interactions without a core patch. |
| Files/packages | `AGENTS.md`, replacement/append system prompt, on-demand `SKILL.md`, Markdown prompt templates, themes; package manifest bundles resource directories from npm/git/local sources. [P7] | Author, install, share, reload and replace behavior. A skill is instructions; an extension supplies executable behavior. |
| Interfaces | `pi-tui` rendering/components, custom editors/widgets/overlays/renderers; SDK events or JSON/RPC over stdio for a separate front end. RPC supports a subset of extension dialogs, not arbitrary terminal components. [P5, P7] | Build a web/mobile/desktop UI over the session protocol; its controls invoke the same runtime. Historical `pi-web-ui` supplied chat/storage/artifact components but was removed; do not base a new integration on it. [P11] |

**Switching providers is changing the selected model, not installing another agent.** Supported endpoints are configured in `models.json`; custom authentication/discovery/streaming uses `registerProvider`. Context is normalized across models, subject to provider differences. For a nested one-shot judgment, an extension calls `ctx.modelRegistry.streamSimple(otherModel, context, options)` and reports nested usage in its result. For a full specialist, instantiate another SDK session or launch Pi with a different model. [P2, P4, P6]

The official subagent example loads Markdown frontmatter (`name`, `description`, `tools`, `model`) plus body instructions, spawns `pi --mode json -p --no-session`, passes the configured model, streams progress, collects usage, and propagates abort. Single/parallel/chained workflows are extension code; a reviewer is a file, not a provider-specific platform feature. Process separation isolates context, not necessarily filesystem/network authority. [P8, P9]

**Deliberate omissions, with the date caveat:** the coding agent does not prescribe a built-in subagent organization or plan mode; review/team policy belongs in extensions/files. Four default tools are `read`, `bash`, `edit`, `write`, with optional search/list/other tools. The 2025 essay's “no MCP” is obsolete: current CLI loads replaceable MCP/codemode/tool-search extensions, while SDK consumers opt into them. Pi also does not supply our multi-tenant credential custody, enforced owner budgets, cloud uptime or cross-user isolation. Its extensions can access process credentials. [P1, P5, P7, P9]

**Do not idealize pi as one tiny universal cloud runtime.** Pi Durable now supplies atomic transcript/document/task commits, persisted submissions, restartable tasks and composition for long-lived agents. It is experimental and distinct from the interactive coding agent. Adopt its commit-before-publish and generic durable-task ideas; do not add it as a third runtime beside LangGraph and our coordinator. Pi's low-level direct API imports can also bypass provider auth/context normalization; our governed public primitive must not expose such a bypass. [P2, P10]

The deficiency is not missing discovery; it is missing equivalence of the discovered capabilities. `tinyassets/served_tools.py` correctly gives models four tools and uses a broader backend grant. Neither shared inventory nor same-class tests prove equivalent provider behavior.

Provider-specific contradictions are concrete: `_CLI_REFS` in `tinyassets/api/compute_connection.py:42`, `_CLI_PROTOCOLS` in `tinyassets/providers/definition.py:54`, `_CLI_PROVIDER_CLASSES` in `tinyassets/providers/provider_resolver.py:34`, named registration in `tinyassets/providers/call.py:237–257`, Claude/Codex launch/catalog/telemetry implementations, `tinyassets/providers/ollama_provider.py`, and service-specific credential layouts/branches in `tinyassets/credential_vault.py:113,142,1128,1356,2069`. Preset JSON containing provider names is configuration, not itself a Direction violation; Python dispatch on those names is. Pi also contains provider adapters, so “copy pi” does not literally remove vendor code: the application needs a stable protocol boundary with vendor integration below it, preferably maintained dependency/package code.

Other differences are necessary, not duplicates to delete: authentication versus authorization; ownership admission versus stale-handle/revocation checks; owner-selected policy versus accounting; control-plane timers versus sleeping compute; browser takeover versus ordinary UI. OS file isolation cannot prove current consent, spend limits, model identity or cancellation.

## 5. Target core and the review built on it

Recommendation: one owner execution context; one file/package resolver; one session/job lifecycle; one normalized model invocation; one tool/effect capability dispatcher; one event stream. Keep identities, admission, credential custody, budget/usage and protected approval outside user code. Keep user behavior and rendering inside owner files/packages.

```text
App / MCP / schedule / webhook / custom UI
                    |
      authenticated owner + execution context
                    |
       installed agent/package revision
       instructions + settings + tools + hooks
                    |
       session / durable job / child session <--- user workflow code
                    |
       model.invoke(request, parent_execution)   [ONE callable path]
         | resolve exact model; authorize; reserve; journal
         | protocol transport; normalized events; settle
         v
       broker ---> owner's connected model source
                    |
       read / write / edit / bash (ta inside bash)
                    |
       owner execution boundary + capability dispatcher
          files/code       connections       child sessions/jobs
                    |
       committed event/receipt stream ---> any authorized UI
```

The model invocation contract carries selected connection/model, request/session/parent IDs, messages, tools, reasoning/options, cancellation and execution budget. The response carries **requested, resolved and provider-reported model separately**, normalized text/tool events, usage provenance, outcome/uncertainty and receipt ID. Never infer the model from an agent/workflow title or its answer. Explicit required-model selection fails visibly if unavailable; only a declared fallback list permits a substitute. Automatic strongest-source choice remains a separate policy mode.

Admission reserves each attempt before transport, links retries/children to the existing parent allocation, and settles completion/refusal/unknown outcomes exactly once. Stopping a wait does not mint a new job; stopping/revoking execution reaches every child. Discovery and auth refresh are infrastructure operations with their own declared semantics, not model prompts. UI, raw connection effects, tool hooks, compaction, action review, graph prompts and subagents cannot create a second inference ledger. General HTTP remains available for non-model work; declared inference goes through `model.invoke`, including a normalized low-level request mode if needed.

**Isolation attaches once at execution admission, credentials and external effects at the broker boundary.** Untrusted hooks/code run under the owner's cell/box, never in a privileged Pi-style extension process. All file access goes through the selected execution backend; no daemon writes owner content directly. Keep fresh revocation/consent and stale-generation checks that the OS cannot enforce. Delete duplicate cross-owner path defenses only after their entire reachable operation is confined by construction. Preserve ADR-012's box seam and outside-box state, but do not reopen the already completed UID migration or add a legacy-host fallback while completing it.

For the founder's review, the agent writes `agents/reviewer/AGENTS.md` and settings selecting an exact connected GPT model with `fallbacks: []`; a skill passes the diff/files to a child session through `ta`. A workflow script starts it, waits/subscribes, then compares the receipt's resolved model/family with the requested reviewer. If unavailable, it reports that fact and preserves the task. Its custom UI renders the same child-session events and receipts. No `codex_review` node, OpenRouter-specific HTTP grant workaround, platform review prompt or copied credential is needed. These are **proposed semantics**, not commands available today.

Native CLIs are the hard constraint: an entire Claude/Codex harness cannot truthfully be advertised as a single model response. Preferred end state is single-response protocol transports (supported by connection configuration or audited transport packages). A CLI that cannot provide that contract remains an explicitly named external-agent package over the generic job API, with its own opaque/native session evidence—not a hidden alternative implementation of the common agent. Do not remove an owner's working subscription source until its replacement passes model/tools/session/usage parity; subscription transport feasibility must be established first. Merely moving the current classes into an `adapters/` directory would change nothing.
