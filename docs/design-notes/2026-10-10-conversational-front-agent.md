# Conversational front agent and observational context

Research only; initial_provider: **Codex**; researched **2026-10-10**. Founder idea dated 2026-10-10.
Base inspected: `main` at `6bd296c1be2f61393874447ff07120b14012861a`; no implementation or deployment claim.
Source convention: **OLD** means published before **2026-04-10** (over six months); **ND** means an undated, changing page, accessed 2026-10-10, whose age cannot be established. All links were researched on that date. Publication dates, API version dates and access dates are distinguished below. Vendor descriptions establish documented behavior, not independently measured reliability or undisclosed internals. No external code copied; linked articles retain their publishers' rights; an implementation must separately check dependency licenses.

## Judgment

The idea is sound: separate **conversation latency** from **execution latency**, and maintain a small, current working context for the conversational agent. DeepMind's Talker–Reasoner is a direct conceptual precedent; current GPT-Live documents a concrete voice/backend split. Muse and dots demonstrate much of the desired experience, but neither product's public documentation establishes the exact proposed tool-free talker / hidden watcher / hidden orchestrator topology.
Recommend a tool-free conversational role, an owner-authorized background supervisor, and a versioned context projection over durable events. Keep the strongest connected model as the default: a smaller talker is an optional optimization, not evidence of “just as smart.” A fast acknowledgment cannot make unfinished reasoning immediately available.
The most important distinction: **“I received that” requires a saved message; “I've started” requires an execution receipt; “done” requires verified outcome evidence.** The talker must remain useful when the supervisor is slow, unavailable, or waiting for approval.

## Research patterns and what to take from them

- **Direct predecessor:** [DeepMind Talker–Reasoner](https://arxiv.org/abs/2410.08328), 2024-10-10 **OLD**, separates fast conversation from slower reasoning/actions updating agent state. It motivates the split, not a universal guarantee of equal intelligence, production reliability or lower cost.
- **Thinker/talker and filler:** speaking an acknowledgment while reasoning lowers perceived latency, not time to correct answer. Google's September Live announcement above is current product evidence. Use factual acknowledgment or a useful question; no invented tool narration, speculative conclusions, fake percentages or repeated “still working” filler.
- **Speculation:** [Speculative Interaction Agents](https://arxiv.org/abs/2605.13360), 2026-05-13, revised 05-14, decouples interaction from reasoning/tool delays and reports 1.3–1.7x speedups with some accuracy loss. Research result, not TinyAssets measurement. Speculate on cancellable reads or private drafts; never speculate an external commitment or assume missing approval.
- **Supervisor vs hierarchy vs swarm:** supervisor owns task decisions; hierarchy recursively decomposes; handoff changes the active speaker; swarm distributes decisions. Prefer one supervisor per task with bounded children and shared decision records. Keep the talker outside that hierarchy's execution path. [Microsoft patterns](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/) and [OpenAI orchestration](https://developers.openai.com/api/docs/guides/agents/orchestration), ND, are implementation examples, not runtime dependencies to import.
- **Shared blackboard:** [Terrarium](https://arxiv.org/abs/2510.14312), 2025-10-16 **OLD**, revisits shared state for multi-agent safety studies. Adapt a typed, scoped board with immutable events and derived views; avoid an ever-growing shared transcript that every model rereads. The event log records what happened; the board records the latest projection; neither should contain hidden chain-of-thought.
- **Event-sourced progress:** ADK's [event loop](https://adk.dev/runtime/event-loop/), ND, distinguishes yielding a state delta from its persistence. Adopt the lesson: commit task transitions before publishing their digest, use sequence numbers and replay after reconnect. This is a recommendation; ADK events alone are not an exactly-once external-effects guarantee.
- **Ambient/background:** [LangChain ambient agents](https://www.langchain.com/blog/introducing-ambient-agents), 2025-01 **OLD**, responds to environmental signals and requests human attention selectively. Wake on meaningful events, permissions and deadlines; “always reachable” should not mean an LLM continually polling or thinking.
- **Important disagreement:** Cognition's [2025 critique](https://cognition.com/blog/dont-build-multi-agents), 2025-06-12 **OLD**, warns about lost implicit decisions and proposes a separate context compressor. Anthropic's [research system](https://www.anthropic.com/engineering/multi-agent-research-system), 2025-06-13 **OLD**, finds parallel research useful but reports roughly 15x chat token use. Cognition's [2026 update](https://cognition.com/blog/multi-agents-working), 04-22, narrows the disagreement: intelligence may be parallel; conflicting writes still require coordination. Different workloads explain much of the apparent contradiction.

## Observational context: a separate working-context editor

The founder's observer is more than storage or periodic summarization: it prepares the evidence another agent needs **for its next response**, while that agent remains available. Public systems supply complementary parts:

### Recommended observer contract (proposed, not implemented)

- **Add:** exact latest user messages; changed task facts; unresolved questions; corrections; durable preferences relevant now; verified outcomes and source excerpts needed for the current topic. Every injected item carries source IDs/ranges, producer, observed time, validity time, task revision and fact/inference/unknown type.
- **Drop from working context:** duplicate progress, irrelevant tool output, superseded plans, closed tasks after acknowledgment. Preserve raw sources under the owner's retention policy; an omission from context is not deletion from evidence. Never silently drop unhandled intent, uncertainty, cancellation or outstanding approval.
- **Rewrite:** consolidate repetitive observations and compress completed exploration; retain negation, exact constraints, numbers, disagreements and supersession links. Do not rewrite the user transcript, execution receipts, permissions or authoritative task states. Validate IDs and exact fields mechanically; semantic faithfulness still needs evaluation and occasional raw-source comparison.
- **When:** deterministically project state transitions immediately; invoke semantic summarization after meaningful milestones, topic changes, idle periods or measured context pressure. Consume only unseen deltas plus relevant prior notes. No model wake for every token, heartbeat or unchanged status.
- **Latency:** snapshot at sequence N, build asynchronously, atomically install version V only if its base still matches, append events after N unchanged. Talker uses the last valid snapshot plus fresh raw delta; never waits for the observer. Reserve headroom and prioritize new user instructions; if overflow makes an answer unsafe, acknowledge and disclose the missing context.
- **Source access:** workers/supervisor can fetch raw evidence through existing reads. With a strictly tool-free talker, the observer retrieves sources relevant to the latest user request; the talker can say it needs a source and the watcher routes that conversational need as a read request. It must not answer as verified until the excerpt arrives. A private direct retrieval request would be an extra capability, and requires an explicit design decision rather than pretending it is “no tools.”
- **Separate roles, initially shared runtime:** watcher handles incoming intent/cursors; supervisor makes plans and owns task state; observer manages relevance/compression. Share event transport and owner scope, not a giant common prompt. Watcher and observer may use one batched inference when useful, but their outputs, write permissions and failure states remain distinct. Observer cannot authorize work or change execution status.

## Recommended architecture

```text
User <------------------------> Talker (conversation only)
  | saved messages                 ^ latest valid context + raw deltas
  v                                |
Owner conversation/event log --> Context projector + optional observer
  |                                ^ receipts, artifacts, decisions
  v                                |
Watcher --> Background supervisor --> Workers (read/write/edit/bash + ta)
  |             |                        |
  +-- cursors   +-- task state/events <---+
                +-- existing approval/effect boundary
User approval controls ------------------^
```

This is an owner-scoped package running on generic platform scheduling/storage. The platform persists and delivers events without an LLM; every model role uses the owner's connected compute. Neither user nor talker addresses the supervisor directly; it consumes saved conversation events. The watcher observes assistant questions for dialogue context but **assistant promises are not new authorization**.

1. Save user message and enqueue its event atomically. Deterministic UI immediately confirms receipt. In parallel, schedule talker and watcher; ordinary conversation need not spawn work. Semantic classification runs under owner authority and records `no_action`, `needs_clarification`, or task IDs against each message; uncertain directives cannot silently disappear.
2. Supervisor binds accepted intent to task ID/revision, scope, dependencies, budget and authority. Its runtime records admission/queue state; only an admitted worker's start receipt permits “running.” Idempotency key includes owner, message ID, task identity and intent revision; repeated delivery cannot create duplicate jobs.
3. Workers return structured milestones, failures, source references and artifact receipts. Deterministic projections refresh status without a summarizer. Observer supplies relevance and explanation; factual task fields come directly from the runtime.
4. Before each talker response, assemble stable persona/instructions + relevant memory + recent verbatim conversation + compact task digest + events newer than the digest. Starting experiment: 2–4k total input tokens, 100–200 per visible task; these are tuning budgets, not platform caps. Include counts and a pageable task index so other tasks do not vanish.
5. Digest includes `task_id`, intent revision, state, verified milestone, blocker/question, evidence reference, last event sequence/time and freshness. Pin the most recent correction and unresolved approval. Hide worker chatter and raw tool transcripts by default; make supporting sources recoverable.
6. One canonical editable identity/style bundle serves all roles. Only talker produces normal conversational replies; workers produce evidence packets, and urgent permission/error UI comes from structured records. Coherent persona means coherent commitments and preferences, not identical worker prose.

### Honesty, interruption and safety rules

- **No invented start:** before dispatch acknowledgment, “I've received your request”; queued: “It's queued”; started: “I'm working on it.” Failure to start must become visible. Never delay the first useful reply just to manufacture the impression that work already started.
- **Freshness is explicit:** stale or disconnected feed means “Last update…” or “I can't confirm current progress.” A recent heartbeat proves liveness only. Validate referenced state/version before publishing status claims; discard or qualify a response superseded during generation. Streaming cannot retract already-spoken words: promptly correct them and keep durable task status authoritative.
- **Corrections:** associate user changes with task IDs, bump intent revision, invalidate incompatible plans/results, deliver the update to affected workers. Pause ambiguous affected work and clarify through talker. New tasks and edits to old tasks must not be conflated.
- **Cancellation:** stopping speech, cancelling one run, cancelling a whole task tree and disabling a recurring schedule are distinct. Record cancellation immediately, fence future effects, propagate to descendants and await receipts. Say “cancellation requested” until confirmed; already-committed external effects remain possible and must be reported. Do not promise rollback where none exists.
- **Approvals:** present exact action, destination, payload/version and consequence through existing request controls; bind approval to that revision/owner and recheck at effect time. Summaries, historic “yes,” retrieved text, worker assertions and talker wording are not permissions. A changed payload invalidates its approval.
- **Concurrent work:** independent tasks may run in parallel; serialize writes to a shared resource or use explicit isolated versions plus reconciliation. Each event names its task/generation. Reserve foreground capacity so background work cannot monopolize provider concurrency; no guarantee of latency when the connected provider offers only one occupied slot.
- **Watcher reliability:** durable consumer cursor, retry/outbox, idempotent intake, explicit handling result per message and recovery reconciliation. Existing “message read” receipts are not “instruction handled” receipts. Quoted instructions and external content remain data; role and source provenance survive summarization.
- **Failure containment:** reject stale-generation writes; reject observer patches with missing provenance; retain last good context on summarizer failure; expose unknown state after lost worker contact. Never let a worker's untrusted output become a trusted system instruction. Per-owner isolation applies to transcripts, memories, events, credentials and model usage.

## Token, latency and cost efficiency

**Model choice:** start with the owner's strongest connected source for talker and difficult work. Short context, short answers and independent scheduling may buy speed without sacrificing model ability. A small model is suitable for routine status phrasing or optional curation only after tests of subtle intent, corrections and source faithfulness. Hard questions can receive a quick acknowledgment while a strong worker reasons; do not call that instant equal intelligence.

**Illustrative text-only arithmetic, not quoted provider prices:** strong model input/output = $3/$15 per million tokens; small = $0.30/$1.50; hypothetical cached input = 10% of uncached price. Tool, audio, storage, retry and reasoning-token charges are excluded; substitute the owner's actual rates. Same underlying worker computation is held constant at $0.60 in both designs.

| Ten user/status exchanges during one job | Extra communication/coordination cost | Total with identical $0.60 work |
|---|---:|---:|
| Single strong agent, 30k input + 200 output each, uncached | $0.930 | $1.530 |
| Same single agent, 27k cached + 3k fresh input each | $0.201 | $0.801 |
| Split: small talker, 3k input + 200 output each; four curator passes, 5k input + 500 output each; supervisor extra 5k input + 500 output | $0.0435 | $0.6435 |
| Same split, strongest-model talker rather than small | $0.1515 | $0.7515 |

The small talker component is $0.012, curator $0.009, supervisor overhead $0.0225. At these assumptions break-even is **one** uncached or **two** 90%-cached large-context status turns for the small talker; **one** uncached or **four** cached turns for the strong talker (ceiling of fixed $0.0315 overhead divided by per-turn savings). These savings depend on the large-context comparison; an already compact 3k-context single agent removes most of the benefit.
With zero follow-ups, split adds $0.0315 plus any extra acknowledgment; a single 1k-in/200-out strong answer costs $0.006 before tools. Simple conversations and tightly sequential tasks are usually cheaper without orchestration. Extra workers, duplicated planning, failed summaries or continuous idle reflection can erase all savings; token efficiency and dollar efficiency are different.

- [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching), ND, rewards matching rendered prefixes; rewriting earlier context can lose cache reuse. Put stable identity/tools first and volatile digest last. Measure cached/uncached usage rather than assume a hit. Different models do not share useful model KV state.
- [Manus context engineering](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus), 2025-07-18 **OLD**, emphasizes cache stability and external memory. Google's [caching guide](https://ai.google.dev/gemini-api/docs/caching), ND, adds TTL/storage considerations. Compact less often when discounted history is already cheap; compact sooner when quality deteriorates.
- Event-driven wakes eliminate idle **model** polling. Example assumption: every five seconds for ten minutes = 120 calls; at 1k small-model input each, $0.036 input alone, versus zero idle model calls. UI polling or a deterministic scheduler tick is not an LLM call and should not be conflated with that expense.
- Batch observer work by meaningful changes; do not send every worker transcript to both supervisor and talker. Charge all roles, retries and cache misses to the same owner-visible task budget. An owner-provided subscription still has throughput/opportunity cost even if its marginal API bill is zero.
- Proposed measurements: p50/p95 first useful reply under worker load, semantic answer quality against one strong agent, progress age, missed/duplicate intent, cancellation-to-last-effect latency, unsupported progress claims, raw-source fidelity and total cost per completed task. No latency or savings numbers above are TinyAssets benchmarks.

## Open questions and “if we build it” order

1. **Contract first:** agree whether “no tools” is absolute, including private source retrieval; define received/accepted/running/verified and correction/cancel semantics. New storage/authority/public contracts require OpenSpec before implementation. This note is a recommendation, not accepted design truth.
2. **Truth before fluency:** project existing activity receipts into the bubble and next-turn context; prove crash/reconnect recovery, stale-state wording and exact action approval. Cross-consider #4588/#4590 and the per-owner isolation cutover before choosing files.
3. **One talker + one supervisor + one worker:** separate scheduling and intake; use the same strongest model initially. Prove a naive user can ask an unrelated hard question while work runs, correct a task, cancel it and get an honest outcome with no host online.
4. **Observer after baseline:** add deterministic digest first, then asynchronous semantic curation with source IDs and raw fallback. Replay real conversations containing corrections, conflicting facts and long gaps; compare against raw-context answers and cache costs.
5. **Then optimize:** independent concurrent tasks, measured optional tiering, idle/sleep-time memory and voice interruption. Proceed only if matched-quality cost/latency improves; no requirement to install the researched frameworks.
