# R5 P-hooks as built (2026-11-21)

R5's fourth slice (d3 §N2, §N3; `r5_research.md` §2.1, §5.3, §6 slice 4), on P-decide (#5672, `r5-decide.md`) and P-resume (`r5-resume-hooks.md`). The research is the design; what it left open was researched first (Fact 14), from the vendors' own pages and code, read 2026-11-21: Claude Code's hooks and headless pages (code.claude.com/docs/en/hooks, /headless), Codex `rust-v0.166.0` (`codex-rs/hooks/src/engine/discovery.rs`, `events/pre_tool_use.rs`, `codex-rs/config/src/hook_config.rs`, `config_requirements.rs`, `codex-rs/core/src/tools/hook_names.rs`, `tools/handlers/mcp.rs`), Gemini CLI `v0.66.0` (`docs/hooks/reference.md`, `docs/hooks/index.md`), pi `1.4.0` (`docs/extensions.md`, `docs/mcp.md`, `docs/cli.md`) and Kimi Code `2.4.1`'s package. What follows is how it landed and where it departs.

1. **Departure: no engine defers; a held call is refused with its card on every CLI, Claude Code's too.** The research chose Claude's `defer` and, until §8.1's live check, a managed `permissions.ask` rule beside each `ask` act. The hooks page rules both out as the run is set up:
   - "Deny and ask rules are still evaluated regardless of what the hook returns." So with the paired `ask` rule, a `-p` run with `--permission-prompts none` denies the approved call too, on every resume: a yes could never admit it.
   - Without the pair, a turn of several tool calls ignores `defer` "and the tool proceeds through the normal permission flow", which in `--permission-mode auto` is the classifier: the held call can run.
   - So the fail-closed shape (Fact 8) is the one every CLI already has: the hook refuses the call with the card's reason, the run goes on or ends, and the owner's yes resumes the conversation on P-resume's message (`r5-resume-hooks.md` item 3), which the approval admits.
   - **Owed:** `r5-resume-hooks.md` items 6 and 7 (a deferred call resumes on no input; its conversation waits on its card) have no deferred call to act on. They come with `defer`, in `untangle/r5-defer`, only if d3 §N9's first live check (`live:` Claude `defer` with several tool calls in one turn) shows that turn denies. The `tool_deferred` matcher (P-resume) stays, and matches nothing until then.
2. **One answer shape for the helper, so a record carries no input paths.** Every CLI here hands its hook `tool_name` and `tool_input`, and each command hook blocks on exit 2 with the reason on stderr (Claude's page, Codex's `pre_tool_use.rs`, Gemini's reference); pi's extension is the record's own template, which runs the same helper and blocks on any other exit. So the helper answers exit 0 and `{}` (no decision: the CLI's own flow goes on) or exit 2 and the door's reason, and a failure of its own is exit 2 too. Claude Code's hook is an `http` hook (item 13), whose refusal is the record's one output template (`runs.http.deny`). The record's `decide` block (`sources/src/schema.ts` `Decide`) is where the config goes, its template, how the CLI runs it (`runs`), the CLI's names for each tool kind and for an MCP tool, `fails`, and `alterable`.
3. **A managed file is the sandbox's, not the run's.** Claude's `/etc/claude-code/managed-settings.json` and Codex's `/etc/codex/requirements.toml` are one path for every run, which the research did not weigh.
   - So the hook's matcher is the owner's rules' for every agent (`Actions.hookTools`), never the run's agent's alone. A sandbox is one authority's, so every run in it needs the same file at one policy generation, and the latest run's start writes it, or removes it when no rule names a tool. There is no per-run share.
   - **Two starts at once around a policy write (review).** The door's check names its policy generation, and the runner writes a shared file under one lock, only when its generation is at least the last writer's (`/var/lib/ta/hooks/<engine>`). So the older rules never land last.
   - The cost: a rule naming one agent makes another agent's matching call ask the door once, which lets it be (the decision holds each rule to its agent).
   - Every run of an engine with a hook carries its decide credential (`TA_DECIDE`), so a hook a later start wrote decides a live run's calls under the live rules. Claude re-reads a settings file it watches; Codex reads its requirements at its start.
   - A run's own file (Gemini's system settings, merged into the record's file of that path; pi's extension, loaded by `-e`) is its start's: a rule added mid-run holds there from the agent's next run, and at the doors at once.
4. **Codex's requirements also pin `features.hooks = true`**, so no config the agent writes turns its hooks off. Managed hooks need no trust and can't be disabled from a user layer (`discovery.rs`).
5. **The helper is a command of the runner bundle (`decide`), so the pair check pins it.** A command hook runs it as the run's user: `/usr/bin/env -i NODE_EXTRA_CA_CERTS="$NODE_EXTRA_CA_CERTS" TA_DECIDE="$TA_DECIDE" <the loader's node> --no-warnings /opt/ta/runner/<digest>/runner.mjs decide <door>`, the runner's own bytes (0644), the door its argument (item 13). It is runner protocol 2: protocol 1's commands but its retired ones, and `decide`; its documents and answers unchanged, so the Worker writes and reads the same.
   - **Two deploys** (`protocol.ts`): the expand, a Worker that speaks 1 and 2 with protocol 1's runner, is `untangle/r5-hooks-speaks` (#5706), merged first. Its deploying first matters only to a rollback past this branch's deploy, which the dark platform has none to make (review).
6. **The start asks first, then checks the hook as its CLI runs it.** The root runner asks the decide door which tools the hook matches (`check`) before it makes the run's files, and writes the hook only for those. Where it wrote one, the hook is run once before the CLI starts, the way the CLI runs it (`runs`): an `http` hook's post, by the credential its header takes from the CLI's environment; the helper's command line through the CLI's own shell (`bash -c` for Gemini) as the run's user, in the CLI's environment; or pi's argv with only what its extension hands it. A failure fails the run loudly (`ta.runner_error`), which closes Codex's and Gemini's fail-open at the start; mid-run it stays open there (`fails: open`). The env files the CLI would load are refused before it (item 13), so the check's environment is the hook's.
   - A run of an engine with a hook asks once even when no rule names a tool: one Worker and one object request a run, none a tool call.
   - The decide door is one path on the egress host (`/decide`), its run named by a credential header (`x-ta-decide: <run>:<secret>`), both from the run's MCP URL (`contract/src/egress.ts` `decideDoor`). So the start document names no new URL and nothing new enters the VM (research §8.8): the run's secret is already its CLI's.
7. **What a call is.** Each act whose hook kinds name the tool (`acts.json`, the record's `kinds`), or one of whose rules names it (`tools`), decided as that act's door call is (`Actions.decide`): every act a rule never lets be first, then the first act asked alone. The card's door is the tool's name and its request the tool's input.
   - **One card for two asked acts (review).** A held call is keyed by its call's digest, which names no act, and a yes is used once. Deciding every asked act in turn, the first used the yes and the next filed a new card, on every attempt: the call could never run. One asked act decides it, so its one card and its one yes admit the call.
   - A `tools` matcher's characters other than a letter, a digit or `_` match any one character, because each CLI rewrites them in its MCP tool names its own way (pi: every one to `_`). The pattern holds every name a CLI may give the tool, never fewer.
8. **Kimi holds no hook (`unsupported`).** Kimi Code 2.4.1 runs `PreToolUse` hooks, but its bundle names no root-owned path they load from, so a hook there is the agent's to edit. A rule holds on Kimi at the platform's doors alone.
9. **Not built: the research's second line of static denies** (`permissions.deny`, `prefix_rule`, an admin policy) from the same data. The hook refuses a `never` already, and a static rule's vocabulary (`Bash(curl *)`) is one no rule here writes.
10. **The honest note (d3 §N5): the policy's projection answers, beside each rule, where it holds and where it can't (`Actions.ruleNotes`),** so `policyRead` and the write's own answer carry it alike. It holds at `doors` (the platform's tools and doors that do its act) and at each engine whose hook sees it, by its kinds or the rule's tools. It can't where `acts.json` says nothing of ours sees the act (`unseen`), at an engine whose CLI holds no hook for it or one the agent can alter (`alterable`, Codex's: item 13), nor, mid-run, at a hook that fails open (`<engine>.fails_open`).
    - **Departure: every engine is named, not the agent's alone.** An agent's engine is `auto` (the strongest connected source, Direction 4) or its own `agent.json` to change, so a note held to one engine would go stale with no rule changed. The owner reads where each engine holds it.
11. **The decide door is outside-callable by its caller (`account`), so the owner's door guard lists it among the doors the doors call themselves** (`owner/guards/doors.test.ts` `DOORS_ONLY`): only the egress host's decide path calls it, by the run's own credential, and its handler refuses every account but a run's.
12. **Owed live checks** (d3 §N9, at the dark redeploy; `live:`):
    - Claude's managed file against an org's server-managed settings;
    - whether a user or project `allowedHttpHookUrls` or `httpHookAllowedEnvVars` can narrow a managed hook's (item 13: the managed file lists its own, so a narrowing should only make it fail, which blocks);
    - Codex loading `/etc/codex/requirements.toml` under a run-local `CODEX_HOME`;
    - Gemini's system-settings hooks under `--approval-mode yolo`, whether a project layer can drop them, and whether its system `advanced.ignoreLocalEnv` holds over a project's;
    - pi's `-e` beside `--no-extensions` in `--mode json`, and that `builtin:mcp` still connects the run's door;
    - the delay one decision adds;
    - **an approval admits only a byte-identical repeat call (review).** A CLI's tool input carries free text, such as the `description` of Claude's `Bash`, which the model may not repeat when it makes the call again: the resumed call may file a new card each time. Measure it on each engine; if it does, the call's digest is held to the fields that do the act.
13. **The hook never trusts what the agent can write (review, BLOCK on #5707).** The first build took the door's address from `TA_DECIDE` and ran a Node helper in the CLI's environment. Claude Code applies a user or project settings file's `env` at a `-p` start and again live, to every subprocess, hooks among them (code.claude.com/docs/en/settings-reference, `env`; /hooks: "A hook process inherits the parent environment"). The reviewer's reproduction: `TA_DECIDE='data:application/json,{"allow":true}'` made a `Bash` call under a `never` rule exit 0. `NODE_OPTIONS=--require <the agent's .js>` beats any check of the address, and so would `LD_PRELOAD` or a shell's startup file under any process started in that environment. Researched again, engine by engine, from the vendors' current pages and source (read 2026-11-21):
    - **The shape, for every engine.** The door's address is only ever the root-owned hook file's (the `http` hook's `url`, or the helper's argument, which `decide.ts` holds to the decide door's path); the agent's environment can carry only the run's credential, and a forged one names a run the door refuses (fail closed). Where a process runs, it starts with an environment nothing the agent writes can reach.
    - **Claude Code: an `http` hook, so no process starts.** The managed file's hook posts the call to the door itself (/hooks, "HTTP hook fields"): `url` the door, `headers` `x-ta-decide: $TA_DECIDE` (only `allowedEnvVars` are interpolated, and only into headers), `onFailure: "block"`, so a refused or forged credential, a non-2xx status or no connection blocks the call ("a failure counts … when an HTTP hook's connection fails, or the response status isn't 2xx"). The door answers in Claude's words: `{}` lets the call be, `runs.http.deny` (its `{reason}` the refusal's) refuses it. A proxy the agent's `env` names can only tunnel the TLS the sandbox's CA verifies, and a CA it names reaches no Node already started. The managed file also lists its own URL and variable in `allowedHttpHookUrls` and `httpHookAllowedEnvVars`, so a user list narrows nothing of it (the page: "Set these … in managed settings to cover hooks your organization deploys"; owed live, item 12). Holds.
    - **Gemini CLI: its system settings turn local env files off.** Gemini runs a hook through `bash -c` with its own environment, sanitized, and the hook's `env` (`packages/core/src/hooks/hookRunner.ts`, `utils/shell-utils.ts`). Its process takes variables from the first `.env` it finds from its cwd up, then the home's, unless `advanced.ignoreLocalEnv` (`packages/cli/src/config/settings.ts` `loadEnvironment`), and system settings override every other layer. So the hook's template sets `ignoreLocalEnv`, and its environment is the runner's. The helper's line also goes through `env -i`. Holds.
    - **pi: only its own extension and the built-in MCP load.** pi's hook is an extension in pi's own process (docs/extensions.md), beside any the agent writes into its home's or project's extension folders, which would share that process. A hooked run adds `--no-extensions -e builtin:mcp -e <the hook>` (docs/cli.md: "`pi -ne -e builtin:mcp` keeps only the built-in MCP support"), and the extension starts the helper by its argv, no shell, with only the credential and the CA. The cost: an owner's own pi extensions don't load while a rule needs the hook, a cost paid only then. Holds.
    - **Codex CLI: alterable, so the note says it holds nowhere there.** Codex runs a hook command as `$SHELL -lc <command>` (`codex-rs/hooks/src/engine/command_runner.rs` `build_command`), a login shell, which reads `~/.profile` in the run's home, a file the agent writes mid-run. It also loads `$CODEX_HOME/.env`, all but `CODEX_*` names (`codex-rs/arg0/src/lib.rs` `load_dotenv`). The hook is written all the same (good faith, and the start's `.env` refusal), but the record's `alterable` says why, and the note lists `codex` under `not_enforced`. **Owed:** a Codex hook that starts no shell, its `mcp_tool` type (`codex-rs/config/src/hook_config.rs`) researched first (`untangle/r5-hooks-codex`).
    - **And before every hooked run, the files the CLI loads are refused if they set the credential or a code-loading variable** (`CODE_LOADING_ENV`, `sources/src/run-env.ts`, the list the record checker refuses in a record already): the agent's `.env`, its home's, its settings' `env`. That covers what each CLI reads at its start; Claude's live reload needs no process to reach.
    - **Claude's `PowerShell` tool is a shell kind too** (review): the tools reference says to match `Bash|PowerShell`, and the same settings `env` can switch it on.
