# oracle-pull-retry as built (2026-11-21)

Merge group run 44079286405's `required-tests shard 5/6` (job 134025918203) failed before any test ran: building the oracle image, `mirror.gcr.io` answered the base's manifest `HEAD` with `429 Too Many Requests`. #5678 left the queue, and `queue_attempts.py` counted the removal against its head.

## Research

1. **How often.** Every failed job in `tests.yml`'s last 1000 runs (2026-11-03 to 11-17, the API's cap), 124 jobs, plus the 48 failed jobs of earlier attempts of re-run runs: one `429` or `toomanyrequests`, this one. In the same window the oracle venue failed before any test five more times, all in the gVisor runtime fetch (`prepare_oracle_runsc.py`, a read timeout and a 504): merge group runs 42477687270 (shards 1, 2, 4 and 5) and 42478295754 (shard 3) on 11-08, both #5471's, and push run 42568633980 on 11-09 (shards 2 and 6). #5472 added that fetch's retry the same day.
2. **The registry's limits.** Google's page for `mirror.gcr.io` ("Pull cached Docker Hub images") gives no quota or rate limit, and Artifact Registry's quotas page lists only per-project quotas. So the limit is undocumented. GitHub-hosted runners share egress addresses, and each shard's build sends an unauthenticated manifest request and pulls the layers from a fresh runner. A queue entry runs six shards at once, and the affected and proof legs add more.
3. **The legs that build the image.** `scripts/linux_oracle.py` builds it for `tests.yml`'s six `required-tests` shards and four `affected-tests` shards, `linux-jail-proof.yml` (two jobs), `real-browser-proof.yml` and `test-shape-prune.yml`, each time on a fresh runner. A green shard spends about 2.5 minutes on it (run 44075582046, 11:37:54 to 11:40:09).
4. **The base.** `docker/linux-oracle.Dockerfile` named `python:3.11-slim` unpinned. On 11-17 that tag resolved to `07d4824036af` (Python 3.11.18, built 11-05). The root `Dockerfile` pins `a3ab0b966bc4` (Python 3.11.15, built 05-19) in both its stages, and `linux-jail-proof.yml`'s header already calls the oracle "the same base as production".

## As built

1. **One pin.** The oracle takes the production image's base: `linux_oracle._base` reads the root `Dockerfile`'s `FROM`s and refuses unless they name a single digest-pinned base. `_build` passes it as `BASE`, and the oracle Dockerfile is `ARG BASE` / `FROM ${BASE}`, so it names no base of its own (a test holds that). `_image_tag` hashes the base too, so a new pin rebuilds the image, and `real-browser-proof.yml` now lists the root `Dockerfile` among its venue paths, as `linux-jail-proof.yml` already did (review). This puts the suite on Python 3.11.15, the version production runs, where it had been running whatever the tag named that day. The supply-chain gap closes with it. There is no second copy to keep equal with a guard: a copy and its guard would be two edits for one change.
2. **A bounded retry, only for a busy registry.** `_build` streams `docker build`'s output and keeps the lines that name the base's registry host together with a 429, a 5xx status, `toomanyrequests`, an i/o or TLS-handshake timeout, or a connection reset. With such a line it waits 15, 30 and 60 s across four attempts. Without one it fails at once, so an apt error, a pip 503 or a missing digest is never retried. After the fourth attempt it fails, naming the last refusal. The worst case adds 105 s to a shard at most. The slowest shard takes about 15 of its 30 minutes (`shard-2-time.md`), so this stays well clear of the ceiling.
3. **No cache.** GHA's BuildKit cache (`cache-from: type=gha`) still resolves the base's metadata at the registry, so it would not remove the request that failed. It would also need `buildx` set up in five workflows. Caching a saved image with `actions/cache` avoids the registry. But the workflows would need the image tag, which is a copy of `_image_tag`, and the multi-gigabyte image (Chromium, build-essential, every dependency; size not measured) would share the repository's cache budget with the npm caches. Restoring it would take about as long as the 2.5-minute build. These legs go at the cutover, so neither cache is cheap enough.
4. **A failure before any test does not count.** `queue_attempts.py` counted every failed job that names no test, and run 44079286405's shard was one. A job now shows it stopped before any test ran in one of two ways. Its first failed step is GitHub's own (`Set up job`, or an unnamed `actions/*` step such as checkout). Or its log holds `linux_oracle.NO_TEST_RAN`, which the venue prints on each of its pre-runner stops: the image build (`_build`), the runtime fetch (`prepare_oracle_runsc.py`'s CLI) and the jail probe. Such a job is no longer "a failed job that names no test". If nothing else failed, the removal does not count ("every failed job stopped before any test ran"). Retro-check: #5471 was handed off on 11-08 by two counted removals, from those two runs' runtime fetch, and merged about an hour later. No open PR carries `queue-handoff`.
5. **Surplus removed:** `attempt_counts`'s `jobs is None` branch. No caller passed `None` (an unreadable run raises, and `classify_removal` counts it), so only its test row reached the branch.

## Found and left

- **Left counting, fail closed.** A failed install step the workflow names (`Install`, `npm ci`) reaches the API only by that name, which is `tests.yml`'s choice: telling it from a test step would copy the workflow's step names into `queue_attempts.py` with nothing tying the two. In the window above these failed only on scheduled runs, never in the queue. A lost runner's job carries no failed step and often no log, the same shape as a job that timed out on a hung test.
- The registry's and the runtime fetch's retries are two loops of a few lines, one over `docker build`'s output and one over `urllib`'s exceptions. They have different transports and different reasons to change, and both go at the cutover, so no shared helper.
