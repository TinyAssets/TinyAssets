# r8-lost-object as built (2026-11-17)

Lane R's PR on #5671's owed list (`r8-erased-orphans.md` item 8): a lost owner object with the account intact, restored from the namespaces R2 holds; a live owner restored from a namespace it holds; every other located namespace naming the owner held; and a located namespace whose owner is erased erased. Researched first, as its own step (Fact 14), on `origin/main` at `5ec1105a7` (#5671 merged).

1. **What main holds.**
   - **A lost object.** Its storage gone, it starts pending, empty, naming no namespace; the directory still records the owner, so sign-in and `owner.admit` refuse it (#5671). `restore.source` answers `namespace: null`, `begins: true`. Mode `restore --generation` begins it from any generation whose header names the owner, but nothing tells the operator which namespace: only R2 does, and only by opening each namespace's newest part 0 (`locate`). `copyback` refuses it (no namespace named).
   - **Who lists the bucket.** `locate` lists one namespace's roots; nothing lists the namespaces. `recover` lists the copy and R2 with rclone, with B2 and R2 keys a restore mints. Mode `restore` holds no R2 key: it reaches R2 only through the operator channel.
   - **A live owner and its old namespace.** `restore.hold` (#5671) has the live owner's own namespace `P` hold the old one `R`. Restoring from `R` was impossible: `restorePin {gen}` takes only the object's own finished generations (`restorable`), the record's `ns` was always the object's own, and `wipedFor` held a begin to it.
   - **The record after a wipe.** A wipe drops `file_space`, so the object names no namespace until its begin; only the record's `ns` names it. The erasure's mark and delete read `storedNamespace()` alone (`owner-do.ts`), so an owner erased while wiped for a restore kept its whole namespace in R2, unmarked, for good. The platform's `erasureBegin` is an admission door, so it runs while a restore holds the owner.
   - **Cycles.** `markNamespace` and `deleteNamespace` walk holds with a seen set; `recovered` stopped the run on any namespace held only within a cycle.
   - **The import.** `restoreHold` refused only an object that takes a restore (empty) and its own namespace. An importing object is pending and not empty, so a hold during an import passed, and the import's discard (`deleteNamespace` of its namespace) would then delete the held one too. No path asks it today: recover's holds are of live owners, and nothing else asks.

2. **A lost object's find: `restore.namespaces` and `restore.locate`, through the operator channel (`deploy.ts` `namespacesOf`).**
   - `FilesLocate.namespaces(cursor)`: one page of the prefixes directly under `o/` (`namespacesPrefix`, R2's list with `delimiter`), each held to a namespace's prefix (`listedNamespace`), and the next cursor. Marks are under `e/`, so none is listed. The op `restore.namespaces {cursor}` (empty for the first page) is the platform's (`PLATFORM_OPS`), as `restore.locate` is: its answer is random names alone.
   - The kit pages it, then locates every namespace `LOCATE_PAGE` a message, `BATCH` messages at a time, bounded by `RUN_MS`, through recover's own `recovering`. It keeps those naming the owner.
   - **With no `--generation`,** for an object naming no namespace with no restore, it names each, with its newest generation and when that was written (`LocatedOwner.at`, the root's sealed time), newest first. The operator chooses.
   - **Rejected:** the kit listing R2 with rclone (mode `restore` would need an R2 key, and the nightly's settings, for an act that needs neither); a filtered op answering only the owner's namespaces (a second op doing `restore.locate`'s work; the operator log already keeps a namespace's owner for every `restore.source` and `recover`); an index of namespaces by owner in the directory (a person's id tied to their bucket names outside the object, and lost with the account anyway).

3. **Every other namespace naming the owner held by the one restored (item 2).**
   - A restore no pin held (`restore.source`'s `restore` null, or its `fresh` null: a lost object's, begun, failed, or done) finds the owner's namespaces before its begin, and after the begin holds each other one by the restored one (`restore.hold {namespace, gen}`, its newest generation), before any step and before the admit. A done one found again holds them again before the admit, so a run cut short anywhere goes on whole.
   - A restore a pin held needs no find: the pin and the wipe hold the owner's namespaces in the bucket (item 4).
   - A namespace the find answers `erased` is never restored from: the run stops before the begin.

4. **A live owner restored from a namespace it holds (item 1): `restore.pin {namespace, gen}`.**
   - The pin names the generation's namespace, as `restore.begin` and `restore.hold` do. Of the object's own namespace, it is held to `restorable` as before. Of another, it is held to this owner by its header and to a schema this code brings forward (`ownGeneration`, `unforwardable`), then held by the object's own (`Files.holdNamespace`), before the pin's unit. The record's `ns` is the pinned generation's namespace, as `RestoreHold.namespace` already said.
   - **The wipe** first has the pinned namespace hold the object's own (`Files.holdUnder`, a plain hold), so from the wipe on the record's namespace reaches the one the object leaves. Its checks are one function, `wipeDue`, asked before that hold and again in the wiping unit, so wrong words or an unloadable undo refuse before anything is written. The undo's restorability is held as before; the pinned one, of another namespace, was held at the pin and is held again at the begin.
   - **The begin** into a wiped object whose record names another namespace has the adopted one hold it first (the undo from the pin's fresh generation, or a lost object's failed restore begun from another of its namespaces). `wipedFor` takes, after a pin, the pinned generation in the record's namespace or the pin's own in any namespace of this owner (its header holds it to the generation and the owner); with no pin, any generation of this owner's. The begin writes the record's `ns` too, which it left as the wipe's when the two were always one.
   - **The restore's last step** (`clear`, before `done`) deletes every hold of the adopted namespace by one it holds (`rootNamespace`), so once done no cycle is left.
   - **So at each step** the namespace the object names, or once wiped the one its record names, reaches every namespace of the owner, and the erasure takes them all: the erasure now marks and deletes the record's namespace when the object names none (`restoreNamespace`), which also closes the wiped-owner gap of item 1.

5. **No cycle of holds (#5671's review): `rootNamespace`.**
   - `FilesService.rootNamespace(ns)`: every hold of `ns` by a namespace it reaches through holds is deleted. Reachability from `ns` is unchanged (each deleted hold points back at `ns`), so its erasure takes all it did, and no cycle runs through it.
   - `Files.holdNamespace` (the object's `restoreHold` and the pin) holds, then roots its own namespace: holding a namespace that held this one (a lost object restored from a namespace another of its namespaces held) leaves one hold, the right way round.
   - The wipe's and the begin's holds are plain: the object still names, or its record names, the namespace they point from, which must keep its holds until the adopted one is rooted at `clear`.
   - **A cycle still stands from a live restore's wipe to its `clear`,** and a failed one keeps it until a begin again. Any order of two R2 writes and a unit leaves either a cycle or a namespace no root reaches for a moment; a cycle loses nothing, so it is the one taken. `recovered` now locates, of each cycle nothing outside it holds, its least namespace, which holds the rest, instead of stopping: a copy taken during such a restore would otherwise stop every recover after the account's loss, for good. Every namespace of such a cycle names one owner, and the restore begun roots the one it adopts.

6. **A located namespace whose owner is erased, erased by the platform (item 3, and the tasks line).**
   - **The shape: the doors erase it as they locate it.** `restore.locate` reads each namespace's owner (`FilesLocate.locate`) and, when the directory records that owner erased, deletes the namespace whole, its mark first (`FilesLocate.erase`, `deleteNamespace`, every namespace it holds with it), and answers `erased`. No object of that owner named it, so its erasure could not reach it; the directory's record is the erasure's own, and an erased name is never admitted again, so the namespace is that person's and nothing else's.
   - `FilesLocate.locate` answers `erased` for a marked namespace before it opens anything, so nothing of an erased owner is read, and a lost object's find never meets an erasure under way as an owner.
   - **The residual case.** An owner erased between a `recover` cut short and its run again: the run again writes nothing new, locates the namespace, and the doors erase it on the spot; the run says how many and begins the rest. No gate record, no second run and no check of its own: the run that would have stopped erases it. An owner still erasing when a run asks (its directory not yet erased) stops that run as before, refused both a begin and a hold, and the run again after it erases it; the stop now says so.
   - **Rejected:** a gate record `recover` clears (#5671's review: a recover that includes any early sign-up always stops, so it never clears); a separate platform op `restore.erase` the kit asks after a locate answers an erased owner (two asks where one does, and a run cut short between them leaves it unmarked); the kit deleting through its R2 write pair (the files Worker is the one writer of marks, and the delete is the mark's).
   - It is an irreversible act only on an erased person's data, which their erasure already decided; it is the agreed work (Fact 4).

7. **A hold made during an import (#5671's review).** `restoreHold` now refuses a pending owner no restore holds that is not empty: the import's, whose discard deletes its namespace and every one it holds. Every other hold is made by a restore's own steps (the pin, the wipe, the begin, a hold after a begin), and while a restore holds the owner the import's door refuses it (`refuseRestoring`), the discard with it; the pin takes only a live owner, which no import touches. So no import's discard ever meets a hold.

8. **Left, each with what fixes it.**

One R2 holds none of is erased at once. Rejected: erasing them once the directory records the erasure (a wait on the erasure queue, and a run cut short after the erase, refused every op from then, leaves them unmarked); a refusal in the doors' `owner.erase` (no find there, so an owner with no namespace left would never be erased, its identity kept).
