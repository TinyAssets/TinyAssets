# r8-account-loss as built (2026-11-16)

Lane R's PR owed by #5653 (R8): an erasure record that survives the account, option A (`r8-copy-restore.md` item 5, the coordinator's engineering choice), so that no restore from the off-account copy ever brings an erased owner back; and the design of what builds on it, `locate` and the restores of a lost object and of an account's loss. Researched first, as its own step (Fact 14), on `origin/main` at `bf241ddbf`.

1. **What main holds.**
   - **The copy (`deploy/offsite.ts` `copy`).** Each night `rclone sync`s the whole files bucket into B2 at the same keys, then checks it. A version is locked `KEEP_DAYS` (22) from its upload; the lifecycle deletes a version 22 days after it is hidden or replaced. Neither B2 key can delete. A night that hides more than a tenth fails, after the hides.
   - **R8's copy back (`copyBack`).** One owner's namespace, as its own object names it (`restore.source`), so the doors' erasure records refuse first. Only what R2 lacks and a row of the object names (`restore.names`). The restore record before the first byte. It is the one write from the copy into R2.
   - **How an erasure deletes a namespace.** The owner's mark (`owner/src/erasure.ts` step 1), then the outside record, then every run ended, then, `PUT_GRACE_MS` (a day) after the mark, `FILES.deleteNamespace(ns)` (`files/src/index.ts`): every object under `o/<ns>/c/` and `o/<ns>/m/`, listed a thousand at a time, repeatable. Then the wipe, then the same delete again. The cutover's discard (`Erasure.discard`) calls the same delete, with no mark and no record. Nothing else deletes a namespace's prefix; the sweeps delete keys built under it (`sweepManifests`, `deleteListed`, `deleteChunks`).
   - **What outlives the account.** Nothing that names an erasure: the object's mark and tombstone and the directory's `o:` record are all in the account. The copy shows an erasure only as hides, which look like any deletion, and a view before the hide (`--b2-version-at`) shows the namespace whole.
   - **What names a namespace's owner.** Only the owner's object (`file_space.ns`) and part 0's header line of each generation (`owner/src/export.ts`: `"owner":"<id>"`), sealed under the owner's data key, whose wrapped copy is in the root, under `FILES_KEYRING`. `restore.begin` already holds that header to the object's own owner (`r5r.md` item 12).
   - **A mark before the delete.** Yes: the delete is one files Worker call, so the mark can be its first act, in the same call, before any list or delete. The importer's proof of a discard lists `o/<ns>/` (`import/window.ts`), so a mark must not sit under it.

2. **The mark: `e/<ns>`, holding `{"kind":"tinyassets-erased-namespace"}`** (`contract/src/files.ts` `MARKS`, `MARK_BODY`, `markedNamespace`; `files/src/keys.ts` `markKey`).
   - **Outside every namespace's prefix,** so no prefix delete, sweep or listing of a namespace reaches it, and the importer's proof still finds `o/<ns>/` empty.
   - **What it holds: what it is, and nothing else.** No owner, no time. A namespace is random 128 bits, tied to a person only by the owner's object, which the erasure deletes; so the mark keeps no personal identifier off the account. It is the one object the files Worker does not seal: it holds nothing to seal.
   - **Made once** (`onlyIf: { etagDoesNotMatch: "*" }`): each delete again finds it and leaves its one version, so the copy holds one version of it, never replaced.
   - **Never deleted.** No code deletes it: every delete's key is built under a namespace's prefix (the r2-keys guard holds every key to a builder, `markKey` now one of them). A restore writes into R2 and deletes nothing. So R2 holds every mark ever made, and the copy every mark made before its last night, kept current for as long as R2 holds it. Kept for good rather than `KEEP_DAYS` past the namespace's last hide: a sweep of marks would be a delete that must never meet an erasure under way, for objects of 40 bytes, one per erasure.

3. **When it is written: in `deleteNamespace`, first, in the files Worker (`files/src/index.ts`).**
   - The mark is put before the first listing of the prefix. A failure or a crash after it leaves the mark standing, and the erasure's job (or the discard) calls the delete again, which finds the mark and deletes the rest. No delete of a namespace can happen without its mark.
   - The discard's deletes are marked too: its namespace is deleted on purpose, and a restore must never bring it back either. The rule is the bucket's: a namespace deleted on purpose never comes back.
   - **Rejected: a mark at the erasure's step 1,** a day earlier. It would put the mark in the copy one night sooner, but it is a second writer of the one record, in the owner's object, with the delete still needing its own guard against a mark lost between the two. One writer in the one call that deletes, a day of the window traded (item 6).

4. **How a copy back reads the marks (`deploy/offsite.ts` `erasures`), before anything else.**
   - From R2 and from the copy as it stands, each listed with `--include "/e/*"`, so a bucket with no mark yet lists none rather than failing, and the union taken: R2 holds the marks since the last night, the copy those that outlive R2.
   - With a time (`--at`), the copy as it stood then is listed too: every mark it held must still be in the copy as it stands. One gone means a night copied a bucket that had lost its marks (a lost account, and a new one copied), so the marks as the copy stands are not whole, and the run stops.
   - A listing that fails, a name under `e/` that is no mark, or a mark gone: a loud stop, before the restore record and before any byte. No copy back runs without the erasures.
   - `copyBack` refuses a marked namespace, writing and recording nothing. It is the one write from the copy into R2, so the rule holds there for every copy back, whatever names the namespace: today the owner's object, after the second PR `locate`.

5. **The drill reads them whole (`drill`).** Monthly, after its byte check, it reads the copy as a copy back of the whole bucket reads it, `BACK_DAYS` ago: the marks (refusing as item 4 does), then every name the copy then held that R2 lacks. It counts as written each mark R2 lacks (a whole-bucket copy back writes the marks first) and each object of a namespace no mark names, leaves out every marked namespace's objects, and stops on any name that is neither a namespace's object nor a mark. So each month it proves: the marks are readable on both sides and in shape; the copy lost none in 21 days; and what a total-loss copy back would write leaves every erased namespace out. It writes nothing, as before.

6. **What is still missed, and its bound.** An erasure's mark reaches the copy at the first night that passes after its delete, a day after the mark. If the account is lost before then, the copy has the namespace and no mark, and only the erasure's own records knew; they are gone with the account. The window is from the mark to that night: about two days, at most `HIDE_NIGHTS` past the delete, under the canary's alarm. It is the copy's own limit (a night a day), named here and in `checklist.md`.

7. **Designed here, built by the second PR (`untangle/r8-locate`, `tasks.md`):** about 1,500 lines with this one, so split; the mark lands first, since every erasure from now on needs it.
   - **`locate`: a namespace's owner, without the directory.** A files Worker read, `locate(ns)`: one root of the namespace listed and opened under its wrapped key, part 0 opened under the data key and held to the root's hash, its first line held to the export header's shape, and the header's `owner` answered with that generation, nothing else of the part. Every generation of a namespace names its one owner (`restore.begin` holds each to the object's). It needs the root and part 0 in R2.
     - Reached through a third entrypoint, `FilesLocate` (`locate` alone), which the doors bind for the operator channel, as `FilesUpload` is bound for the upload door. The op is `restore.locate {namespaces}`, a page of namespaces a message, addressed to the platform's reserved principal (`PLATFORM_CALLER`, which no owner is named): the op table says which ops are the platform's, as data. Its page is sized against the queue consumer's CPU limit (each locate opens up to 4 MiB): measured by that PR.
     - **Rejected:** the owner's object (it answers only for itself, and the owner is what is sought); the kit opening part 0 with `FILES_KEYRING` (owner rows opened in a runner; `r5r.md` item 12 puts it in the files Worker); a sealed owner tag beside each namespace (a new format, the same keyring).
   - **After an account's loss: mode `recover --at`,** in a new account after a dark deploy, with the copy's read key and a day's R2 write pair:
     1. the marks read (item 4), and every mark R2 lacks written back first, so R2 holds the record again and the next night keeps it in the copy;
     2. each namespace of the copy at `--at` that no mark names and that holds a root: the restore record, then its objects written back whole (`copyBack`'s refusal holds again), then its owner located;
     3. the located owner's restore begun in the same run (`restore.begin {namespace, gen}`), so from the run's end every written namespace is named by an object, whose erasure deletes it and whose restore's sweeps delete what no restored row names (`r-restore-chunks.md`, `backup.ts`'s adoption sweep). A run cut short writes and begins again (`--ignore-existing`; begin goes on).
     4. Two namespaces locating to one owner: a loud stop naming both. A namespace with no root is not written: no wrapped key of it survives, so nothing opens its chunks.
     - Item 11's predicate (only what a row names) can't hold here: no object holds a row yet. The restore's own sweeps take its place.
   - **A lost object (the account intact):** the same path for one `--owner`: the unmarked namespaces whose roots R2 holds located, the one naming the owner taken, then mode `restore` from it. One whose roots only the copy holds goes through `recover`.

   - The drill's fake names (`o/aa/…`) were no namespaces; its test now uses real ones, since the drill holds the layout.
   - Left: `r8-copy-restore.md` item 5 says the mark is "written at the mark"; item 3 here decides otherwise, and this file is its record.

9. **The proof.** Fakes and workerd only; nothing live.
   - `files/test/chunks.test.ts`: the mark is put before anything is deleted, so a crash between the two leaves it and the namespace; the delete again deletes the namespace and leaves the one mark as it was; no sweep or chunk delete reaches it; another namespace is not marked.
   - `deploy/guards/offsite.test.ts`: a namespace marked in the copy or in R2 alone is not written and no restore recorded, nothing of the owner's object asked; another namespace's mark changes nothing; the marks unreadable (a listing failing, a name out of shape, a mark the copy held then and no longer) refuse with nothing recorded or written; the drill leaves a marked namespace's objects out, writes a lost mark back, and stops on a name of no layout or marks out of shape.
   - `deploy/guards/deploy.test.ts`: mode `copyback` lists the marks first, and its plan says so.
   - **Mutations**, each failing its test: the mark's put dropped; the mark put after the delete; the mark not made once; the mark check dropped; R2's marks not read; a name out of shape let through; a lost mark unchecked; the drill keeping marked namespaces.
