# Sandbox slot queue as built (2026-11-26)

The Doors contract requires the first owner in the platform's line to receive another wake while it waits. A new owner and a retry both use the same line. On main `d662e63e` every wait replaced the head's alarm with a deadline measured from the latest caller. Independently replaying arrivals every 30 seconds for six simulated minutes on Node 22 and 24 produced zero wakes, while the quiet queue rang three times. The queue order itself was correct. The same scheduling code is on #5857 and the staged capacity and creation branches.

- [x] Preserve the earlier alarm in the queue's existing scheduling method. A missing alarm is armed, a shorter ceiling may advance it, and an empty line still disarms. The deadline stays with the queue across retries and handovers. The architecture guard permits only the queue to read its clock here. No new storage or caller input is needed.
- [x] The ordinary Workerd regression checks the stored deadline after a new arrival, a retry by the first owner and a retry by the second. It delivers the wake and checks that both owners are notified in order as the first leaves. Main postponed the first deadline by 30,004 ms. The candidate passed all 164 sandbox Workerd/guard cases and the full Node 22 platform typecheck. The first draft exercised two separate test line instances and timed out, so it was discarded. The first full candidate run caught the old clock guard rejecting the queue's own read.
- [x] On the fixed code, nine independent SQLite and virtual-clock histories per Node version (22 and 24) verified arrival and retry traffic rang the first owner at 60, 180 and 300 seconds. A shorter ceiling, missing alarm, empty line, and two overlapping notification histories also passed.
- [ ] Recheck the queue alongside the open template move on #5857 before coordinator integration. Recovery after a sandbox creation reply is lost and retaining the verified copy through an interrupted move remain open on their existing branches.

A rejected ring exposed another scheduling boundary. The prior code armed the next wake only after the queue accepted its message. An ordinary immediate ring still had its earlier alarm. During an actual alarm delivery, the platform could retry the old event, but the queue had not installed its own future deadline. Cloudflare documents a finite retry count for that event. [Durable Objects alarm contract](https://developers.cloudflare.com/durable-objects/api/alarms/)

- [x] Arm the next wake before sending the notification, then read the current head. Queue failures remain visible to the caller. On the previous code the ordinary Workerd regression saw no scheduled successor after the test harness delivered the alarm and the send rejected. With the fix the ten line tests passed, including rejection followed by eviction and successful notification. A separate time-driven Workerd exercise confirmed a new deadline 5.003 seconds after the first delivery and successful notification 5.001 seconds later. All queue failures were injected locally.
- [x] The first deadline change at `94be59ef` passed 185 combined sandbox tests with the same six existing creation and template-move failures on current main plus #5857. The first combined typecheck was killed during concurrent checks. Full verification of this subsequent queue-failure change is in progress.

Final verification on `a3babe83` passed all 165 standalone sandbox Workerd/guard tests and full Node 22 platform types. The current-main rehearsal with #5857 and the staged creation, capacity, list and move regressions passed 186 sandbox tests and full types. Its six existing failures remained the same. The joined test already imported the eviction helper, so the rehearsal retained that single import. The first deadline change's joined typecheck also completed successfully on retry.
