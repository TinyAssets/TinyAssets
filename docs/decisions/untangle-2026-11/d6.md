# D6 as built (2026-11-14)

D6 settles the two inbound-door items `c7.md` item 5 left to lane D, each from the research below.

1. **A capability URL's sender gets one refusal body, `{error: <code>}`.**
   - **The two shapes.** Before D6 the sender got `{error: <shown code>}` (`refused.ts` `asInbound`) for every refusal the door or the object threw. For the object's refused answer (`InboundAnswer`: `mailbox_full`, `event_conflict`, `agent_unavailable`, `too_large`) it got the answer itself, `{state: "refused", error, retry?}` (`inbound.ts` `delivered`). So the same `too_large` came back in two bodies: `{error}` when the door could not read the event, and `{state, error}` when the object could not mail it.
   - **Who reads them.** A capability URL is n1's "generic webhook" (`n1-inbound-door/design.md`, the channel table): a per-binding URL whose sender (an HMAC signer, a header token) reads the status and `Retry-After`. The n1 design states the capability answers as a status and a code (`400 event_identity_required`, `404 not_found`, `400 stale_event`, `413`, `429` with `Retry-After`), never a `state` field. No sender, doc or probe in the repo reads `state` or `retry` on a capability answer (`scripts/probes/capability_url_live_proof.py` reads the status). The Python door this ports (`webhook_inbound.py`) answered every non-2xx to a generic sender with `{error: <code>}`, and `{state: "refused"}` was only ever a `200` body.
   - **The shape kept is `{error: <shown code>}`.** It is D2's JSON refusal frame (the code's status, its `Retry-After`, `{error}`), with the code shown in place of the message, as `refused.ts` has the inbound hooks show one, because n1 tells senders codes.
   - **The fix is one rule, not a second copy of it.** `delivered` throws the object's refused answer as a `Refusal`, and the surface already around the call (`asInbound` or `asShared`) answers it, as it answers a refusal the object throws. `delivered` no longer restates `asShared`'s rule (terminal is a `200`, transient is its status and wait), and it loses its one-caller `shared` parameter.
   - **A shared app's side follows from the same rule.** Past its proof and its route, a shared app is answered by `asShared`, `{state: "refused", error}`, with two exceptions before D6:
     - the object's `mailbox_full` answer also carried `retry: true`;
     - the owner's maintenance gate was thrown outside the shared surface, so it was answered `{error: "unavailable"}`.

     The gate now runs inside the routed surface, so a shared app is answered by `asShared` for everything past its route. Both answers keep their status and `Retry-After` (`429`/`5` and `503`/`60`). Slack reads only the status class (n1 §5), so no sender sees the difference. A capability URL's sender is answered by `asInbound` either way, so the move changes nothing for it.
2. **`invalid_signature` was `inbound_proof_invalid`: one refusal, one code.**
   - **Both codes meant one thing.** The door threw `invalid_signature` when a shared app's request failed `proves(app.profile, …)` against the platform's signing secret. The object threw `inbound_proof_invalid` when a capability event failed `proves(proof.profile, …)` against the owner-held secret. That is the same function (`contract/src/inbound-proof.ts`), on the same raw bytes, at the same `401`, terminal and named. Whose secret is checked follows from the route, and a sender would do nothing different for either. No code or sender read either code, only the tests that pinned them.
   - **The code kept is `inbound_proof_invalid`.** It has the wider meaning: a proof is any `inbound-proof.ts` profile, the header token as well as the HMAC, and Slack's `v0` signature is one such profile. It is also the code capability senders already got (`doors-live.test.ts`). `invalid_signature` is removed from the code table.
   - **The wire change:** a shared app's request whose signature fails is answered `401 {error: "inbound_proof_invalid"}`, where before it was `{error: "invalid_signature"}`. A real Slack delivery never fails its signature, and Slack reads only the status in any case.
   - The entry moves in `contract/src/refusal.ts` (lane C's file: that one entry and its comment) from the object's codes to the inbound door's, since both throw it.
3. **The object's `retry: true` goes too.** C7 kept it (`owner/src/inbound.ts` `inboundRefused`, and `InboundAnswer`'s `retry?` in `contract/src/binding.ts`) because it was on the wire. After item 1 nothing reads it and no sender sees it, so it is deleted here, with no wire change: `mailbox_full`'s transience is its code's alone.
