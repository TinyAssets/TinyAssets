# Restarting a backup across a schema change

The manifest pass replaces a writing generation after a migration so a single backup cannot mix schemas. Its ordinary completion test covers an uninterrupted switch. On main f934871ad the pass first removed the old generation and owed a sweep, then separately tried to open the new one. In an offline schema-17 to schema-18 rehearsal, an interrupted replacement insert left zero writing rows. A subsequent pass, after the fault cleared, swept the old generation and deferred recovery by 9,602 seconds. Joining the pin, capture and pass-failure corrections still had that delay, although the log no longer captured for an absent generation.

The local transition now removes the prior row, stops its capture, owes its sweep, records the owner notice and opens the new-schema capture in the same SQL transaction. If opening fails, the existing writing row carries the pass retry. A subsequent pass detects its old schema before reading a page. It can restart without mixing data or repeating the owner notice. The per-generation backoff, the other reasons for giving up a generation, and the Files operations before and after this transaction keep their distinct responsibilities. An owner that already lost the replacement evidence on an earlier version may still wait for the next night.

A successful replacement can also consume the rest of the pass. On main the continuation then targeted the old identifier, so the new writing row had no retry time and the next job was immediately due. The pass now returns the identifier it actually left unfinished and records the existing five-second continuation on that row. On an ordinary pass the identifier stays the same.

At f1b3cf832, five focused Workerd cases and the scoped Node 22 typecheck passed. A second SQLite replay used all eighteen migrations and interrupted six distinct writes on Node 22 and Node 24. All six preserved the old capture, buffered changes, sweep count and notices on each runtime. After the stored 300-second retry, a fresh lane opened the replacement, recorded one notice and set the five-second continuation. The same checks passed on local combined 6db9b9e60. Its separate simulations used stored schema stamps 9, 12, 17 and a prospective 19 with a schema-18 worker.

The export door obtains its generation through the same backup object. On f934871ad and combined 533733c40 an export resumed at the quiet-unit boundary after the old generation was removed could start another generation before the schema replacement opened. On both Node versions that interleaving produced two writing rows, with the export’s generation different from the active change log. On f1b3cf832 and 6db9b9e60 it produced one row and the export named the active capture. This replay exercised the production generation selector with a synthetic concurrent callback.

An offline workerd replay also entered through the public owner export door with a real owner session. Starting an export at that boundary on the shared-opener branch 703e4c638 left two writing rows. The stored export receipt named the generation whose change log had already been replaced. On 1c11576c6 there was one writing row and the receipt named its active capture. Each run checked the receipt returned by the door against the persisted export row and the active change log.
