# o-keyrings as built (2026-11-17)

`untangle/o-keyrings` is the merge plan's item 5: lane O's two keyring lines, V2-H1's goldens and B14's keyring half.

1. **The gateway's binding takes the owner's connection ids, and a doorbell its own key space** (d2 B6, `v2:V2-H1`).
   - Before, `gateway/src/keyring.ts` held its own connection grammar, `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`, a copy wider than any id the gateway is sent. Every model connection is the id the owner's object mints, `c` and 24 hex (`contract/src/ids.ts` `CONNECTION_ID`, the same since #5457; `owner/src/connections.ts` mints and reads it back by that grammar). A doorbell is `wake.<SUBSCRIPTION_ID>`.
   - Now `binding` checks `CONNECTION_ID`, and `wakeBinding` checks `SUBSCRIPTION_ID` and names `wake.<subscription>`, both in `keyring.ts` beside the seal's domain. `doorbell.ts`'s own `bound`, which checked the subscription and then went through the wider grammar, is gone.
   - **Not the union d2 wrote** (`CONNECTION_ID | wake.<SUBSCRIPTION_ID>` in one grammar). A union would let a model door (`seal`, `exchange`, `verify`, `forward`, `refresh`, `reseal`, `revokeAtProvider`) bind into a doorbell's key space, with only the opened value's checker keeping the two kinds apart. Splitting by kind refuses it at the binding (`invalid_binding`), and each kind's grammar is the contract's id. The checker still separates them for a `Binding` built by hand (`keyring-main.test.ts` "opens no doorbell as a model credential").
   - **No stored record is refused.** Every caller names a connection the owner's object minted: the doors' connect steps take `connectionPrepare`'s id, the egress door parses `CONNECTION_ID` from the path (`contract/src/egress.ts`), and the owner's reseal, refresh and revoke read their rows by that grammar. The doorbells are bound as before. The bytes of every seal are unchanged: the domain and the additional data are the same strings.
2. **The goldens, sealed again by their own commit's code.**
   - `ci/keyring-vectors.json` holds blobs sealed by main's code at `e115a12`, which `gateway/guards/keyring-main.test.ts` runs from git (`ci/history.ts` `treeAt`). The credential (`gateway.k1`, `gateway.k2`) and the plain value (`gateway.value.k2`) were bound to the connection `c1`, which the owner's object never mints and today's binding refuses (#5543's body, "Left").
   - They were sealed again for `c0123456789abcdef01234567` by `e115a12`'s own `binding`, `seal` and `sealValue`, loaded through `treeAt` exactly as the guard loads them, under the same throwaway keys and rings. Each was opened again by that code before the file was written. No blob was written by hand, and the doorbells and the files Worker's vectors are as they were. The tool was a scratch script (sha256 `972d856c2a892dd6…`), not kept: a golden is sealed once by code that no longer changes, and the guard below is what holds it.
   - SHA-256 prefixes, old to new: `gateway.k1` `9361092b3374a7f4` to `debfcb62346e254a`; `gateway.k2` `d59c8c6bb559ccc1` to `b9bd3e9276060f68`; `gateway.value.k2` `5207a80adf6cc364` to `faddf4d3981eebfc`.
   - **A stored record still opens.** Both golden suites now bind each golden as the gateway binds a stored record, by its names through today's `binding` and `wakeBinding`, not with a `Binding` built by hand. So `keyring-main.test.ts` shows `e115a12`'s blobs opening on today's code under every ring that holds their kid (the older kid resealed, a retired kid refused), today's blobs opening on `e115a12`'s, and every refusal matching; `keyring.test.ts` shows the same goldens opening in workerd.
   - The gateway's test bindings that went through `binding` with `c1` or `c2` now use two ids from `test/support.ts` (`C1`, `C2`). The binding's refusal table had owner and version rows bound to `c1`, which would now pass on the connection alone, so they take `C1`, and two rows are new: a connection the owner never mints, and a doorbell's key space through the model binding. `wakeBinding` has its own.
   - One caller outside the gateway named a connection no owner mints: the owner's tests' catalog check (`owner/test/gateway-support.ts`) sealed its throwaway key for `c-catalog` on the real gateway Worker. The rpc and rv recorders found it: on the first head run, every door they connect a source for was refused `invalid_binding`. It now seals under a connection id.
3. **B14's keyring half: not built. `platform_setup.py` and its keyring case go on the manifest** (`x5.md` item 10). The weighing:
   - **Building it costs the founder's setup the platform.** `deploy.ts keyring-new` runs only under Node 22.18 with the platform's `npm ci` (it imports the envelope and the E2B client), on the founder's Windows machine, for one keyring. And `keyring-new` writes the ring to a file, which breaks the setup's rule that a value travels on stdin alone, never on disk; keeping that rule would add a stdout mode to `keyring-new` for this one caller.
   - **It buys nothing that runs.** The setup is done (`deploy/checklist.md`, "Before you run it"), and `ensure_secret` makes a value only where it is absent, so `make_keyring` makes no keyring again before the cutover deletes the setup, unless a keyring is added to `made`, and then the case below still holds it to `keyring-new`'s shape. After that, `keyring-new` is the one maker, as the kit's notes already say.
   - **The copy is not hidden.** `make_keyring` is three lines of a fixed shape, and `deploy.test.ts` "takes the keyring the founder's setup makes" holds it to `keyring-new`'s shape, until both go.
   - So `platform/cutover.json`'s cutover phase deletes `scripts/platform_setup.py` and `tests/test_platform_setup.py`, and its edits take `tests/test_platform_setup.py` out of `tests.yml` and the case out of `deploy.test.ts`. The case ran the kit's maker as well; that half is now its own case, "makes a first keyring with keyring-new, run as the release runs it", which stays, so the deletion takes only what reads the Python.
   - Left for `untangle/b24-manifest` (its line in tasks.md): the text that names the setup (`platform.json` `made`'s `why`, `deploy.ts`'s kit note, `checklist.md`, `platform-deploy.yml`'s header, `docs/host-actions.md`, `.github/test-durations.json`, `deploy/review-app.html`, which runs the setup's `review-app` step and is read only by the setup's tests, and `tests/test_workflow_production_environment.py`'s note). The inventory of `scripts/` decides those whole, with what `made` says once no setup makes its secrets, and where the setup's `workos` and `review-app` steps go, since the deletion takes them too (review).
