# r7-rotation-driver as built (2026-11-15)

Lane R's key rotation, PR 2 of two: the kit's driver over PR 1's answers and ops (`r7-rotation.md`, #5627). The design is lane R's research of 2026-11-15, item 2, its PR 2 half (Fact 14); what the build settled or found is below.

1. **Mode `rotation`** (`--keyring FILES_KEYRING|GATEWAY_KEYRING`; `deploy/operator.ts` `rotate`).
   - The keyrings and their ops are data, `platform.json` `keyrings.rotated` (`FILES_KEYRING`: `owner.rewrap`, copied; `GATEWAY_KEYRING`: `owner.reseal`, not copied), read and checked once in `facts.ts` (`ROTATED`): each a keyring, each op an operator `owner.` op. `OPERATOR_KEYRING` is not there: a MAC key strands no stored blob.
   - It lists the directory's `o:` keys (`OWNER_ENTRY`, now in `contract/src/ids.ts` beside `INBOUND_ROUTE`, which `doors/src/directory.ts` reads too: the kit holds no copy of the prefix) and sorts them by their UTF-8 bytes, so `through` compares the same way whatever KV's order.
   - A page is one Queues batch push (`cloudflare.ts` `sendBatch`, at most `BATCH` = 100) and one answer read per owner, each after `PACE_MS` (400 ms): Cloudflare's API takes 1,200 requests per five minutes per user, so the reads run at 2.5 a second, under two thirds of the ceiling (Fact 15, a vendor's limit). The batch path and body (`/queues/<id>/messages/batch`, `{messages: [{body, content_type: "json"}]}`) are recalled from Cloudflare's API reference, which no session here could reach (`developers.cloudflare.com` is outside the network): the `live:` rotation proves them, and a wrong one fails loudly at the first page with nothing recorded.
   - Each answer is read at least once, then again until `WAIT_MS`; one not answered by then owes, naming the dead-letter queue, and the run goes on.
   - Its record, `deploy:rotation:<keyring>:<active kid>` in the control namespace, is the research's: `keys` (each kid's key's SHA-256, never a key), `active`, and `passes` of `{began, through, owing, swept}`, every time an answer's `done`. It is written after every page, so a crashed run goes on after `through` and the page cut short is asked again. A record begun with another ring under the same active kid stops the run.
   - Order of a run: the pass's `owing` first, then the directory after `through`, then whoever owes once more; whoever still owes is named with `owner.state`'s restore step. `swept` is set at the page that leaves nothing owing and nothing after `through`, so no field beyond the research's is needed. A swept pass makes the next run begin a new one.
   - `owner_erased` counts as done; any other refusal, and no answer, owes. An answer that left nothing (`left` 0) whose `kid` is not the stored ring's active kid stops the run before its page is written (`owes`): the deployed ring is not the stored one. One that left some names the kid the owner's own key is still under (a restore's hold before the owner was rewrapped, a key that no longer opens), which proves no ring, so it owes (the review's fix: every such owner had stopped the run). That closes `checklist.md`'s residual for this act, as the research said.
   - At `RUN_MS` it stops at a page's end, saying to run again; the end's `owner.state` asks stop there too, the owners left unnamed still owing in the record (the review's point). `RUN_MS` (20 minutes) is `PIN_WAIT_MS` renamed: one value for one reason, the apply job's 30 minutes, which mode `restore`'s pin wait and the rotation both stay inside.
   - It refuses while the doors Worker's secret listing holds `IMPORT_KEY` (the window open). `cutover.json` lists that edit of `deploy.ts` and of its test, with their import of `contract/src/import-message.ts`.
   - The plan job holds no keyring, so its one line is fixed text; a run with the secrets and no `--yes` says where the record stands and asks nothing.
2. **`keyring-retire <file>`** writes `<file>.retire`, the active key alone, beside the file and never over one (`wx`), and leaves the file as it is: the old ring kept offline is the one way back (`ringWith` never reuses a kid's name). A ring of one key is refused.
3. **Mode `retire`** (`--keyring`, `--confirm`; `deploy.ts` `retirement`, a function of the record, the stored ring, the copy's nights and the clock, so each gate is tested alone).
   - It refuses unless the stored ring is the record's ring less every other kid (one key, the same active kid, its hash the record's), and the record's latest pass swept.
   - For a copied keyring it refuses while the copy is `overdue`, and reads T with `offsite.ts` `firstNightAfter`: the copy job's `completed_at` of the first night on `main` that passed and whose run was made after pass 1's `swept` (made, not started: a night made before and re-run after still counts as before). The gate is T + (`KEEP_DAYS` + 1) days; the latest pass must have begun at or after it. With no night after pass 1 it refuses, unless no night ever passed: then the copy holds nothing, and the plan says so.
   - `firstNightAfter` and `watch` now read the nights through one generator (`nights`), so the copy's jobs are found by one rule.
   - Without `--confirm` the apply job names the words, `retire-<keyring>-<kids>`, and changes nothing; other words stop it. With them it sets the keyring on each Worker whose config requires it, `wrangler secret put <name> --name <script>`, then the canary runs. Not through `setSecrets`: that needs the stage, whose steps make namespaces on an applied run and read the owner issuer's discovery, and its `secretPlan` keeps refusing a rotated ring of fewer than two keys, so the shrunk ring is taken on this path alone with no flag on the general one. Each holder must be deployed and hold the keyring already.
   - It needs `GITHUB_TOKEN` (the copy's nights), which the apply job already holds for the canary.

8. **The research's open check fails: an imported owner can be left with data and no `o:` record after the window.** `window.ts` `admit` admits none unless every bundle verified clean ("going on without one is the founder's call"), and stops at the first refused admit ("nothing more is admitted"); `wipe` discards every bundle of `out`, and a real owner already admitted refuses the discard (the consumer's gate 4), so it is a rehearsal's tool, not one owner's. The way on without a failed owner, an `out` without its bundle, leaves that owner's object pending with its imported data under the old files kid, and nothing lists it: no rotation reaches it, and after `retire` its data never opens. `rotation`'s refusal while `IMPORT_KEY` is held covers only the window itself. Options for the founder (a product decision: it deletes an imported copy of a user's data, the old stack's final backup holding the original through its 14-day hold):
   - **A.** A window step `close`, before `IMPORT_KEY` is deleted, that refuses unless every bundle's owner has an admitted `o:` record or a discard in the window's record, and discards, with the founder's words naming each, an owner left behind.
   - **B.** The same check, refusing only, with the owner left to be imported again in a later window.
   - **C.** The import writes a directory record of its own state (`imported`) at its first slice, which the rotation lists and the sign-in reads as never signed up: it changes the directory's meaning for every reader.
   The founder chose B (2026-11-16); built as `i-window-close.md`.
9. **Owed by PR 1's review: an owner a blob that no longer opens keeps above `left` 0.** From the code, three cases land in `owing`, so `retire` never passes while one exists (safe, but stuck):
   - a refused doorbell blob is counted left (`wakes.ts` `Doorbell.reseal`, PR 1's review);
   - a connection's blob the gateway refuses, counted left by `Connections.reseal`, the rest resealed;
   - a data key or generation root that no longer opens, counted left by `rewrap`, the rest rewrapped.
   The last two threw (`credential_refused`, `data_key_refused`), refusing the owner's whole op and leaving its other blobs under the old kid; the review fixed both as PR 1's fixed the doorbell's, the three through one `contract/src/refusal.ts` `orRefused`.
   A remedy deletes, or strands for good once the kid is retired, a credential or a user's files: a product decision, so it is not chosen here. Options:
   - **A. Quarantine** (`owner.quarantine`, an operator op with words naming the owner): each blob the ring refuses moved, as it is, to a quarantine table not counted in `left`; a connection set `error` (reconnect), a subscription ended (subscribe again), a generation hidden from `restore.source`; the owner told by a notice. It opens again only if the retired key comes back from the offline file. An owner migration.
   - **B. Removal**: the same, the blob deleted. Irreversible.
   - **C. No op**: the founder restores (mode `restore`, an older generation) or erases that owner, or keeps the old kid.
   Owed: `untangle/r7-unopenable`, after the decision (`tasks.md`).

12. **The provider listings a rotation relies on (2026-11-18).** A successful HTTP response can still be missing the identity of a resource. With synthetic responses on `f934871ad`, a secret row without its name let rotation send a rewrap, a second namespace with the directory's title hid the admitted owners, and a KV key outside the requested prefix sent a rewrap under the wrong principal. The kit now reads the whole inventory before sending the first batch. Worker and secret names must be present, namespace titles and IDs must each be unique, and KV keys must have the requested prefix. Rotation reads each suffix through the same principal validator the doors use when writing directory keys.
    - Numbered pages must identify the page requested and retain their page size. A different size changes its starting offset. A repeated cursor stops a cursor listing. KV keys and R2 buckets can return a final empty cursor or omit it, with a count and no page number. The single unpaginated result is still accepted. These checks concern the provider's responses. A listing across requests is not an atomic snapshot of a changing account.
    - The applied-mode tests check both the operator messages and the progress record. They use a fake provider, synthetic directory and test keyrings. The live sweep and retirement remain stage work.
