# X6 as built (2026-11-14)

X6 builds the plan artifact that `d3` §A5 put in B12 (`p3:P26`, `tasks.md` §10's B12 line): the `apply` job runs the plan it was approved on. Before this, `platform-deploy.yml`'s apply job planned again from scratch and acted on that, so a live change in the window between the two jobs (the pair job alone can take most of an hour) made it do something the plan job never showed.

1. **The plan is what the dispatch asked and the plan job's lines, not a typed item per line.**
   - `Plan` (`deploy.ts`) holds `asked`, the dispatch's mode and options as `parse` reads them, and `lines`, each line the row's plan-job steps report. The report prints the same `lines`, so the printed plan and the compared plan are one list.
   - **Why lines, not typed items:**
     - The founder's dispatch is the approval (`checklist.md`, "Starting a run with a mode other than `plan` is the approval"), and P26's statement is that the apply job may do "something not shown". What is shown is these lines. Comparing anything less would miss a shown change, and anything more would stop on facts nobody was shown.
     - Each line is built only from what its step read live and from the tree, and both jobs of one workflow run check out its one commit. So two equal lines are two equal sets of shown facts.
     - A typed item per line would mean about 35 kinds, each with a renderer. The step would decide and a second place would word it, tied only by the kind's name. That is a hidden link, added to compare what the lines already compare exactly.
   - **What the plan job's lines are:** the row's `steps.public`, the `--public` list with its `…Later` twins. It is never the apply job's own plan, which reaches what the plan job can't (WorkOS's listing, E2B's hook, the optional secrets' values) and words its checks differently by construction. So the apply job makes the plan job's plan again: the same row's `steps.public`, run with the plan job's reach and no apply, before any step of its own (`approved`).
2. **The facts that change by the moment are in no line.**
   - The run's id was in four lines: the route record's key and its handback hint (`keepRecord`, both branches) and the control record's kept key (`controlEdit`). A by-hand run's id is the clock (`local-<time>`). Those lines now name "this run's route record" and "<this run's id>". The report's heading names the run (`Run <id> would change:` / `Run <id> changed:`), and the plan file holds it beside the plan, never inside it.
   - **The run is read once,** in `parse` (`Run.job`). The heading, the route record's key and record, the control record's kept key and the plan file all name that one id. Before this, `keepRecord` and `controlEdit` each read `runOf` with the clock themselves.
   - No line reads the clock. The times a line does show (`record.at` in the held record's line and in the handback's) are stored live state, and they are compared like any other.
3. **The doors' upstream line now names the client and the JWKS the doors deploy.** Before, it named the issuer alone. A repository variable edited between the jobs (`WORKOS_CLIENT_ID`), or a discovery that names another JWKS, would have deployed another `UPSTREAM` with no line different. The test changes `WORKOS_CLIENT_ID` between the jobs and the apply stops.
4. **How apply holds it, before any change:** `given` (the inputs), then the plan job's plan made again, then the file read, then its run checked, then the two plans compared, and only then the apply job's own steps.
   - **Making the plan again first** means a state the plan job itself refuses stops the apply with that same refusal, before any change. On the harness this covers the 13 `split` scenarios: main's apply made storage changes before reaching the routing key's refusal, and head's stops with no write.
   - **On a difference,** it names each one: the dispatch's option that differs, each approved line not planned now, and each planned line never approved. Then it stops with "nothing is changed. Dispatch the mode again for a new plan".
   - **On a pass,** the apply's own plan opens with "the plan job's plan, made again from the live state, is the one approved".
5. **The artifact.**
   - The plan job writes its plan to `--plan` (`${RUNNER_TEMP}/deploy-plan.json`) and uploads it as `deploy-plan`, with `if-no-files-found: error`, `overwrite: true` (a re-run of the plan job writes it again) and `retention-days: 1`.
   - The apply job downloads `deploy-plan` by name, with no `run-id`, so it reads this run's artifacts alone.
   - **The kit refuses on its own** (Fact 8), whatever the workflow hands it:
     - `--yes` without `--plan`;
     - `--plan` with neither `--public` nor `--yes`;
     - a missing, unreadable or shapeless file;
     - a file whose `run` is not this run's id.
   - The pins are the repository's own (`ios-release.yml`, `android-build.yml`).
6. **By hand, each invocation is its own run.** Its id is the clock, so a `--yes` by hand refuses a plan made by another invocation, unless both ran in the same second, since `local-<time>` keeps whole seconds. `--yes` is the apply job's anyway: the production secrets are never on a host (Direction 8). The kit still accepts a by-hand id (x3 part 2, item 5), but a by-hand apply now needs a plan of its own run.
7. **Re-runs.**
   - **Re-run all jobs:** the plan job plans the state as it now is and writes the file again, and the apply job holds to that. A routes attempt keeps its first attempt's record, as before.
   - **Re-run the failed apply job alone:** if the earlier attempt changed anything, the live state no longer plans what was shown, and it stops before any change. `checklist.md` says to re-run all the jobs.
8. **Left:**
   - **Seconds between the apply's remade plan and its own steps' reads.** The apply job's steps read the live state again as they run, interleaving reads and writes by design. Another actor's change inside those seconds is not caught. No other kit run interleaves, since the workflow's concurrency group holds them apart. Closing the gap means the apply's steps would take the remade plan's reads, one pass: a reshape of every row's steps, not this PR.
   - **The namespaces' ids are in no line.** An existing namespace's id changes only if it is deleted and made again. A deleted one shows as a create, unless it is remade inside the window.
   - **The plan's path is spelled in the workflow four times:** the plan job's command and its upload, the download and the apply's command. The workflow test holds the four together.
