# D5 as built (2026-11-14)

D5 gives the doors' own pages their touch icon, which `x4.md` §4 left owed to the doors lane.

1. **The problem.** After the cutover's `routes`, the doors take `/app*` (d3 §J1), and with it the root `/apple-touch-icon.png`. The doors' pages (`doors/app/index.html`, `signed-in.html`, `connected.html`, served by `src/pages.ts`) named no touch icon, so iOS fell back to asking the root for one and got the doors' 404.
2. **The pages name the website's icon.** Each page links `<link rel="apple-touch-icon" href="/icons/apple-touch-icon.png">`, the file X4 moved to `WebSite/site-react/public/icons/`.
   - The file has one home, the website's. No doors route takes `/icons/*`, so after `routes` the site serves it, on the same origin as the doors' pages (`identity.json` `host`).
   - The doors' headers allow it: the pages' CSP has `img-src 'self'`, and the icon is same-origin. `Cross-Origin-Resource-Policy: same-origin` is on the doors' own answers, not the site's, and binds nothing here.
   - A copy in the doors' assets is not built: it would be a second home for the same bytes, kept in step by nothing.
   - The link carries no `?v=`. The site's mark version is the site's constant (`layout.tsx` `markAsset`); copying it into the doors' HTML would be a copy of a value with nothing tying it to the site's.
3. **The guard.** `doors/guards/app-files.test.ts` holds every doors HTML page to naming a touch icon, the path it names to no doors route taking it (`contract/src/identity.ts` `routeTakes` over `identity.json` `routes`), and to the website's public folder holding the file. A page without the link, a link under `/app*`, or a link to a file the site lacks each fails it.
4. **The root fallback is not served.** iOS asks the root for `/apple-touch-icon.png` (and `-precomposed`) only when a page names no icon. Every doors page and every site page (`layout.tsx`) now names one, so nothing of ours needs the root. A client that probes the root regardless gets the doors' 404, which costs nothing. The doors serve no `/apple-touch-icon.png`.
5. **No favicon link.** X4's review suggested one as well. The doors' pages name none, so browsers ask the root `/favicon.ico`. No doors route takes that path (the identity guard holds the site's `public/` files to that), so the site answers it after `routes`. A link would only restate the browser's default.
