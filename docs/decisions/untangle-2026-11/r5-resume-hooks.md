# R5 P-resume as built (2026-11-17)

R5's third slice (d3 §N4; `r5_research.md` §3 steps 3 to 5, §6 slice 3), on P-decide (#5672, `r5-decide.md`), with owner migration 17's pin. The research is the design; what follows is how it landed and where it departs. P-hooks, combined with it in the merge plan (item 8), is its own branch: item 7.

1. **Migration 17's pin rode this branch, as its own commit.** `node ci/kit/locks.ts pin owner 4d9d66745` (#5672's merge), as #5537, #5589 and #5637 pinned theirs; `digests owner` lists seventeen. tasks.md's line is ticked, naming this branch.
2. **A held call of a run's is bound to its conversation.** A run's account carries its conversation (`runs.ts` `GRANTS` joins it from the run's row; `door.ts` `Account.run.conversation`), so the decision's actor names it (`actions.ts` `Actor.run`), and the call's digest holds it. An approval admits the same call by the same agent under the same authority in that conversation alone, once, within the day. This closes `r5-decide.md` item 8's first half. An outside client's own call names none: its client retries it when its user says so.
3. **The owner's yes resumes the conversation (`actionApprove`).** In the answer's transaction, the yes writes a run `waiting` in the held run's conversation (`Runs.resume`), and the lane starts it once the conversation is free, resuming the engine's session as any next input does. It runs under the held run's authority as the run's receipt keeps it: its agent, initiator, client, stamp and unattended, and its origin's family. Its input names the card and asks for the call again; the approval then admits it. The door's gate is `synced`, so the lane is armed. Its answer names the run (`run`, null when none resumes). A no resumes nothing: the card goes, as P-decide built it.
   - **What the held call keeps (migration 18).** `action_requests` gains `conversation`, `run` (the run it was held in, whose receipt the resume copies) and `family` (that run's origin's family, which a receipt does not keep, and which the ledger holds a client's run to). They are set when the call is held and never changed, so the held call's trigger names them too. The table is not exported (`NOT_EXPORTED`), so `FORWARD` 18 is null and no generation's line changes.
   - **Why the yes writes the run, not the hold.** A non-deferring engine's run goes on after its call is held, and may end before or after the answer. Written at the yes, the resume exists only when a yes does, and a no leaves nothing behind to settle. Written at the hold, every no and every expired card would leave a waiting run to clean up.
   - **When nothing resumes.** If the held run's receipt or its conversation is gone (past `RUNS_KEPT` or `CONVERSATIONS_KEPT`), the yes still stands and admits the call once if it is made again. A resume refused for the inputs' queue (`QUEUE_ROWS`, `QUEUE_BYTES`) refuses the yes too, in the same transaction, so the owner never holds a yes whose resume was dropped.
   - **The resumed run answers no mail.** A mail's held run answered its own mail when it settled. Its resume's result is in its conversation and its receipt, like any run's. A schedule's resume posts to the owner's room, as a schedule's run does.
4. **Claude Code's `tool_deferred` stop is data in its record (`engine.events.deferred`).** It is one more matcher list on every CLI record: Claude Code's matches `{type: "result", stop_reason: "tool_deferred"}`, and the others are empty, since no other engine can defer. Its effects:
   - `readEvent` reads it (`Read.deferred`), and a run whose engine stopped there settles `succeeded` with the code `tool_deferred` (`runs.ts` `TOOL_DEFERRED`).
   - Its result posts no reply (`#answerOf`), since the turn ended at the held call.
   - The mark is kept on the run's `code` from the batch that brought it, so an end posted in a later batch still settles `tool_deferred`.
   - Claude's own page (code.claude.com/docs/en/hooks, read 2026-11-17) gives the shape: `type: result`, `subtype: success`, `stop_reason: tool_deferred`, with `deferred_tool_use`. The checker holds the list's shape (`check.ts`). Kimi's record is a CLI's too, so it carries the empty list.
5. **Departure: "a run settles `waiting` on a card" goes to P-hooks.** Nothing defers a call until the hook helper exists, so no run stops at a held call before P-hooks. Until then a run's held call comes back to the engine as the door's refusal, and the run goes on. What the line asks for is the conversation of a deferred session waiting on its card. The page is plain on why: "If you sent a prompt with that resume, Claude answers it without the tool's result and doesn't run the call." So a deferred conversation's next input must wait for the answer. That belongs with the decide door that defers, which knows the engine's record says it can.
6. **Owed to P-hooks (`untangle/r5-hooks`), from the vendor page:** a call the hook deferred resumes on no input. The page says "Resume without a prompt until the hook returns `allow` or `deny`", so the hook's resume input is empty where the record says the engine defers, and the message of item 3 where it doesn't. The decide door knows which, from the record's `decide` block. The page also says to pass the permission mode again on resume. A resume carries the held run's `unattended`, so it gets the same `unattended_argv`.
7. **Owed to P-hooks: its conversation waits on its card.** While a card filed for a deferred call is pending, the conversation's next waiting run doesn't start (`nextWaiting`). Its card answered, the resume runs first. Whether a no resumes a deferred session too is the decide door's to settle (item 6). If it does, the hook returns `deny` and the model hears the no. If it doesn't, the next input drops the call unrun, as the page says.
8. **P-hooks is its own branch, after the sandbox pass (`untangle/r5-hooks`).** The runner writes the root-owned hook files and runs the start check in `platform/sandbox/runner/`, and the sandbox pass (`untangle/pass-sandbox`) is open there. The honest note (d3 §N5) reads the records' `decide` blocks, so it lands with them, never ahead of a hook that holds. The merge plan's split rule is met on its other ground too: the helper, the run-scoped door, four records' blocks and the runner's writes are past what one review reads beside this slice.
9. **Owed:** migration 18's pin, after merge (`untangle/r5-resume-pin18`).
