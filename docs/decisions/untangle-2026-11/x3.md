# X3 as built (2026-11-14)

X3 builds `d2` B12 in two PRs, split where the brief put the seam. This first PR covers the rows, the typed steps, the per-Worker data and the workflow's check. The reporter and `deploy/actions.ts` come second.

1. **A step is a function from named values to named values.**
   - `Values` names every value a step makes. `step<In, Out>` names, never infers, what each step takes and makes. `Steps.none.then(a).then(b)…` builds a row.
   - `then` accepts a step only when every value it takes is made earlier in the chain, so a row out of order does not compile.
   - `Work`, `made()`, `e2bOf()` and "the kit's row is out of order" go.
   - Values a run can lack stay typed as lacking them, never stood in for:
     - an unmade namespace is absent from `ids` (`planned-` goes);
     - the configs are staged when first used, so a plan writes none;
     - `kept` is null on a run that changes nothing.
2. **A row declares its inputs, whether it deploys, and two step lists.**
   - `Row` holds:
     - `inputs` (`public`, `secret`, `optional`);
     - `deploys`: it takes `--rotate` and `--migrate`, and its apply needs the pair;
     - `applies` and `record`;
     - `steps.public` and `steps.secrets`, chosen once by `--public`;
     - `report`: what a run that changes nothing ends saying, and what an applied run runs after its report.
   - The runner checks the row's inputs before any step: the public ones, and on a run that reaches them the secret ones, each keyring parsed. This removes the `inputs`, `probeInputs`, `handbackInputs` and `keyrings` steps and every `secretsReached` branch.
   - A missing probe or handback input now names where it comes from, as a deploy's always did.
   - Where the plan job can't reach a check, its list holds that check's `…Later` twin, which says the apply job checks it. So the plan job's summary still names each check it leaves to the apply job. `hookLater` is now one of these twins and no longer a step of its own.
3. **h2 and pair plan nothing.**
   - Their rows have no report, and their plan-job lists are empty: `--mode h2 --public` prints nothing (h2's constant print goes, and so does `h2Next`).
   - h2's row declares H2's probe keys from `h2-probes.ts` `INPUTS`:
     - the two every probe needs are `secret`, so a run without them stops before the probes run;
     - the revoke probe's two are `optional`.
   - `probe`, `handback` and `h2` are otherwise reshaped only as far as typed values need (`d3` §A5). The handback's hook line and its disable became a step of their own (`hookBack`), since only the apply job lists the hook.
4. **What varies per Worker is data.**
   - `platform.json` `workers.folders` gives the doors `identity` (they serve `contract/identity.json`) and `shared_apps` (their shared-apps file).
   - `facts.ts` builds each Worker's record, `WORKER_FACTS`: `optional`, `upstream`, `routes` and `migrates`. `deployedConfig(worker, ids, upstream)` reads it, with no doors parameter.
   - `routedConfig` is that config plus its record's routes.
   - `DOORS` is the identity Worker's name, and `facts.ts` no longer imports `doors/shared-apps.json` by name.
5. **Departures from `d2` B12, with reasons:**
   - **`migrates` comes from the config's `migrations`, not a `migrates: false` flag.**
     - A flag in `platform.json` would restate what the config says, and `platform.json` holds only what no config can say (B10).
     - `--migrate` now names only `codemode`, `sandbox` or `owner`: `files`, `gateway` and any unknown name are refused too.
   - **The routed config stays a second staged file (`routed.json`).**
     - `wrangler triggers deploy` reads a custom domain only from a config (`--routes` takes no `custom_domain`).
     - A first `wrangler deploy` must never see the routes, since it would attach them before the handover.
     - It is now `stage.routed(IDENTITY)` from the record, with no doors parameter.
6. **The workflow is checked against the rows by a YAML parse.**
   - The test evaluates each job's `if` as Actions does, for every offered mode, ref and needs result, and holds it to the rows:
     - the pair job runs when the row deploys and applies;
     - the apply job runs when the row applies, after the plan and, if the row deploys, the pair.
   - The plan and apply jobs' `env` must be the union of the rows' inputs, plus the canary's bearer and the dispatch's four inputs.
   - The args array goes. Each job runs one command line that hands on the dispatch's inputs as they are, and the kit reads an empty option as no option (`--record ""` included).
   - `parse` takes `io` with no default.
7. **Owed:**
   - **Part 2:** built, below.
   - **The plan artifact** `apply` runs (`p3:P26`), before `routes` joins B12.
   - **Mode `probe`'s deletion** comes with the stage's kit PR (`d3` §H).
   - **`MIGRATED` (the locks the kit runs) is a hand list** beside the configs' `migrations`: `codemode` declares migrations and holds no lock. That's lanes C and S (`ci/kit/locks.ts`).

## Part 2: the reporter and `actions.ts` (2026-11-14)

1. **`deploy/actions.ts` holds all of the kit's GitHub specifics**, each read from a variable Actions sets:
   - `summarize(env, text)` appends to `GITHUB_STEP_SUMMARY`;
   - `maskLine(env, value)` gives the `::add-mask::` command, or null outside Actions;
   - `runOf(env, now)` gives the workflow run's id and attempt.

   `deploy.ts` names no `GITHUB_*` variable now.
2. **One reporter.** Each step's `Context` is the run's `Reporter`, plus the run and its scratch folder:
   - `say` adds plan lines;
   - `mask` masks a value in the log;
   - `summarize` adds to the summary at once.

   The `zone` step masks the account through it, `keepRecord` writes the record's copy through it, and the runner reports the plan through it. `report` and `maskInLog` are no longer exported.
3. **The record's copy is still written to the summary at once**, not gathered for the end. A `routes` run that stops after writing the record must still show the founder its id for `handback`.
4. **The run is read once a record is kept**, and its id and attempt go together into the record (`routeRecord(job, at, …)`). Before this, `recordId` read the clock twice.
5. **The by-hand id (`local-<time>`) stays, inside `actions.ts`.** It names a run with no workflow run behind it: the harness, the tests, a founder's own shell. The kit doesn't refuse such a run, since `routes` by hand is as valid as from the workflow.
6. **An empty Actions variable is read as unset**, as every other input of the kit is, by the one reader both use (`actions.ts` `set`). Before this, an empty `GITHUB_ACTIONS` still masked and an empty `GITHUB_STEP_SUMMARY` was written to. Actions never sets either empty, so no job changes.
7. **Left:**
   - `h2-probes.ts:32` still repeats the key check h2's row makes. That's outside this change's files, and h2 lives only until the cutover (the review of #5565).
