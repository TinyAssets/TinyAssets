# Lifecycle webhook observation as built (2026-11-18)

1. An E2B listing could contain the doors' webhook URL but omit its `enabled` field. The old-side canary then reported it disabled. The same interpretation could enter the pre-cutover route record and influence handback. A listing with an unreadable URL could also be mistaken for an absent webhook and trigger a second registration.
2. The deploy kit and canary share `heldHook`. It checks that every row has an absolute HTTP(S) destination and matches the normalized HTTP endpoint, including equivalent default ports and omitted request fragments. It retains the duplicate check, and requires the matching hook to have a nonempty string ID and a boolean state. An unrelated hook only needs a readable URL for selection. The existing repair of a matching hook's event subscriptions is unchanged. E2B's [WebhookDetail contract](https://github.com/e2b-dev/E2B/blob/c4bab34e85a82cf55bbec5ce89d91d1abf299b1a/spec/openapi.yml) requires all three fields.
3. Through the canary entry point a missing state on the old side now fails the E2B check with exit 11. Through the lifecycle update path, an unreadable identity or state stops after the listing and before any write. Both regressions failed on main with synthetic vendor responses. The deploy and handback harnesses exercise the same reader.
4. Platform typecheck and the deploy workspace passed on Node 24 with 287 tests passing and one skipped. An independent ten-case replay also verified normalized duplicates fail. Local simulations of applied routes and handback both stopped before any provider, Worker, KV or route mutation on a malformed state. Neither vendor access nor a real route operation was involved.
