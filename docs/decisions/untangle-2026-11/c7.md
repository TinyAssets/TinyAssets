# C7 as built (2026-11-14)

1. **The inbound door's answers are the contract's codes** (d3 "D2 as built" item 3, lane C then D, both halves here: the doors half is one file and a type). `contract/src/refusal.ts` gains, under "The inbound door's":
   - the door's own: `too_large` (`413`), `too_many_headers` (`400`), `event_identity_required` (`400`), `invalid_signature` (`401`) and `inbound_app_unconfigured` (`503`, `Retry-After: 5`, transient);
   - the object's refused answers (`InboundAnswer`, `owner/src/inbound.ts` `inboundRefused`): `mailbox_full` (`429`, `Retry-After: 5`, transient), `event_conflict` and `agent_unavailable` (`409`), and `too_large`, the same code as the door's. D2 named only the `retry` answer's wait; the door's `too_large ? 413 : 409` picked the other two statuses itself, so they take codes too, or the door keeps a status of its own.
   - Both waits are `INBOUND_RETRY_S`, one value: how long an inbound sender waits before it delivers again.
2. **`InboundAnswer`'s refused `error` is a `RefusalCode`,** so the object and the door share the codes by type, not by spelling. The door answers it with its code's status and `Retry-After`, the answer itself as the body; to a shared app a terminal one is a `200`, a transient one its status and wait (as the object's `retry` answered before). The door no longer reads `retry`.
3. **The wire is byte for byte the same,** every status, body and `Retry-After` (the four recorders, base against head, are identical). So no outside sender sees a change: Slack reads the status class (2xx, or a failure it retries and counts against the app's budget, `n1-inbound-door/design.md` §5) and the URL challenge's body; a capability URL's sender reads the status, `event_identity_required`'s `400` among them, as the n1 design states it to senders.
4. **The one behaviour change, the reviewer's:** a shared app's thrown transient refusal (`asShared`: a full pool's `busy`, the object's `storage_busy` or `unavailable`) was a `200`, so Slack took the event as delivered and it was lost; it is now its code's status and `Retry-After`, as the object's transient answer already was and as `n1-inbound-door/design.md` §5 states ("admitted delivery during maintenance … retryable 503"). A terminal refusal stays a `200`.
5. **Left, each with its reason:**

   - **Lane D, with research first:** a capability URL's sender gets two refusal bodies: `{error}` for the door's own and a thrown refusal, and the object's answer (`{state: "refused", error, retry?}`) for an answered one. One rule for both changes what outside senders see, so it is decided from their research, not here.
   - **Lane D:** `invalid_signature` and `inbound_proof_invalid` are both "a sender's proof fails" at `401`, one the platform's signing secret at the door, one the owner's held proof at the object. One code for both changes a shared app's body; it waits with the item above.
