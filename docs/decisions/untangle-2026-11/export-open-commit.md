# Opening an export at the session limit

The owner selects or opens the generation, retires expired sessions, and makes room for the new reader in one quiet WriteGate unit. That unit preserves work done before a refusal. If a replacement insert fails, the previous reader loses its session and its generation can lose a retention pin. A failed first export can also leave a newly opened generation without the reader that requested it.

The initial owner export now commits these SQL changes together in a nested transaction, before scheduling the generation and reading its first page. A successful open keeps the existing session limit, ordering and expiry. The old reader remains resumable when the replacement's SQL fails. The nightly and restore capture paths own their distinct operations. A first-page response lost after the commit remains ambiguous to the client.

The normal owner export handler, its WriteGate, the real backup and export stores and all eighteen migrations were exercised with a temporary SQLite database on Node 22 and 24. Main f934871ad and local combination 23361076e retained fifteen existing readers and started one capture after a forced session-insert failure. On 0f8873a20 all sixteen existing readers remained, with no capture. A successful retry on each tree left sixteen readers and one capture.

The Doors NDJSON stream's first call reads a page before it can send a cursor. On both main and 0f8873a20, a synthetic Files read failure after the opening commit followed by one fresh request consumed two of the sixteen slots for the same generation. A prior cursor is resumable only if the client received it. The app's planned export needs to distinguish that uncertain first-page outcome from a continuation, particularly when opening at capacity.

On 67fa3d9c9, four owner Worker cases passed for interruption, joining a running generation, garbage grace and nightly pin retention. The same interruption case on f934871ad lost the old reader. The scoped Node 22 typecheck passed. With two finished generations, the oldest protected timestamp moved from two days ago to one hour ago after a failed insert on f934871ad and 23361076e. It held at two days on the correction, on both Node 22 and 24. Moving the transaction into the reader store alone kept all sixteen readers but stranded a capture. Moving it into generation selection alone stranded a capture and lost a reader.
