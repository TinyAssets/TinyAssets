# r8-erased-orphans as built (2026-11-17)

Lane R's PR on #5667's review finding: an owner whose old namespace was never adopted, then erased, came back from the old one in a recover after an account's loss. Researched first, as its own step (Fact 14), on `origin/main` at `dcfd9df87` (#5667 merged).

1. **When an owner gets a new namespace, and what becomes of the old one.**
   - An object makes its namespace once, on first use, only while it holds none (`owner/src/files.ts` `ns()`, `space()`); a restore's begin adopts a generation's namespace only into a pending, empty object that holds none (`adoptSpace`). No other code changes `file_space.ns`.
   - **Restore.** A wipe (`restore.wipe`) empties the object, and its begin is held to the wiped record's own namespace (`wipedFor`), so a restore into a live owner keeps its namespace. A lost object's restore adopts the namespace of the generation it is begun from: its own.
   - **Import.** The import makes the owner's namespace at its first put. Its discard deletes it (`Erasure.discard`, `deleteNamespace`) with its mark; a run again makes a fresh one. The old one is marked, so nothing brings it back.
   - **The R7 rotation.** It rewraps the data key in place (`dataKeyRewrap`): the namespace is the same.
   - **Where a second namespace begins today** (so #5667's review is refuted: the lost-object path is not the only source, and these paths are on `main` now):
     - `recover` (#5667) writes every unmarked namespace with a root, then locates and begins each. An owner who signed up in the new account before the run is live, so its begin is refused (not empty). Its old namespace is written into R2 and no object names it; the owner's first file write makes a new one. A run stopped or cut short before its begins, with sign-ups opened meanwhile, does the same for every owner not yet begun. The checklist said "`restore` with its generation takes it (its pin and wipe)": wrong, since `restorePin` takes only one of the object's own finished generations and `wipedFor` only the object's own namespace.
     - `owner.admit` (the operator channel, and the kit's mode `owner --act admit`) admits a pending object whatever the directory says. On a lost object, or on one wiped for a restore that never began, it gives the owner a fresh, empty object, whose first write makes a new namespace. The old one keeps its roots. Sign-in never does this: it admits only an owner the directory has no record of.

2. **Can an un-adopted namespace survive with its root, for how long, and who deletes it?** Yes, for good. Nothing deletes a namespace's prefix but an erasure or a discard of the object's own namespace (`deleteNamespace`); the sweeps (`sweepManifests`, the restore's chunk sweep, garbage collection) each act on the object's own namespace. The nights keep it in the copy as long as R2 holds it, so it is kept there for good too: `KEEP_DAYS` only runs from a hide. When the owner is erased, only the namespace its object names is marked and deleted. The old one's bytes outlive the erasure in R2 and in the copy. That is the finding, and a gap in the erasure itself even with the account intact.

3. **Which readers bring it back.**
   - **`recover`:** yes, the finding. After the account's loss the old namespace is unmarked and holds a root, so it is written, located to the erased owner and begun.
   - **`copyBack`:** no. It writes only the namespace the owner's own object names (`restore.source`), and the doors refuse an erased owner first.
   - **The drill:** writes nothing, but counts the old namespace as a recover would write it. Its count is `recovered`, the one rule, so it moves with recover's.
   - **`locate`:** answers the owner and writes nothing. It is how recover finds the erased owner.
   - **The lost-object path (`untangle/r8-lost-object`, not built):** it will meet the same case, with the account intact.

4. **The options.**
   - **A. The erasure marks every namespace the owner ever held, read from where they are recorded. Chosen, with the record kept in the bucket, under the namespace that holds it.** The owner's namespaces are recorded in only two places: the object's `file_space.ns`, which is one namespace and is lost with the object, and each generation's sealed header, which only a full scan of the bucket finds. So the flow that meets a second namespace records it, as the bucket holds it: the hold `o/<ns>/h/<held>`, empty, under the namespace the owner's object adopted. It outlives the object and the account, because it is under the holder's prefix: the copy carries it, and copy back and recover write it back with the holder. The erasure's mark and delete read it.
   - **B. An un-adopted namespace deleted or marked when the new one is adopted. Rejected:** the object that makes a new namespace does not know the old one (a lost object knows nothing), and deleting an owner's only backup when an operator admits or restores it would be an irreversible act on real data. The part of B that holds is used: the path that makes the second namespace knowingly is closed (item 6).
   - **C. `recover` refuses an owner that a marked namespace and an unmarked one both name. Rejected:** a mark carries no owner, and an erased namespace's roots are gone from R2 and, `KEEP_DAYS` after the hide, from the copy, so nothing could tell whose the mark was. A mark naming its owner, whether plain, hashed or sealed, would keep an erased person's identifier off the account for good: plain or hashed it is testable by anyone holding the copy; sealed under `FILES_KEYRING` it must be resealed at every rotation, or fail closed and stop every recover after a `retire`.
   - **D. A namespace derived from the owner (an HMAC of the owner id). Rejected:** the mark would then be a keyed pseudonym of the erased person, kept for good, and the discard's mark would bar the owner's next import, which takes the same namespace.
   - **E. `recover` refuses a new account that already holds owners. Rejected as the fix:** it refuses before writing, but a run cut short and sign-ups opened after it still leave every owner not yet begun with a second namespace. The checklist now says to keep the gate closed until recover begins every owner, as defence in depth.

5. **The hold (`contract/src/files.ts` `HOLDS`, `heldNamespace`; `files/src/keys.ts` `holdKey`, `holdPrefix`, `listedHold`; `files/src/index.ts`).**
   - **Its writer:** `holdNamespace(ns, held)`, made once (`etagDoesNotMatch: "*"`), never of the namespace itself. It holds nothing, and its name is two random namespaces, so like a mark it holds no person's identifier. It is the one other object the files Worker does not seal.
   - **The mark:** `markNamespace(ns)` marks `ns` first, before any list, as before (the crash test holds this), then each namespace it holds, and each those hold, once each (a set, so a cycle ends). The erasure's start marks them all, so the one-night window of `r8-account-loss.md` item 6 covers them too.
   - **The delete:** `deleteNamespace(ns)` marks, then deletes each namespace it holds as a whole, then its own chunks and manifests, and its holds last, so a delete cut short finds them again.
   - **Only its owner's object asks it,** through a restore door (item 6). It first holds the generation to its own owner as a begin does (`ownGeneration`, factored out of `restoreBegin`), so no owner can hold another's namespace and have its erasure delete it.

6. **Who writes a hold, and the closed path.**
   - **`restore.hold {namespace, gen}`** (`restoreHold`, a reserved admission door; its operator op). It refuses an object that takes a restore (that one adopts the namespace through its begin), a namespace that is the object's own, and a generation of another owner's. The doors refuse an erased or erasing owner first. It makes the object's own namespace if it has none (`Files.holdNamespace` → `space()`), and answers `{namespace, held}`. Asked again, it answers the same.
   - **`recover`:** each begin refused or unanswered is followed by a hold of that namespace, asked of the same owner. The run still stops loudly, naming each, and says whether it was held: "held by the owner's own namespace, so its erasure takes it, and not restored", or why not.
   - **`owner.admit` (`doors/src/authorize.ts` `admit`)** refuses an owner the directory records whose object is pending: its state was lost, or a wipe emptied it, and a mode `restore` brings it back. That closes item 1's second path. Sign-up never reaches the check: it admits only owners the directory has no record of, so it costs no extra call. After a restore is done the object is admitted again from the generation, so the kit's final `owner.admit` passes as before.

7. **How a recover of the whole bucket reads the holds (`deploy/offsite.ts` `recovered`, one rule for `recover` and the drill).**
   - **Left out:** a marked namespace, and every namespace a left-out one holds, transitively. A hold whose holder is marked is taken as marked, which covers an erasure cut short between its marks.
   - **Written, not located:** a namespace another written namespace holds. Its owner is the holder's owner, whose restored object holds it again, so its erasure deletes it. Two namespaces naming one owner where one holds the other are therefore no longer the two-to-one stop. Two that neither holds still are.
   - **A namespace held only within a cycle** of written namespaces, which no begun namespace reaches through holds, would be named by no object, so the run stops before writing anything. No code makes a cycle today: an object never adopts a namespace it holds.
   - `copyBack` writes back the namespace's holds R2 lacks (`referenced`: `h/<held>`). They name no row and only add to what the owner's erasure deletes.
   - The drill's line counts those held by another.

8. **Left, each with what fixes it.**
   - **A restore of a live owner from a namespace it holds** (the owner who signed up before `recover`). Its old data is held, so it is safe, but it is not restored. Owed to `untangle/r8-lost-object`, which chooses among an owner's namespaces (`tasks.md`).
   - **An owner erased between a recover cut short and its run again**, after sign-ups opened against the checklist. The run again locates the old namespace to an owner the doors refuse as erased, so neither begin nor hold runs: the run stops naming it, and the namespace stays in R2 unmarked. A second account loss would then restore that owner. Fixing it needs a platform-side erasure of a located namespace whose owner is erased, which the lost-object path needs for its own located namespaces too: owed to `untangle/r8-lost-object` (`tasks.md`).
   - **The lost-object path** must hold every other located namespace that names `--owner` under the restored one: on its `tasks.md` line.
