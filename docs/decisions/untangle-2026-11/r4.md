# R4 as built (2026-11-14)

R4 is lane R's fourth PR, the off-account copy (d3 §G; `operator_research.md` §4, adopted whole). The files are sealed under each owner's data key since R1, so the copy carries ciphertext alone. Restore from the copy, and its monthly drill, are lane R's eighth PR.

1. **The copy is a module of the deploy kit, `deploy/offsite.ts`, run by one workflow, `offsite-copy.yml`.** The research names one workflow file and no platform code. Three things need code:
   - the files bucket's name, which `deploy/facts.ts` reads from the files Worker's config (`FILES_BUCKET`, which `IMPORT_NAMES` now reads too). A literal in the workflow would copy it;
   - the nightly holds of item 3, which read Backblaze's API;
   - tests of both states, dark and configured.

   It uses the kit's own `Io` and facts. It is not a kit mode: `platform-deploy.yml` is dispatched by hand, and a schedule there would run the deploy's jobs every night.
2. **Dark until all seven settings are stored, then loud.** The settings are `OFFSITE_BUCKET` (a repository variable) and the six `OFFSITE_*` secrets of research §4.5. The workflow has two jobs.
   - `settings` checks out and runs `offsite.ts settings`, which installs nothing. With none of the seven, it prints a `::notice` and a summary saying "not configured", writes `configured=false` and passes.
   - `copy` runs only on `configured == 'true'`.
   - With some of the seven, or one out of shape, `settings` fails and names them. Once configured, any error fails `copy`.

   The repo's one scheduled recovery workflow, the old stack's `dr-drill.yml`, is red on purpose while its off-region store is missing. The founder asked for the opposite here: a dark night is green and says so.
3. **Each night holds the keys and the bucket before rclone runs** (`held`). This goes beyond the research, which leaves these to the founder's steps and one live probe. Anything else stops the night with nothing copied, so a key made in the web form with `deleteFiles` can never write.
   - Each key's `b2_authorize_account` must show exactly its capabilities, on the one bucket, with no name prefix.
   - The read key's `b2_list_buckets` must show the bucket private, with Object Lock in compliance mode for `KEEP_DAYS`, and one lifecycle rule over every name: `daysFromHidingToDeleting` equal to `KEEP_DAYS`, and nothing hidden by age.
   - The read key gains `readBucketRetentions` over the research's list. Backblaze shows a bucket's lock only to a key that holds it.
4. **`KEEP_DAYS` is derived from the erasure's window, which moves to the contract.** `RECOVERY_WINDOW_S` was `owner/src/erasure.ts`'s. Both the erase answer's `complete_at` and the copy now hold it, so it is in `contract/src/limits.ts`, and `KEEP_DAYS = RECOVERY_WINDOW_S / 86_400 − HIDE_NIGHTS − 1`, which is 22. A longer copy can't be configured without the erasure's promise changing in the same place.
   - **How an erased owner's data leaves the copy:** the wipe deletes every object under the owner's namespace from R2 (`owner/src/erasure.ts` step 4). The first night that passes hides each object in B2. The lifecycle deletes each hidden version 22 days after it was hidden. Its daily pass adds at most a day. The lock never outlasts that: it runs 22 days from the upload, which came before the hide. So the last copy goes by the wipe plus `HIDE_NIGHTS` (7) plus 23 days, inside `complete_at`.
   - **Why a week of slack (R4's review).** As first built, 28 days left none: the first night's lag is a day plus GitHub's schedule delay, so even a green week could overrun by hours, and each red or dropped night by a day. Worse, `--max-delete` stopped the sync after a tenth of the copy, so erasing any owner holding more than a tenth (most owners, at five) left every night red, hiding a tenth a night, until someone dispatched `max_delete`. So the deletion limit no longer holds a hide back (item 8), and the hide has a week, which R6's canary guards by alarming past two nights without a pass (its line in `tasks.md`). The spec's erasure scenario names the copy.
5. **What the copy holds: the files bucket, and nothing else.** That bucket holds every chunk, and every generation's base parts, log segments and root (`files/src/keys.ts`).
   - Each object is AES-GCM under its owner's data key, with the object's R2 key as the seal's additional data.
   - A root's clear fields are its format, version, generation id and the data key wrapped under `FILES_KEYRING`. Namespaces and chunk names are random hex.
   - So no plaintext and no usable key leave the account. Not copied:
     - the keyrings, which stay in the Workers and in `production`;
     - the control record (KV; its dark form is `deploy/control.json`, and mode `control` sets the rest);
     - the directory and the OAuth store (KV; after an account loss, owners sign in again, research §4.6);
     - the operator log;
     - the final backup's bucket.
6. **The layout is the one restore reads.** Every object is at its R2 key, byte for byte, at the bucket's root, and only from the one bucket. That is because the seal binds the key: an object copied back to any other key won't open. A restore is a byte copy of `o/<ns>/` back to the same keys. An older generation is read with rclone's `--b2-version-at`. Restore itself is lane R's eighth PR.
7. **The check is one-way, as of the run's start.** The research checks that both listings agree in count and bytes. Owners write and the sweeps delete while the copy runs, so two listings taken a minute apart can differ honestly. So:
   - `rclone check --one-way --size-only --min-age <start>` holds every object R2 held when the run began to be in the copy at its size;
   - 16 of those objects are downloaded from both sides with the read key and compared byte for byte;
   - both sides' counts and bytes go to the job summary.
8. **A night that hides more than a tenth of the copy (at least 100) fails, after hiding them all.** The research asks for `--max-delete` with "a set number", which stops the run. A fixed number would stop normal nights as the bucket grows, so the limit scales with the copy. It is not `--max-delete`: a stop holds an erasure's hides back past its window (item 4), and protects nothing the lifecycle doesn't, since every hidden version stays `KEEP_DAYS` and neither key can change the rule. So the night counts what it will hide (the copy's names R2 no longer lists, before the sync), syncs whole, checks, and then fails loudly past the limit. There is no dispatch override to log or guard.
9. **`--use-server-modtime` and `--fast-list`.** An object a Worker wrote carries no rclone time, so without the first flag rclone would ask R2 for each object's metadata every night. B2's backend ignores the flag (rclone 1.75.2 source, `backend/b2`) and keeps the time each upload is given. A root rewrapped by a rotation gets a new time, so it is copied again.
10. **rclone 1.75.2, pinned by its release zip's SHA-256,** checked before it is unzipped. 1.76.0 is eight days old, under the two weeks a pin waits. Each credential is defined in one rclone call's environment as `RCLONE_CONFIG_<REMOTE>_*`, and only for the remotes that call reads. None is an argument, and rclone reads no config file.
11. **The R2 read token has no IP condition and no end date,** unlike the import's. GitHub's runners have no fixed address, and the token is used every night. It reads ciphertext alone. A restore mints its own write key for a day (research §9 step 4).
12. **Nothing spends on merge.** Until the founder's steps (`founder_batch.md` item 3; `checklist.md`, "The off-account copy"), each night checks out, reads its settings and stops. Backblaze bills only once the bucket exists.
13. **For R8 (restore from the copy): erasures must be applied after any restore from it.** The erasure's tombstones (the object's `erased` admission row, and the directory's erased `o:` record in KV) are not in the copy. A restore after an account loss that reads older versions (`--b2-version-at`) can bring back an owner erased within the last `KEEP_DAYS`, chunks and a root holding its wrapped key. R8 must apply every erasure the copy can't show: from a record that survives the account (for example, erasures listed outside it) or by refusing any namespace whose owner is erased, before any owner is restored.
