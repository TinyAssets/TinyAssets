# O2b as built (2026-11-16)

B4's contract half (`o2.md` item 9; d2 B4; `tasks.md` §10, `untangle/o2b`), first part: the doors' view of the owner object, `OwnerDoors`, written by `npm run generate` from the door table, and the services guard's door checks become type facts. The table's split into `contract/doors.json` and `owner/doors.json` is the second part, `untangle/o2c`.

## The plan (research, before building)

**What is there.** `OwnerDoors` (`contract/src/owner.ts`) is 220 hand-written lines: 93 of the table's 134 doors, each with its binding, its request and its answer. The services guard (`contract/guards/services.test.ts`) holds it to the table by parsing it: every method a row, its arity its row's (a binding but on the two unbound doors, a request where the row takes one), and its request `Asked<"door">` or `Handed<"door">` of its own row. It also pins the count of those requests (51), and `doors.test.ts` pins the admission class's doors by name, so a new door edits both guards (R8's #5653). The generator (`contract/requests.ts`) already writes `requests.ts` and the owner's `door-map.ts` from the table, and `ci/guards/generated.test.ts` holds both current.

**What a generator can write and what it cannot.** From the table it knows each door's name, whether it binds (`UNBOUND_DOORS`), whether it takes a request and which fields (`args`), and its tool's description. It cannot know what the doors build into a field (a value type), what they read of an answer, or a loose door's request type: those are TypeScript the table's JSON cannot hold. They are what the hand-written methods add today, door by door.

**The shape chosen.**
1. **`contract/src/owner-doors.ts`, generated:** `OwnerDoors`, one method for each of the table's doors, its doc its tool's description. Its parameters follow from the row: the binding but on an unbound door; no request (`none`), an optional one (`omitted`), the row's fields (`DoorRequest<"door">`), or a loose door's own parameters (`DoorLoose<"door">`, a tuple). Its answer is `DoorAnswer<"door">`. So every door's name, arity and request are the table's by construction, and the services guard's parse of them goes.
2. **`DoorTypes`, hand-written in `contract/src/owner.ts`:** what the table cannot say, only for the doors that need it, keyed by door: the values the doors build into its fields (`values`), that the doors hand a parsed body on (`handed`), a loose door's parameters (`loose`), and the answer the doors read (`answer`). A door with no entry takes its row's fields, typed `unknown`, and answers `object`. A key that is no door is refused by `tsc` (`TypedDoors`, in the generated file).
3. **Every door is in `OwnerDoors`,** not the 95 the doors call: a table door the doors call by name (`tools.ts` `callDoor`), or the doors' tests through `ownDoor<T>`, is typed by its row too. T2b's "answers typed from the contract" (`t2.md` item 10) builds on this.
4. **The guards that pinned door lists by hand go:** the services guard's name, arity and request checks, and its count of 51 (type facts now); `doors.test.ts`'s list of the admission class's doors, which `doorProblems` already holds by rule (the class `admission` exactly on the reserved and erasure callers). A new door then edits the table, and `DoorTypes` only if the doors build its values or read its answer.

**Departures.** d2 B4 wrote `OwnerDoors` into `contract/src/owner.ts`; it is its own generated file, since a generated region in a hand-written file is what O2 avoided for the object. d2 also kept `OwnerDoors` to the doors' calls; every door is in it now (item 3).

**Size, and the split.** The generated file is about 700 lines, `DoorTypes` replaces the hand methods, and the generator and guards change by about 200: about 1,100. The table's split rewrites every one of 134 rows in two JSON files, and the readers of the runner's steps (the runner, the write-gate and policy-boundary guards, the recorders, the tests, `ci/gate.ts`): over 1,000 more. So the split is `untangle/o2c`. The two do not depend on each other: the generator reads only the contract's keys (`door`, `args`, `tool`) and `UNBOUND_DOORS`.

## As built

1. **`contract/src/owner-doors.ts`** is written by `contract/requests.ts`, beside `requests.ts` and the owner's `door-map.ts`: `OwnerDoors`, all 134 doors, each its row's (the binding but on `UNBOUND_DOORS`; no request, an optional one, `DoorRequest<"door">`, or `...request: DoorLoose<"door">`), its answer `DoorAnswer<"door">`, its doc its tool's description. `TypedDoors` holds `DoorTypes`' keys to the doors: a key that is no door fails `tsc` (mutation: a `fileProbe` entry, refused at `owner-doors.ts`). The review added that it holds each entry to its row: `values` and `handed` only on a field list, `values` only of the row's fields, `loose` only on a loose door (mutations: each refused at `owner-doors.ts`).
2. **`DoorTypes`** (`contract/src/owner.ts`) holds what the 93 hand methods said beyond the table, for the 67 doors whose methods said more than their row: `values`, `handed`, `loose` (a tuple: `wakeEvents` keeps its optional command center) and `answer`. It was derived from the hand methods by a script, so no door's type changed. The other 67 doors take their row's fields and answer `object`.
3. **`contract/services.json` names each class's contract as `<module>#<interface>`,** as it names the queues' messages: `OwnerDoors` is no longer in `contract/src/owner.ts`, which the binding types (`ci/kit/types.ts`) took from the Worker's folder. Each Worker's generated `env.ts` is unchanged but the doors', which imports `OwnerDoors` from its new module.
4. **`registerPropose`'s handler takes `Readonly<Record<string, unknown>>`,** not the card's `Fields`: `OwnerDO implements OwnerDoors` now holds every door, and a request narrower than its row's fields (`unknown` each) is neither a subtype nor a supertype of them. The card checks the fields' values itself (`Registrations.file`).
5. **Guards retired:** the services guard's `ownerDoors` and `doorProblem` and their test (each name a row, its arity, its request its own `Asked` or `Handed`, and the count of 51), and `doors.test.ts`'s hand list of the admission class's doors. The class rule (`admission` exactly on the reserved and erasure callers) is `doorProblems`' already, and a new door no longer edits either guard.
