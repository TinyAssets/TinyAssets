# r-restore-schema as built (2026-11-15)

A restore took only a generation of the object's own schema (`restore.ts` `restoreBegin`), and its schema was checked only at begin, so a migration landing under a restore under way left its later steps loading the old schema's lines into the new tables. Every owner's kept generations, and every version the off-account copy holds, were unrestorable after the next migration. This PR builds the research (`rschema_research.md`, Fact 14) as the coordinator decided it: option A, with option C's parts folded in. It folds in `untangle/r-restore-migration`, and corrects `r5r.md`'s "Not built: another schema".

1. **What a generation of an older schema needs is permission, not a transform.**
   - Migrations 10 to 16 change no exported table. They touch only `owner_restore`, `restore_rows`, `owner_backups`, `owner_backup_state`, `restore_filter`, `log_staged` and `log_capture`, none exported. `export.ts` has added only `NOT_EXPORTED` entries since migration 9. So a generation of schema 9 to 15 holds the lines a schema-16 one would.
   - **Migrations 7 and 9 can't be replayed from a generation.** Migration 7 re-keys `collection_history` by `rowid` order, which no generation holds. Migration 9 computes exported columns from `ledger_receipts` and the parent message: other tables' rows. So the floor is schema 9. Below it the platform was dark and no real data exists (`tasks.md`: the dark redeploy is still owed), so the floor costs nothing.
2. **Each migration declares its forward form** (`schema.ts` `FORWARD`, one entry a migration). Null means the migration changes no exported table, so each line is the same line after it. A string is why no generation from before it can be brought forward, in the words a restore refuses it with. Entries 1 to 9 are one shared refusal, 10 to 16 are null.
   - `unforwardable(schema)` judges a generation's schema: null from 9 to the code's own. A newer one is refused ("code older than its data never loads it"); an older one is refused with the refusing migration's own words and number. The floor is derived from the last refused entry, never stated.
   - **Where the bringing-forward happens: `rowOf`** (`restore.ts`), the one function every line passes: index's spans, the log's staging, apply's and check's base rows. Staged rows are stored brought forward, so the log's rows are read at the current schema. Today the form is the identity, so `rowOf` does not change. Not on the staging tables (base rows stream from R2 and never reach them), and not in a scratch schema (one database, migrated to N on every wake; it would double the owner's storage, and still replay 7 wrongly).
   - **The future form, decided now and built by the first migration that needs one:** `forward(line) => line | null`, pure and per row. It may rename a table, drop a dropped table's line, and add the columns its migration adds, computed from the row alone. It must not change a table's key columns or their values. That PR freezes a fixture of the old schema's lines, written by the code before its change, and adds any widening to the room `LOG_BYTES` is derived from. A migration with no such form is declared refused.
   - **The staged count** keeps counting each line's bytes as its object holds them, before any bringing-forward: the capture's measure, so the pin's judgment and the log step agree for any schema.
3. **The guard** (`owner/guards/migrations.test.ts`):
   - one `FORWARD` entry a migration;
   - a null entry's migration text names no exported table (`\b<table>\b`);
   - generations are brought forward from 9 to the code's schema, and none before or after;
   - the export's shape (`exported()`'s digest) pinned with its schema count, so the export changed with no migration fails it. That was a hidden link: two readings of one schema number. Each new migration pins it again.
4. **The record keeps both schemas** (migration 16): `owner_restore.schema`, the object's when the restore was begun, and `source`, the generation's. `restoreBegin` writes both on its insert and its upsert; the pin's upsert clears them.
5. **A migration landing mid-restore fails it, loudly.** One check in `piece`, right after the record is read: at any step under way (a step with a next, `index` to `clear`), a record whose `schema` is not the object's moves to `failed`, in a `still()` unit, with "a migration landed while it was under way: begun at schema s, this object's is n; wipe it and restore again, from the same generation".
   - **Why not re-stage:** the wake's migration has already run over the half-loaded tables, so the object holds neither generation's state. Undoing that is the wipe, which is operator-confirmed and resets the instance by design. A self-wipe in `piece` would be a second wipe path. Migrations come with deploys, so this is rare, and it costs one re-run.
   - Item 1 is what makes the re-run work: the same generation begins again under the new schema. That also makes migration 15's frozen words ("wipe it and restore again") true.
   - `pinned` and `wiped` need no check: at `pinned` a fresh generation cut by the migration is given up and begun again (`backup.ts`), and at `wiped` begin checks the header itself. A `failed` record is wiped as before.
   - **Migration 16 records a restore under way as begun at 15,** so its first piece fails it through the same check. That replaces migration 15's pattern of a failure statement per migration.
6. **The wipe at `pinned` refuses** while the pinned generation or its `fresh` undo is not `restorable`: "generation g can no longer be restored: release the pin, and pin one restore.source names restorable". The live owner stays held, and `restoreRelease` gives it back. This covers the window between the fresh generation finishing and the wipe (`rmig_plan.md` §2.3), where a migration since could refuse a schema, or a generation could stop being whole.
7. **`restorableAt` checks the schema** (`backup.ts`): `unforwardable(row.schema) === null`. Through `restorable`, that covers `restore.source`, `restorePin`, the fallback and the `lost` telling. A null entry leaves every generation restorable, so it adds no noise; only a migration declared refused makes the owners' generations unrestorable, and then the owner is truly told none can be restored.
8. **`adopt` records the generation's own schema** (`held.source`), not the object's, which was false for an older one. `backup.ts` now imports `MIGRATIONS` from `schema.ts`, as `restore.ts` does, and `BackupParts.schema`, a pass-through of `MIGRATIONS.length` from `owner-do.ts`, goes: one route to the code's schema, not two.
9. **Export and import.** The export door ships a generation's objects verbatim, and its header names the schema; its reader is outside the platform and loads nothing, so it needs no bringing-forward. The off-account copy is a byte copy back to the same keys (`deploy/offsite.ts`), which `restore.begin` then reads unchanged, so it shares item 1 exactly, and needs it more: its versions (`--b2-version-at`, up to `KEEP_DAYS`) are older than more migrations. The cutover's import writes through the object's own write path at its schema and reads no generation.
10. **The proof** (`owner/test/restore.test.ts`; `writtenAt` in `generation-support.ts`).
    - **A generation is written by an object at its schema, never relabelled.** `writtenAt` makes the owner's object again at schema s: every table dropped, that schema's migrations applied, and the exported rows put back column for column (a column the schema lacks fails it), that schema's triggers off for the put and made again after. Its base is read by the export (`readPage`) under a header of s, and its log is what that schema's own capture triggers write (a notice changed, two written, one gone), shipped as one segment (`ChangeLog.segment`), then sealed under the owner's namespace and key.
    - **Each schema 9 to 15 restores:** a lost object takes it, the check passes, the rows equal those at E, and the adopted row keeps s. At 9 the owner is production-shaped: every counter equals the source's, and the live owner then pins, wipes and restores it again.
    - **The off-account copy's path:** a schema-9 generation's objects, every chunk and generation of the namespace, read, deleted from the bucket and put back byte for byte at the same keys, restore a lost owner.
    - **Refusals:** schemas 1 to 8 and 17 are refused at begin with the named reason, nothing written. A generation recorded at 8 is shown not restorable by `restore.source`, and `restorePin` refuses it. A refused begin reads only part 0's header, so these generations are their header alone.
    - **A migration mid-restore:** at each step from `index` to `clear`, a record begun at 15 fails on its next piece with the words, no table's count moved; the operator's wipe by the failed restore's words follows, and the same generation is begun again, to done, the rows equal.
    - **The wipe at `pinned`** refuses when the pinned generation's, or the fresh one's, row is at schema 8; the owner stays held, and release gives it back.
    - **A crash mid-bringing-forward:** there is no separate step to crash in, so the existing crash-at-any-read test now runs on a schema-9 generation of the production-shaped owner.
    - **Migration 16's map:** a migration-15 record at each step from `index` to `clear` maps to `schema` 15 and fails on its first piece; at `pinned` and `done` it stays null. The migration-15 map test now migrates to 15, its subject.
    - **A stale fixture:** `storage.test.ts`'s `generation` recorded each row at schema 1. A schema-1 generation is rightly no longer restorable, so the fallback test lost its fallback. The fixture now records the object's schema.
    - **Mutations, each failing its test:** begin taking only its own schema (the six of schema 10 to 15); `FORWARD`'s first nine null (the refusal); no check in `piece` (the mid-restore test); migration 16 not recording 15 (its map); `restorableAt` without the schema (the pin refusal); `adopt` recording the object's schema (schema 9's); the wipe's check off (the wipe test); and a 17th migration with no `FORWARD` entry (the guard: "expected [ …(16) ] to have a length of 17").
11. **Declaring a migration refused after the cutover is the founder's call** (Fact 4). It strands every owner's kept generations and every version the off-account copy holds, and for a lost object that loss is permanent: an irreversible act on real data. A PR that needs one stops and asks.
12. **Order.** Migration 16 is unpinned here; its pin is `untangle/r-restore-schema-pin16`, after this merges. All of it lands before Step 7's dark redeploy, which then applies 10 to 16.
