# owner-state-op as built (2026-11-15)

The operator's read of an owner, owed since R2 and R3 (`r2.md` item 1, `r3.md` item 9): the doors answered `owner.state` `invalid`, so mode `owner` could not show an owner's state before and after its op. Built in the shape `owner.erase` used (`owner-erase-op.md`): one path, the signed message, the operator log.

1. **One door, `ownerState`, the platform's alone.** A `reserved` row of class `admission` (`contract/doors.json`), its `OwnerDoors` method, the object's method and its handler in `owner/src/admission.ts`, beside `admissionSet`. The doors' `owner.state` (`OPERATOR_OPS`, `doors/src/operator.ts` `OPS`) calls it through `bindPlatformFor`, as every op does. An owner's own binding there is refused `PLATFORM_ONLY` by the account step, as at every reserved door.
2. **What the state holds: names, codes and counts, nothing else.** `OwnerStateAnswer` (`contract/src/owner.ts`): the admission (`state`, `reasons`, the keys `admissionSet` answers, so a suspension's answer and the state read alike), the `tier`, the step of a restore that holds the owner (`restore`, null when none), the live runs (`runs`) and the bytes of content stored (`stored_bytes`, the one storage number's used figure). Never content, a credential, a key or route id, a namespace or a binding. The tier's storage figure is left out: the reserved binding carries no tier numbers, so it would read null; the tier names it.
3. **Erasure is answered by the refusal, as at every door.** An owner being erased is refused `erasing` by the binding check, and an erased one `owner_erased` (the channel's directory check first, the object's tombstone at its own door). No field restates either, and the state door takes no exception to the mark.
4. **A read, changing nothing, with no confirm words.** The handler is one unit that writes nothing, so the gate marks nothing changed (`gate.ts`). Asked again, or delivered again after its read and before its answer, it answers the same over the same rows (proved over every table of the object). A forged or unsigned message is dropped at the gate, nothing kept in the log, as every op's.
5. **The restore's hold is one read.** `holdingStep` (`owner/src/restore.ts`) answers the holding step; `restoring` is now `holdingStep !== null`, so the two cannot disagree. A held owner's `owner.state` answers its step, since `admission` doors skip the restore's refusal.
6. **Mode `owner`: the state before and after.** The apply job asks `owner.state`, then the op, then `owner.state`, saying each answer; a refusal of any stops the run, named, so an erased owner's run stops before its op is sent. The plan job only plans it (it holds no `OPERATOR_KEYRING`), its one line naming both reads. `--act state` is an act like the others (`OWNER_OPS` takes every `owner.` op without words), so a read-only run is `--act state`: three reads, the same answer, which is the dark check `operator_research.md` §6 asks for ("`owner` reads a rehearsal owner's state").
7. **A name nobody signed up is read as its object stands.** Like `restore.source` and every op but `owner.erase`, `owner.state` reaches the object `getByName` starts, which answers `pending`. `owner.erase` checks the directory first because an erasure bars the name; a read bars nothing, and the operator's admit of an owner the directory does not hold yet (the import's pending owners) needs its `before`.
