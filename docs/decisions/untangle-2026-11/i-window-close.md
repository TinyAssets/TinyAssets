# i-window-close (2026-11-16)

Lane R's item from the rotation driver (`r7-rotation-driver.md` item 8), decided by the founder on 2026-11-16 as option B: the window's close refuses until every bundle's owner is admitted or discarded; nothing is deleted, and an owner left behind is imported again in a later window. Researched first, as its own step (Fact 14), on `origin/main` at `1ba94beca`.

1. **What main holds.**
   - **The steps after staging** (`import/window.ts`). `verify` keeps each bundle's result in the run's record (0600, on the import host). `admit` admits none unless every bundle verified clean, and stops at the first refused admit. `wipe` asks a discard of every bundle of `out`, skipping one the record holds discarded, then deletes the run's `o:rehearsal-<run>-` records and its staging (`<run>/`), then proves each listing empty. Each step reads its run's `out` (`bundle/out`, made once and never remade, `window.sh`).
   - **The doors' consumer** (`doors/src/import/`). Every op reads the bundle's index (`<run>/<key>/bundle.json`) from the staging bucket before anything else, and an import slice writes only from what is staged. So an owner can hold imported data only once its index is staged. The admit writes the owner's `o:` record last. A discard is answered again by an object that discarded already.
   - **The kit.** `rotation` refuses while the doors hold `IMPORT_KEY` (`deploy.ts` `rotationNamespaces`), and lists the owners it reaches as the directory's `o:` keys (`OWNER_ENTRY`). No kit mode belongs to the window; the kit reads R2 objects by name only, with no listing.
   - **Step 12** (`tasks.md` §9): the doors' `IMPORT_KEY` deleted by the founder's `wrangler secret delete`, "after the admit, before `routes`" (`checklist.md`). Nothing ties that command to any check. **Step 15** deletes the window's code, queue and staging bucket; `clean` destroys a run's import host, its `out` and its record.
2. **The hazard, exactly.** An owner whose index is staged and that has no `o:` record. The rotation never reaches it, and once the window's key is gone no step can admit or discard it.
3. **The predicate.** The window may close when every bundle index in the staging bucket, of any run, names an owner the directory lists. One fact, read where it lives:
   - **admitted:** the directory lists `o:<owner>`, the listing the rotation sweeps;
   - **discarded:** the index is no longer staged. `wipe` deletes a run's staging only after the doors answered every one of its discards, and nothing else deletes it before the cutover.

   Why not the run's record and `out`:
   - The record is a receipt that goes stale. A run staged again after its wipe puts the owner's data back while the record still says discarded. `wipe` skipped that owner on the record's word, deleted the staging and proved "empty", leaving the data behind. That is a bug today, independent of the close.
   - `out` and the record are one run's, and live only on that run's host. `clean` destroys them, and one import host is up at a time, so a run cleaned before its owners settled is listed by nothing. The staging bucket outlives every host until the cutover, and holds every run's indexes. So the close needs no gate on `clean`.
4. **Where close belongs.**
   - **A job step, `close`.** Only the job holds a listing of the staging bucket (the window's R2 pair, pinned to the import host's reserved IP) and the directory's listing. So it runs on an import host, as `window.sh close`. It reads; it writes nothing. It refuses (exit 3), naming each owner left by run and bundle ordinal (stdout holds no owner's name or key), or passes.
   - **Step 12's key deletion follows from the pass, in the same dispatch.** The workflow's next step deletes the doors' `IMPORT_KEY`, for the real window alone, and only after the host's `close` passed. The key is then deleted by nothing but a passing close. `rotation`'s existing refusal while the key is held becomes "no rotation before the window closed", with no new record. The founder's `wrangler` command goes. A rehearsal's close only checks, since the window needs the key after it.
   - **The token.** Deleting a Worker secret needs the deploy kit's Cloudflare token (`CLOUDFLARE_API_TOKEN`). The window's own tokens are pinned to the host's IP, and none may edit Workers. The key step runs on the GitHub runner, never on the host. The token sits in that step's environment and in the dispatch gate's, which checks it is there, and never in the run step's or on the host. The job is the one built from the same checkout. That ends the workflow's rule that no deploy-kit token is read there, for this one step.
   - **Rejected: a kit mode `close`.** The kit cannot list R2. So it would trust a marker that the job writes and that a later stage must remember to delete. That is two halves joined by a file, and a gap of a dispatch between the check and the act.
   - **Rejected: the founder's command kept, ordered after close by `checklist.md` alone.** Then "the steps after close can't run before it passes" would hold by the founder's memory.
5. **Found and fixed.**
   - `wipe` skips an owner when its index is no longer staged, so a discard can't be asked anyway, rather than when the record says discarded. An owner staged again after a wipe is discarded again. An owner never staged is skipped rather than waited on for 30 minutes. A wipe killed between its discards asks the first ones again, which the doors answer again.
   - `wipe`'s `o:rehearsal-` prefix is `OWNER_ENTRY`'s, not a copy of it.
   - The job's live names carry the doors' Worker (`IMPORT_NAMES.doors`), so the key step names no Worker of its own.
6. **Left, and why.**
   - The workflow's "Destroy the run's import host" still destroys a host it cannot reach. That costs no owner now, since the close reads the staging bucket, not the host.
   - A left owner keeps the window open: the key stays and `rotation` refuses. That is the decision (B). The way on is to admit it, in this run once it verifies or in a later run that imports it again. `wipe` discards a whole run: a rehearsal's, or a real run none of whose owners is admitted. The doors refuse to discard an admitted real owner, so `wipe` stops at one.
   - The Cloudflare endpoint `DELETE /accounts/<id>/workers/scripts/<script>/secrets/<name>` is recalled, as `r7-rotation-driver.md`'s batch path is. A wrong path fails loudly, and the step reads the doors' secret listing back before it says the window is closed.
7. **The proof.** Fakes only; nothing live.
   - `window.test.ts`: close refuses with an owner left and names it, writing nothing; another run's leftover counts; it passes once every owner is admitted, and once every owner is discarded; a wipe asks again of an owner staged again after it; the key step deletes the doors' key and reads the listing back, refusing when it stays.
   - `runner.test.ts`: the dispatch gate asks a real window's close for the kit's token and a rehearsal's for none; the run step hands close the job's credentials and never the kit's token; the key step runs only after the run step's success, for the real window's close; `window.sh close` runs the job with the network, seeing the bundles alone.
