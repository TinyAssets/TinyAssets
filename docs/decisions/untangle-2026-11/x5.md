# X5 as built (2026-11-14)

X5 builds `d2` B14 as `d3` §A7 narrows it (only the platform's side of the canary, in TypeScript; the old side stays in Python until the hold ends) and as `d3` §J2 and §J3 decided R6 from the research of 2026-11-12 (`research_b13_r6.md`).

1. **The platform's canary is `deploy/canary.ts`**, run outside-in by `platform-canary.yml` and by the kit after each mode (Fact 11).
   - It reads the side from the public resource document's authorization server (`scripts/canary_handles.json`, each side's record). The old stack's side is the platform **dark**: it checks that the old stack still answers `/mcp` (a body on its anonymous `401`; the doors send none, so a `routes` stopped partway is exit 10) and that E2B holds the pinned template and the hook, disabled. Every doors check waits, named. A waiting check is never a pass.
   - The doors' side runs the research's model-free list: the challenge and resource document; `/app` and `/app?upgrade=1` with the CSP; the client document; the egress host's refusal; the sign-in's start (the doors' `/authorize` to WorkOS, then the kit's own `authorizeCheck` to AuthKit, the issuer's discovery by `upstreamFrom` and its JWKS); E2B's template and the hook, enabled. With `TA_PROBE_KEY`: the handle set (the Python's new side, ported whole), a file written, read and removed, and the full run.
   - Each check has its exit code; the first failure's is the run's. `--side` and `--unkeyed` are the Python's (`routes` asks for `--side doors --unkeyed`). The kit spawns it as its own process, as it did the Python, so the kit imports nothing back from it.
2. **One full run a day, which is the day's one sandbox boot** (§J3 decided both). It is one short `converse` turn of the canary owner's main agent on the free-tier source connected to that owner: a boot, the engine, the egress host and the model. A separate throwaway boot would spend a second boot to prove less. `converse`'s own `wait_ms` waits on the run, so the canary holds no sleep. The run's record (`/workspace/canary-full-run.json`, the owner's own file) says when it last ran and how it ended. Every run within a day carries that ending, so a failed day stays red, and the alarm's two-in-a-row rule works on it, until a full run passes. The workflow's `full` input runs it at once.
3. **The free-tier key is connected in the app, not stored in GitHub.** `founder_batch.md` item 5(b) says to save it with `gh secret set`. But only the owner's own session can connect a source (`doors/src/connect.ts`: the owner surface, its first-party token and session cookie), so the canary never could. The founder connects it once as the canary owner, and no new secret holds a model key.
4. **The clock** is `doors/src/canary-clock.ts`, the doors' one `scheduled` handler, on `triggers.crons` `*/10 * * * *`.
   - Its three secrets are optional (`contract/canary.json`): `PLATFORM_CANARY_TOKEN` and the pager's two keys. `deploy/platform.json` gives the doors `clock`, so `facts.ts` lists them among the doors' optional secrets, set only when given, as a shared app's are.
   - **No token: nothing is sent** and one line is logged. That is the clock from merge until the founder's token and a deploy, and its test.
   - A failed dispatch fails the tick (the Worker's logs hold it) and pages Pushover directly, at high priority, on the ticks at `:00` and `:30` only. A stateless page each tick would wake the founder six times an hour for one expired token.
   - `wrangler deploy` and `triggers deploy` set a schedule; a version upload does not (wrangler 4.154: `triggersDeploy` is called by those two alone). So on the deployed doors the schedule starts with `routes`' `triggers deploy`, or with the doors' first deploy. Either is harmless, since the canary itself reads the side, and a handback leaves the schedule running for the same reason. The route record does not keep it.
5. **The alarm** is `deploy/alarm.ts`, the same for every run: the clock's, the watchdog's and a run by hand.
   - **Dark until the deploy.** It acts only when `production` holds `PLATFORM_CANARY_TOKEN` (`CANARY_ARMED`, from the token's presence alone) and the doors serve `/mcp`. The existing scheduled workflows (`uptime-canary.yml`, `dns-canary.yml`, `dr-drill.yml`) start alarming the moment they merge, so none had a pattern to copy. Only `auto-enroll-merge.yml` and `okf-watch.yml` gate on a token's presence, which this follows. The canary's first run that can page is the first after the founder arms it, after `routes`.
   - A red opens the `platform-down` issue at the second red in a row (the previous completed run on main failed within 30 minutes), or at once for a stopped clock, which spans 30 minutes alone. While the issue is open, every red comments on it. Pushover's emergency page goes out on opening, then at 1 h, 4 h and 24 h, unless someone commented since the last page: `pushover_page.py`'s ladder, ported. A green closes the issue.
   - The issue and page logic is ported from `incident_issue.js` and `pushover_page.py`, not called, so the canary keeps nothing in `scripts/`, which the cutover deletes. The page form is the contract's (`contract/src/canary.ts` `pageForm`), the clock's too.
6. **The watchdog** is the workflow's own hourly schedule with `--clock`: no run dispatched in 30 minutes fails alone. The research's `workflow_run` after Platform deploy is not built, because the kit already runs the canary as each mode's last step.
7. **Workers Logs on in all six configs.** `ci/kit/config.ts` `EVERY_WORKER` holds every config to `observability: {enabled: true}`, beside each Worker's own rules. The doors' rules allow `triggers`. The owner's own checker, which is not the kit's, takes the same keys and check, and so does its hold on the Workers it binds. A version deploy syncs the setting (wrangler's `maybePatchSettings`), so logs start at the next `dark`.
8. **The manifest.** `routes`: disable `uptime-canary.yml` (a new live kind, `workflow`). `hold`: delete `handles-canary.yml` and its guard, and take the old record out of `canary_handles.json` and the dark side out of `canary.ts`. `mcp_public_canary.py` itself is the inventory's (tasks §10 step 3). It must stay until the hold ends, because `handles-canary.yml` runs it.
9. **The Python's doors side is gone.** `scripts/cutover_handles_canary.py` is deleted. `handles-canary.yml` runs the old stack's own check, `mcp_public_canary.py --assert-handles`, directly. `tests/test_cutover_handles_canary.py` becomes `tests/test_handles_canary.py`: the old record's and the image's two tests are kept, and one holds the new workflow. The kit spawns no Python, and the kit text check in `deploy/guards/canary.test.ts` holds that.
10. **Left: B14's keyring half** (`platform_setup.py` calling `deploy.ts keyring-new`). It is not the canary, and building it would make the founder's local setup need Node 22 and the platform's `npm ci` to make one keyring. So the one Python-running deploy test left is the keyring's (`deploy.test.ts`, "takes the keyring the founder's setup makes"). It is owed to the coordinator's call.
