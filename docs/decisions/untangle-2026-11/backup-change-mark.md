# Which changes start the backup retention clock

A generation stays whole until the first change since it began plus the recovery window. A rolled-back inner transaction can make an unchanged generation expire. The gate tracks whether the enclosing unit attempted a write, and SQLite rolls back the inner transaction independently of that flag. This affects restore transactions, exports and ordinary owner writes using the same gate.

The savepoint correction at e90169f1d records the previous flag on entry and restores it when SQLite rolls that savepoint back. An earlier write that survives in an ordinary outer unit still marks the generation. The original error propagates to its original caller. Main f934871ad has 60 explicit savepoint calls in 15 owner modules. Local combined 23361076e has 62 across those modules.

On both originals, an inner rollback with no surviving write made an adopted generation expire at the recovery horizon, scheduled another backup and made export open a second generation. The corrected gate preserved eligibility, left the nightly job idle and let export reuse that generation. A real earlier write preserved the existing behavior on every tree. These twelve downstream comparisons ran on Node 22 and 24 using Backups, ChangeLog and the 18 migrations. A separate fourteen-case gate replay on all three trees covered successful, rejected, nested, caught and quiet units.

## Remaining decision for committed units

The gate also counts SQL that commits without changing recovery data. On main, e90169f1d and 6cc6be8f8, the actual sign-out-all handler acting on an empty session and flow inventory returned zero. Of all 82 SQLite tables, only owner_backups changed. The generation then failed the eligibility check at the recovery horizon. Reading the same empty inventory preserved eligibility. Removing one synthetic session changed owner_sessions and the trigger-maintained policy_usage as well. Both tables, and the connection flow table that sign-out can update, are excluded from export. All three cases ran on Node 22 and 24 at each commit. The fixture entered the session handler directly. On an empty sign-out it observed one schedule sync request and one request to close signed-out sockets. Those side effects remain required. The measured recovery consequence was a change in eligibility. Physical pruning and the loss of a recovery copy were outside this experiment.

The source of the recovery projection is shared by the export and changelog. The schema has 41 exported and 41 excluded tables. Its 123 capture triggers cover the exported tables and run only during active capture. An independent comparison of every projected column ran six cases with capture off and on, on f934871ad, 23361076e and e90169f1d, using Node 22 and 24. With capture off, a same-value update, a changed exported value, an excluded tier write and a rolled-back update each incremented SQLite's total change counter by one and emitted zero journal records. With capture on, the same-value update and the changed exported value each emitted one record. Two opposite updates emitted two records while leaving the final projection equal. A delete matching zero rows emitted zero records in either mode. Counting statements, affected rows or capture events cannot establish that a committed unit changed the recovery image. The existing history rule conservatively dates unknown generations at migration. It does not settle how to handle known, unchanged images during normal use.

Before tightening the marker for committed units, establish the intended semantics for matched same-value rows, opposing writes within one unit, projected columns and direct statement failures with a surviving prefix. Verify bounded cost and compatibility on historical owners and compare the normal nightly, export, restore and pruning callers. This remains a shared backup decision. An exception for the sign-out caller would leave the same behavior in other callers.
