# What retains an offsite copy's selected generation

The R8 copy-back command asks for the owner's namespace and its current references, then copies missing chunks, holds and objects of every named generation. The actual job has a thirty-minute workflow timeout. Its final read can detect that a row retired after its first read. The runner can also lose the copy response or terminate before that final read. See the earlier local comparison on `4ad72f337`.

- The public export belongs to a live owner session. Its first page joins the writing generation, reuses the latest clean one, or opens a new one. The caller cannot select a namespace or a generation. An existing export ID on an initial request still starts a reader of the current generation. Reading another page keeps the first page's seven-day expiry. The seventeenth reader evicts the oldest, and the owner can end one earlier. The owner also prunes an unwhole generation even if a reader remains. A copy may start just before an existing reader expires.
- A live owner's operator restore can pin one explicit, restorable generation of its current namespace while its root is missing. The owner checks the saved SQL row before requesting a fresh undo generation. The hold survives caller loss and an object restart and has no timer that releases it. It blocks ordinary owner activity and stands until an explicit release or restore. Another namespace needs an independently readable root and first part proving ownership. A pending account cannot take the live-owner pin. A named finished generation over the restore staging bound also fails pin admission.
- The existing restore operation can therefore protect a single eligible source during an operator-directed restore with the owner held. The copy-back command selects an entire namespace's current inventory and identifies no single restore generation. Its second names query and the workflow timeout give the host no durable right to complete or reconcile a write after it loses its process. The namespace hold used by recovery records an erasure relationship. It does not pin a generation in the owner's backup lane.
- The signed operator channel records a distinct ask and result for each page of names. Its acceptance record binds the op, owner and args. A new copy attempt issues new asks. The offsite control record contains only kind and start time, the input to key retirement. Neither record connects a selected set of generations to the bucket writer or records its completion. The open dependency is a durable disposition for all eligible copied objects through incomplete writes, expiry and erasure. No new protocol is selected.

On main `f934871ad` and combined `b0e6e6137`, all four local Node 22/24 comparisons used the original handlers and all 18 SQLite migrations. The seventeenth export evicted the first and the real continuation preserved its original expiry. Three SQL generations were named. A single eligible older generation's missing root was never read when its restore pin was claimed. The database closed and reopened after loss of the caller, and the pin still held eight days later. A second generation was refused until release. The overweight generation, a pending owner and a missing root in a different namespace each failed pin admission. Independently signed names requests had distinct ask and receipt keys. Only local synthetic stores and clocks were used.

The same comparison found a separate public export defect. The real Files Worker code sealed a generation containing a header and three migrated rows. The Doors stream returned those lines, a cursor and an end. Taking away just the finished root left the part in the bucket but returned HTTP 200 and just the end line. Replacing the root's original bytes restored the entire stream. This holds before any rclone operation is invoked.
