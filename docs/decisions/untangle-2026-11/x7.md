# X7 as built (2026-11-14)

X7 is lane X's PR for the 2026-11-14 cross-PR re-check (`list7_recheck.md`): item 2, R4's erasure promise has no alarm, and items 5 and 6, GitHub specifics outside `deploy/actions.ts` and three GitHub request shapes.

1. **The platform canary reads the off-account copy's nights** (`deploy/offsite.ts` `watch`, the canary's check "the off-account copy", exit 15). R4 (`r4.md` item 4) keeps an erased owner's hidden copy inside 30 days only if a missed night is seen within `HIDE_NIGHTS`, and X5 built the canary before R4 asked for it.
   - It lists `offsite-copy.yml`'s completed runs on `main`, newest first, and reads each run's two jobs, `settings` and `copy` (`NIGHTLY`), until one decides.
   - **A night owes nothing** when its `copy` job passed, or when its `settings` job passed and its `copy` job was skipped: the settings job found no setting stored. A night stored in part fails its settings job, so it is red, never unconfigured.
   - **The newest night unconfigured:** the check waits and says "not configured". So does a workflow with no completed night. A waiting check exits 0 and never alarms, and is never a pass.
   - **Otherwise the newest night that owed nothing decides.** Inside `OVERDUE_MS` the check passes if that night copied, or waits for the first pass if the copy was configured after it. Past `OVERDUE_MS`, or with no such night, it fails, enough alone for the alarm, which opens `platform-down` and pages up the existing ladder.
2. **`OVERDUE_MS` is two nights and half a day (60 h),** beside `HIDE_NIGHTS` in `offsite.ts`. The half day is for a night GitHub starts late: the canary workflow's own comment records GitHub's schedules running hours late under load, and a strict 48 h would page for one missed night followed by a late one. That leaves four of the seven `HIDE_NIGHTS` to mend the copy before a hide is late.
3. **It runs on every doors-side run of the canary, not only the watchdog's.** The alarm closes `platform-down` on any green run. A check run only by the hourly watchdog would open the issue, and the next ten-minute dispatched run, which wouldn't check it, would close it: a page an hour for one overdue copy. The clock's check is different: while the clock is stopped no dispatched run happens to close its issue.
   - So the canary reads GitHub on every run, with the job's own token. `GITHUB_TOKEN` is one of the canary's `INPUTS`.
   - The kit's apply job (`platform-deploy.yml`), which runs the same canary after each mode, gains `GITHUB_TOKEN` and `actions: read`. The workflow's guard derives its env from `INPUTS`, so it holds that.
   - On the old side nothing changes: the doors' checks wait, and the copy's with them, since no owner is on the platform before `routes`.
4. **"Alone" is a failure's, not a check's.** An overdue copy already spans two nights. GitHub refusing the listing does not, so it waits for a second red in a row like any other failure. `Failure` carries `alone`. The clock's failures stay alone, its listing's refusals included. An unreachable GitHub is exit 2 for either check, and not alone.
5. **One GitHub request shape, one client.**
   - `contract/src/canary.ts` `repositoryCall(token, method, path, body?)` is the repository's REST call: base URL, `Accept`, the API version and the user agent. The doors' clock dispatch is one of them (`dispatchRequest`).
   - The kit's calls go through `deploy/actions.ts` `github()`, which reads the job's token and refuses loudly without one. Before this the alarm sent `Bearer ` with an empty token. `pages()` walks a listing, and the alarm's `all` and the copy's watch both use it.
   - The canary's clock and copy checks call it through `bounded()`, the canary's timeout-and-unreachable rule. The canary's three hand-copied error-to-`Failure` wrappers and two bounded fetches became `failingAs()` and `bounded()`.
6. **`actions.ts` holds every Actions variable and workflow command again.**
   - `output()` writes `GITHUB_OUTPUT`. `annotate()` makes `::notice` and `::error` lines, escaped as the runner reads them back (`%`, line breaks, and `:` and `,` in the title); by hand, it gives the title and the message plainly. `runLink()` gives the run's page from `GITHUB_SERVER_URL`, `GITHUB_REPOSITORY` and `GITHUB_RUN_ID`, or null by hand.
   - `offsite.ts` writes its summary, output and annotations through these. Its own `runnerFile`, which threw by hand where `actions.ts` writes nowhere, is gone. The alarm reads the run's id through `runOf` and its page through `runLink`, so a run by hand names itself "a run by hand", not `…/actions/runs/`.
7. **The retro-check: would one home for Actions specifics and one GitHub client have changed anything else built since X3?** `deploy/`, `contract/`, `doors/src/` and every script a platform workflow runs were grepped for `GITHUB_*` reads, `api.github.com` and workflow commands. After this PR, `actions.ts` is the only reader in `deploy/`, and `contract/src/canary.ts` `repositoryCall` is the one request shape. The rest are not copies of either:
   - `platform/import/host.py` (`::error::` and `::warning::`) and the shell in `import-window.yml`, `sandbox-template.yml` and `tests.yml` (`$GITHUB_OUTPUT`, `$GITHUB_STEP_SUMMARY`) are Python and shell. They can't import a TypeScript module, and they write Actions' own interface directly, which is the interface itself, not a second home for it.
   - `scripts/platform_setup.py:47` calls GitHub's app-manifest conversion from the founder's own machine, with no token. That is a different API, outside the repository's, and the setup runs without Node (`x5.md` item 10).
   - `ci/guards/locks.test.ts:56` reads `GITHUB_EVENT_PATH` to find a merge group's base. That is CI's own read, which `actions.ts` doesn't make, and `ci/` must not import the deploy kit.
