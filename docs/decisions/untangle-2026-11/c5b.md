# C5b as built (2026-11-14)

1. **What a Worker's `rules.ts` states** (d2 B8, "keeps the allow-list … drops the values the configs already state"): the keys its config may set, each binding kind's binding names (with a namespace's own classes), its secrets by name, and each value that is itself a security statement. A value whose one home is the config is not restated: a queue's, bucket's or namespace's name, a placeholder id, the build command and its rules, a consumer's batch size, concurrency and dead-letter queue. Where two configs must agree, the guard compares the configs.
   - Kept as security statements: the flags each Worker relies on (the doors now `carries` `disable_ctx_exports` and `global_fetch_strictly_public`, where they listed all four); the doors' four vars' inert values (a checked-in `DCR_ENABLED: "true"` or a real `OWNER_ISSUER` would turn sign-in on before its slice, and nothing else holds them); the doors' `assets` whole (each field is a serving mode, `directory` among them: `./src` would serve the source); codemode's `limits` (Paid's most, above code mode's interrupt budget).
   - The kit gains two rules for this: `objects` (own-class namespaces by binding, each a class of its `classes`, no `script_name`) and `queues` (producers by binding, each a binding and a queue name, and whether the Worker consumes). The sandbox's `exact` is gone (`s2:S93`), and codemode's `exact.durable_objects` became `objects`.
2. **The owner's statement about a Worker it binds is reach, and only reach** (d3 §U3). Evidence: `owner/guards/rules.ts`'s own header lists what must refuse the owner's binding, and every item is a binding (a Durable Object, a service, a queue, a workflow, a dispatch namespace, a Worker loader, a tail consumer, a shared store, an unsafe binding). None is a secret, a var or a limit, each of which binds nothing. The old `SERVICES` imported those from the four Workers' rules, so the owner restated what each Worker's own guard already holds, and through their rules.
   - **The owner's (`owner/guards/rules.ts`):** each binding's Worker, by folder; the binding kinds it may hold and how many of each (`FILES` one bucket, `GATEWAY` none, `CODEMODE_VM` one namespace, `SANDBOX` two namespaces, one KV namespace, one producer); the keys that bind nothing (`BOUND_KEYS`, now with `secrets`, `vars` and `limits`); and `RING_QUEUES`.
   - **The owner's invariants over any bound config** (`boundProblems`, read from the config, never from its rules): a namespace only of a class its own migrations make, no `script_name`, never `OwnerDO`; migrations that only make classes, so a `transferred_classes` from another script is refused; producers only onto a ring, and no consumer.
   - **The bound Worker's own (its `guards/rules.ts`):** its name, flags, secrets, vars, limits, build, class names and binding names. Each owner probe these covered (a var or secret on the gateway, codemode or sandbox, a second class made, codemode's other limits) is a probe in that Worker's own config guard already.
   - `RING_QUEUES` stays a name the owner states. Read from the producers' configs (the generated `QUEUES`), it would follow a sandbox producer moved onto the erasure queue, so the check would hold the config against itself (as d3 §U2).
   - The owner's rules import no other Worker's rules, and their four `B8` owed entries go.
3. **Corrects `d2` B8's sense of a Worker's name:** the guards name a Worker by its folder, and read its name from its config. `platformConfigs()` is keyed by folder, as `deploy/facts.ts`'s `CONFIGS` already was. The owner's `SERVICES` and the doors' `OBJECTS`/`SERVICES` name `files`, `gateway`, `codemode`, `sandbox` and `owner`, and the doors' guard reads `tinyassets-owner` and the others from their configs (`d2:N81`).
4. **The doors' cross-Worker facts are read from the configs** (`d2:N81`):
   - `OWNER_SECRETS`'s exact copy becomes `SHARED_SECRETS` (the owner declares the routing key too).
   - The `FILES`, `GATEWAY` and `EGRESS` objects become `SERVICES`, each with its Worker, entrypoint and the members it serves, written once (`CONNECT_METHODS` was written twice). Every entrypoint must extend `WorkerEntrypoint` itself, the gateway's two included (only the files one was checked).
   - The consumers are held to every queue the platform's Workers produce onto. No other Worker may bind the doors' bucket or produce onto the doors' queue. Both checks are in `doorsConfigProblems`, so the probes reach them.
   - `IMPORT_WINDOW` is the two binding names. The binder guard reads them from there, not from a copy.
5. **Left, accepted:**
   - The owner's `controlOnly` still holds the owner's `CONTROL` id to the doors' placeholder. The deploy kit fills every namespace id by binding name (`deploy/deploy.ts` `deployedConfig`), so that id agreement checks nothing live. It is the owner's own store, not a bound Worker's fact, and is owed to lane O with the owner's config guard.
   - The gateway's `flags.exactly` stays. The Worker holds every credential's key, so any added flag gets a review (its guard's "an extra flag" probe), and C5b owed no change to it.
