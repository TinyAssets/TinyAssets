# Doorbell acceptance as built (2026-11-18)

The owner used any HTTP 2xx as evidence that a doorbell started a wake. xAI documents HTTP 200 as the only response that starts a **Grok Bot routine**. The separate consumer Automation can answer 202, but uses another endpoint and credential. OpenAI's MCP receiver acknowledges delivery with any 2xx. [Bot routines](https://docs.x.ai/grok-bot/skills-routines-and-automations) · [Consumer Automations](https://docs.x.ai/grok/automations/webhooks) · [MCP Events](https://developers.openai.com/plugins/build/mcp-events)

The existing wake-kind records now specify the accepted status or range. Each callback keeps its actual HTTP status. The owner counts a wake as sent only when at least one receiver accepted it under its own rule. The same test applies when a sibling callback asks to retry after a 429. The existing 2xx rule continues for Claude and ChatGPT. A 201 or 202 from a Grok Bot routine records a failed wake and preserves its status. The owner's hourly pacing still counts a claimed send attempt. A failed receipt leaves its mail unwoken. A previously settled wake is never sent again by this change. The November 18 vendor source reread is recorded separately on `codex/vendor-wake-evidence`.

A Worker regression registers a Grok Bot, delivers a message to its inbox through the owner, runs the alarm, and reads back both the wake receipt and the callback status for 200, 201 and 202. Paired Grok callbacks show that only a 200 alongside a 429 wakes the mail and only the 429 callback remains owed. Existing MCP Events cases exercise acceptance of 202 and a mix of 202, 429 and 410. These are local Worker fixtures.
