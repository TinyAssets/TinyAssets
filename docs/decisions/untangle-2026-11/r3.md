# R3 as built (2026-11-14)

R3 is lane R's third PR, the operator path's modes `control` and `owner` (d3 §G; `operator_research.md` §2.1, §2.2, adopted whole). It blocks the cutover (d3 §C2). The channel is R2's (`r2.md`).

1. **The modes are rows of the deploy kit and options of `platform-deploy.yml`, not a second workflow.** The research names a new `platform-operator.yml` sharing the deploy's concurrency group. That file would copy the deploy workflow's plan and apply jobs, their checkout and install steps, and the production environment's secrets, and the copy could drift. The kit already runs every mode from one table (`MODES`), and the deploy workflow already holds the concurrency group, the main-only `production` apply job and `OPERATOR_KEYRING`. So the workflow gains four inputs, `set`, `replace`, `owner` and `act`, each handed to the kit as the option of its name. The apply job's `if` now names the two modes that need the pair (`dark`, `routes`) instead of listing the ones that don't, so a new mode that deploys nothing needs no edit there. `ci/guards/environment.test.ts` needs no change: no new workflow reaches `production`.
2. **A mode declares the options it reads (`Row.own`), and refuses every other mode's.** `record: boolean` was one mode's flag. The table `OWN` in `deploy.ts` names each mode-owned option (`--record`, `--set`, `--replace`, `--owner`, `--act`), what it is, and whether a mode reading it needs it. `parse` checks and reads each before any step, as it did `--record`. `--record`'s refusals now read "mode handback needs --record: …", "--record is …" and "mode X takes no --record: it is mode handback's" (the stale test strings changed with them).
3. **`control`'s edits are general, not one rule per field.** `--set` takes edits separated by white space: `<path>=<value>`, `<path>+=<value>` and `<path>-=<value>`, where the path is the record's keys joined by dots and the value is JSON where it parses as JSON (`5`, `true`, `[]`) and otherwise the text itself (`on`, an owner's id). A list holds each value once. The kit knows nothing of the record's fields: `parseControl`, every reader's parser, decides the result whole. So the control record is described in `contract/src/control.ts` and nowhere else. A field the edits can't remove, and a record that is missing or malformed, take `--replace`, the whole record as JSON, which the edits then start from. That is the research's "replacing it needs `--replace`", given the record as its value so a dispatch input can carry it.
4. **The plan is each leaf's difference** (`differences`: a nested field by its dotted path, a list whole), from the live record as KV holds it. The plan job runs the same steps, because the Cloudflare token reads KV. A record that is already as asked changes nothing and keeps nothing.
5. **The previous record is kept at `deploy:control:<run id>`, once per run.** A re-run attempt finds its run's key there and keeps it as it is, as `routes` keeps its route record, so the kept record is always the one before the run. A missing record keeps nothing, and the plan says so. The write is then read back through the API and held to what was written, or the run stops loudly.
6. **X4's `closedToAll` is not used.** X4 (#5574) has not merged. `control` needs only the parser. Its proof checks the result with the contract's own `outsideOpen` and `ownerOpen`.
7. **The ops and their args are one table in the contract** (`OPERATOR_OPS` in `contract/src/operator-message.ts`). It names each op the channel takes and its args' names exactly. The doors' `OPS` is typed by it, so an op in one is in the other. The kit's `--act` grammar (`tier=<tier>`, `suspend=<reason>`, `lift=<reason>`, `admit`) is read from it. The doors refuse args that aren't exactly the op's as `invalid`. An arg's value is left to the owner door, which already checks it (`tierName`, `SUSPENSIONS`), so no check is copied.
8. **Each op calls a door that already exists, through `bindPlatformFor`.**
   - `owner.tier` calls `tierSet` with its args as the request.
   - `owner.suspend` and `owner.lift` call `admissionSet` with `{reason, suspended}`.
   - `owner.admit` calls `authorize.ts`'s `admit`, now exported and returning the object's admission: the object first, then the directory's `o:` record. Sign-up and the operator share that one admit; it isn't copied a third time beside the import's.
   - Each answer is the owner door's own answer: the tier, or the admission and its reasons.
   - Each op is idempotent from the owner's state, and a redelivery after the op but before the answer leaves the owner as one delivery did (proved).
9. **`owner.state` is owed** (r2.md item 1 allowed this). It needs a new owner door (`ownerState`): a `doors.json` row, the `OwnerDoors` method, its `owner-do.ts` method and its handler in `admission.ts`. That is four files, two of them lane O's, and `owner-do.ts` is in T1c-b2's diff. So it isn't a few lines in lane O's files. Until it lands, mode `owner`'s plan says the op it will ask, and the apply job prints the door's answer, which is the owner's state after the op. The doors answer `owner.state` `invalid` today.
10. **The kit waits on `Io.sleep`,** so the tests' clock moves only while the kit waits for an answer. The kit's `Io` is the one `Waiting` the operator's sender takes.
