# Keep a pruned generation's root ahead of its parts across listing pages

The owner rereads the retained generations before every Files sweep page. An export can expire between two reads. Files previously assumed a root sorted onto an earlier page had already been removed if that page's descendants were now eligible. A root retained on the earlier page can then name a part that Files has deleted.

On main f934871ad and local integration eff491215, the original owner, all 18 SQL migrations and Files service were exercised with an ordered synthetic bucket and the normal 1,000-key list limit. The first page retained a root and 999 of its 1,003 parts. After expiry the second page removed four parts while the root remained. A later pass removed the root. Held, previously expired and unopened export controls preserved the promised ordering. All four scenarios ran on both trees with Node 22 and 24.

Files owns the object key grammar, the delete order and the list cursor. On a continuation, only the first listed generation can span the boundary with its root on an earlier page. If this generation is no longer retained, remove its canonical root with the roots on the current page before deleting any descendants. Repeating a root delete is idempotent. A page that begins with a descendant can contain at most 999 listed roots, so the existing batch limit still holds. The returned count remains the number of eligible keys on the listed page. The owner consumes only the cursor. Partial failures retry through the existing sweep obligation.

The Files RPC and its caller need no new state. Persisting the owner's listing progress across deadlines, namespace changes, and independently due capture is a separate design obligation. A concurrent independent writer that republishes a deleted root needs its own ownership review.

On local 180e98f58, 481 independent paging histories ran on each of Node 22 and 24, totaling 3,010 pages per runtime. Four delete-failure and retry controls passed on each. A boundary page containing one descendant and 999 later roots issued at most 1,000 keys per batch. On main and combined eff491215, 103 of the same 481 histories left a visible root naming a deleted object.

The original nightly copy made eight rclone calls against local synthetic stores in each run. On main and eff491215, on both runtimes, it succeeded with a readable older root despite four missing parts. The actual locator selected the newer healthy generation. On the correction the retired root was absent from the copy. Failure after root retirement left the parts available for a later pass. The stored retry deadline held and all 1,003 remaining parts disappeared on retry. These four candidate runs made 32 further local rclone calls. They measure the owner sweep and copy ordering. External restore and writer coordination remain separate.

The permanent Worker regression failed on main f934871ad because the root was still readable immediately before its second part was deleted. On c3e088d84 it passed together with the original fixed-retention paging case. Across the ordinary and large selections, all 169 Files tests passed on that commit, along with scoped Node 22 TypeScript. On local combined b0e6e6137 the two paging cases and all four owner cadence regressions passed, as did the Files scoped typecheck. An external copy-back writer can still reintroduce a retired root. Its owner must cover interruption after the write.
