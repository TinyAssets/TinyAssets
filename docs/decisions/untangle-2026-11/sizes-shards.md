# sizes-shards as built (2026-11-14)

`archive-mail-sizes.md` §4 owed this split to `untangle/sizes-shards`. The figures below come from #5604's measured merge-group run, 43646845463 (`sizes-report-0`, `sizes-report-1` and `tests-report-0`).

1. **`archive-mail.test.ts`'s large tests are split by subject, each test moved whole.** The file was one Vitest file of about 470 s of large tests, so it was owner 2/2's critical path, and no shard split could spread it. Each test, and each `describe` around it, moves verbatim:
   - `archive-move.test.ts`, the lane's moves: the move from half the hot ceiling, the units held on the pool, the aborted move, the body of control characters, the lane's failures and the full owner's archive. 163.8 s.
   - `archive-read.test.ts`, archived mail read back: the archived parent, the chain reads (N9, N10, paged bodies), export v3 and the export across a move. 89.5 s.
   - `archive-merge.test.ts`, stragglers merged: the schema's overlap refusal, the lone straggler, the merge's byte budget and the worst merge. 49.3 s.
   - `archive-erasure.test.ts`, a deleted agent's archived mail: the drop at once, the `maxAgentRows` wait, the rewrite kept byte for byte, the two deletions, the bounded rewrite and mail moving during a long purge. 130.1 s.
   - `archive-mail.test.ts` keeps the record format: the segments' encoding and ids, a message's counted bytes, the tail's seal at production's limits (5.7 s) and `TIER_STORAGE_MAX`.
   - "the ledger at its production limits" tests the ledger's two ceilings, not the archive, so it moves to `ledger-bounds.test.ts` (32.1 s), whose header named that file for it. `ledger.ts`'s two comments that cite it name its new file.
2. **One support module, `archive-support.ts`.** It holds `seeded()` and every helper more than one file uses. A helper only one file uses stays in that file (`watchMoves` in erasure, `MUSE_ID` in read). The old file kept its own `Rig` type, which is now `ledger-support.ts`'s, and a `RESULT_CHARS = 50_000` copy of `contract/src/encoded.ts`'s, which is now imported.
3. **Vitest's shards can't be steered, and the split doesn't need them to be.** `--shard` sorts every file of the run (81 here, the tag filter applies later) by the sha1 of its path and cuts the list into contiguous slices. Only a file's name moves it, and a name chosen for its hash would be a hidden link. Vitest's own sequencer puts `archive-read` in owner 1/2 and the other three, with `archive-mail`, in 2/2. Inside a shard, though, three workerd files run at once: in the measured run, owner 2/2 ran `archive-mail`, `collections` and `export` side by side. So a shard takes at least the longer of its longest file and a third of its total, and a schedule of three files at a time gives its time.
   - **owner 2/2:** 535.6 s of large tests, the longest file 163.8 s. Scheduled three at a time in Vitest's order (the larger file first, with no cache in CI), about 206 s, against about 485 s before.
   - **owner 1/2:** 203.8 s of large tests, the longest file 89.5 s, about 90 s.
4. **No watchdog or budget changes here.** `platform-sizes`' watchdog and the large budget are re-derived from CI's own shard times and reports after this merges. That's the `live:` re-derivation already owed by #5602 and #5604, which now reads the split shards.
5. **Product fix: a door's sync leaves a job that is already due.** The split exposed it. "mail moves during a long purge > keeps pace" failed once with all six files side by side: no mail move seen, with "Skipping job owner-schedule/archive: previous execution still running" in its log.
   - **The cause.** Lifecycle keeps a job's single-flight mark in its row (`cf_agents_jobs.running`). Its `push()` of the same id sets `running = 0` and `execution_started_at = NULL`, as "newer durable intent". `Schedule.#set` pushed a door's sync whenever the job's time or set-for time differed from the rows' next work. The archive lane's `next()` is `now` while it has work, so a door's sync during a running pass always pushed. That cleared the mark, and the next overlapping alarm drove a second pass beside the first.
   - **The evidence.** A probe held an archive pass at its first `putChunks` at the FILES gate, then ran an overlapping alarm, as `drainDue` and the deadman do:
     - With no door between, the mark stays (`running` 1), the alarm skips, and one upload is held.
     - With one small post between, `running` goes from 1 to 0. The alarm starts a second pass, so two uploads are held at once, and the second pass's `moveBegun` replaces the first's `archive_moves` row (intent `5766c49c…` becomes `07a8628e…`), both moving the same batch.
     - In "keeps pace", the diagnostics showed uploads held with no `archive_moves` row: one pass's `moveEnded` had taken the other's. That is how `watchMoves` lost the mail move.
     - With the fix, the same probe holds `running` at 1 and one upload.
   - **The fix** (`schedule.ts` `#set`). For a door (`hold === undefined`), a job whose time is at or before `Date.now()` (Lifecycle's due clock) is left as it is, neither pushed nor cancelled. A running job is always one of these, since Lifecycle drives only rows with `time <= now`. The job runs, or is running, and its run sets it from the rows at its end: `onJob` calls `this.#set(job.fn, heldUntil(answer))`, and a run's set (`hold` null) always writes. A job not yet due keeps the old rules. A door moves it earlier when the rows have earlier work, and later when it isn't held. A job held later than its work stays held unless the rows have earlier work. It's cancelled when the rows have none.
   - **The coordinator's proposed rule, `job.time <= due`, was not taken.** It would also leave a future job that is earlier than the rows' next work, so a door could no longer move a not-yet-due job later. The schedule test "is never set before now, nor before the lane's work" shows that. The rule taken covers only the jobs that can be running.
   - **Lane by lane** (`owner-do.ts`: `new Schedule`). Each lane's `next()` is never before `now`. Each lane's run reads its own rows, so a due job left for its run loses nothing. At most it runs one pass that a door would have deferred.
     - `wakes`: the soonest due wake, at least `now`, or none. Its pass takes only the wakes due then.
     - `files`: `now` for a retention change or early garbage, else the soonest expiry or prune plus `HOUSEKEEPING_SLACK_S`, or none. Its pass takes only due rows.
     - `connections`: the soonest expiry, pending deadline or revoke, at least `now`, or none. Its pass sweeps what has expired and revokes only due rows.
     - `runs`: `now` for mail no run has taken, else the soonest of the runs' own next and the leases' re-apply, or none. Its pass reads its waiting rows.
     - `manifest`: a retry, a prune or the nightly generation, at least `now`, or none. Its pass checks that it is due before it opens a generation.
     - `sandbox`: `now` for unmetered runs, or the open spans' read time or a retry, at least `now`, or none. An early pass is one meter read, idempotent by its cursor.
     - `archive`: `now` while there is mail to move, a purge or a compaction, or none. Its pass picks only what is due.
     - `starter`: `now`, or a retry, while the package isn't reconciled, or none. Its pass returns unless `next(now) <= now`.
   - **Nothing relied on a door's push clearing the mark.** The owner never reads `running`. The only same-id pushes are the schedule's `#set` and the erasure and relay jobs (`erase.ts`, `relay.ts`), which are not single-flight lanes and don't go through `#set`. No lane needs a running pass's drive result thrown away when newer work arrives: `onJob` returns `undefined` only after its own set has written the job from the rows as they stand at the run's end, which carries any door's change.
   - **Production impact.** Lifecycle's own comments name overlapping `alarm()` calls in production: the 30 s deadman pre-arm (`DEADMAN_ALARM_DELAY_MS`) and the platform's re-fire. A lane pass may run up to `LANE_PASS_S` (45 s). So on main, any door whose sync met a long pass with work still due (a post during a purge or a move, a file change during housekeeping) could let the next overlapping alarm run that lane a second time beside it. The archive's two passes could then move the same batch, each replacing the other's `archive_moves` row.
   - **Tests.** `schedule.test.ts` "stays single-flight past a door" holds a run on a promise the test controls, runs a door's sync, then an overlapping alarm. On main, `running` reads 0 after the door, and without that check the lane ran twice at once (`[2, 2]`). With the fix, `running` is 1 and the lane runs once. "is left alone by a door once due" fails on main, which cancels the job. "is moved earlier by a door whose rows have earlier work, and later while not yet due" holds the rules that stay. "is never set before now, nor before the lane's work" now sets its fractional-millisecond job on a second lane, because its first lane's job is due by then.
