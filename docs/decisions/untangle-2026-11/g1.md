# G1 as built (2026-11-15)

G1 is lane G's first PR: R5′ (d3 §O5), which removes G-H13 (`MISTRAL` a near copy of `COMPLETIONS`), G-H11 (four lists of pi-ai API ids that had to agree) and G-SP5 (`provider === "custom"` in the gateway).

1. **One per-API table, in the contract.** `contract/src/api-rules.ts` `APIS` keys one row by pi-ai API id: `takesFetch` (whether pi-ai's adapter takes `options.fetch`), `declared` (whether a declared endpoint may speak it) and `rules` (its `ApiRules`). The table is the module's own: callers read it through `supportedApis()`, `apiRules(api)`, `takesFetch(api)` and `declaredApi(api)`, never the row's shape, so `apiRules`' callers in the gateway and the owner are unchanged.
   - `SUPPORTED_APIS` is gone: "the gateway runs it" is "it has a row" (`egress-scope.ts` `supported`), so the gateway test that held the two lists equal goes with it.
   - `GLOBAL_FETCH_APIS` is gone: `meter.ts` reads `takesFetch`.
   - `CUSTOM_APIS` is `catalog.ts` `DECLARED`, typed `satisfies Record<DeclaredApi, …>`, where `DeclaredApi` is derived from the table's `declared: true` rows. Marking an API `declared` without its adapter, or holding an adapter for an API not marked, fails `tsc` (both mutations shown). The adapter's lazy import stays in the gateway, as R5′ decided: the contract imports no pi-ai code.
2. **`MISTRAL` is `{ ...COMPLETIONS, usage: [], served: null }`.** Its values are unchanged (the table dumped before and after is byte-identical), so no metering rule or wire answer moves. The module-state rule (`ci/kit/module-state.ts`) refused the spread, as u3-services found; it now accepts an object literal that spreads a name, by the same reasoning that lets it hold one (the name is a `const` the rule checks where it is bound). Spreading a call (`{ ...build() }`) and an array spread stay refused. This is lane C's file: one rule line and its comment, with a case each way in `ci/guards/module-state.test.ts`.
3. **A declared endpoint is sealed only on a declared API** (the one wire change). Before, a `custom` source on `mistral-conversations` sealed, and every use then failed `unsupported_source` in the catalog. Now sealing it is `invalid_source`; a built-in Mistral source still seals. `gateway/test/credential.test.ts` "seals a declared endpoint only on an API the gateway holds a declared adapter for" fails without it.
4. **G-SP5: the gateway branches on the sealed shape, not on a provider value.** `providerFor` takes a declared endpoint's provider when the upstream carries `models` (the seal holds `models` present exactly when the provider is `custom`), and names the pi-ai provider by the sealed `upstream.provider`, not a second `"custom"` literal. The contract's `upstream` grammar keeps `provider === "custom"`: it is the one place that defines a declared endpoint.
5. **The use-time API check in `providerFor` goes.** Every `Upstream` the gateway holds was opened through `upstream()` (`credential.ts` `credential`), which checks the API against the table, so a blob sealed on an API the gateway no longer runs is refused `credential_refused` at open; the catalog's second check could not be reached. The spec's scenario said the catalog refuses it `unsupported_source`; it now says what happens, and a credential test holds it. `declaredProvider` keeps a `declaredApi` test, which the types need to index `DECLARED`; failing it answers `unsupported_source`, as a built-in provider pi-ai lacks does.
6. **Callers outside lane G, one or two lines each:** `sources/guards/sources.test.ts` and `owner/test/connections.test.ts` read `supportedApis()` for `SUPPORTED_APIS`; `sources/src/schema.ts` and `gateway/src/egress.ts` comments name the table.
