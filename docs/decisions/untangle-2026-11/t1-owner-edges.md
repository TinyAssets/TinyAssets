# T1's owner edges as built (2026-11-15)

T1 (#5515 to #5588) moved the owner's tests onto the object's own wiring, but five owner test files still reached another Worker's internals, each an `owed` B23 entry in `owner/guards/rules.ts`: `connections.test.ts`, `export.test.ts`, `gateway-support.ts`, `holds.test.ts` and `runs-authority.test.ts`. This PR moves each onto that Worker's front door, as T2a moved the doors' (`t2.md` items 2 to 5), and deletes the five entries. The egress memory leg's entry stays, for T3 (`tasks.md` lane T).

1. **A blob sealed under the older kid comes from the gateway's own front door.** The test config runs the real gateway twice more beside the owner, from its real entry, each with its config's every binding and one changed secret:
   - `CONNECT_OLDER`: the gateway's `ConnectGateway` on the same ring with the older kid `k1` active, as a Worker still sealing under it mid-rotation. Its `seal`, `exchange` and `sealDoorbell` make a blob sealed before a rotation. The ring keeps `k2`, since the files Worker on such a ring must open the owner's key before it wraps it again (item 3).
   - `GATEWAY_RETIRED`: the gateway's default entrypoint on the ring with `k1` retired. Its `reseal` and `resealDoorbell` resolve only for a blob that opens without `k1`, which is what "it still opens once the old kid is retired" means.

   `gateway-support.ts` `connectAt(kid)`, `keySealed`, `tokensSealed`, `opensRetired` and `doorbellOpensRetired` are those calls. `keyring`, `sealedAs`, `underOlderKid`, `retired`, the test's copy of the ring (`TEST_KEYRING`) and every import of `gateway/src/keyring.ts` and `credential.ts` go.
2. **An OAuth credential is bought by the gateway's exchange, never built by hand.** A test that needs a refresh token the fake answers in its own way (`rt-dead`, `rt-down`, `rt-lapsed`) passes the code `good-code:<token>`, and the fake's token endpoint issues that refresh token (`gateway/test/fake-upstream.ts`, one rule). The fake answered those tokens before; it now issues them too. `good-code` alone still buys `rt-1`, and no test sent a code with a colon before, so every other test's exchange is unchanged. That is the one line in lane G's files.
3. **A data key wrapped under the older kid comes from the files Worker's own front door.** `FILES_OLDER` is the files Worker on its ring with `k1` active. Its `rewrapKey` gives the owner's key under `k1` (`export.test.ts` `olderKey`), in place of `files/src/datakey.ts` `rewrap` over the test's copy of the ring (`FILES_TEST_RING`, deleted). The manifest reads go through `env.FILES`, the contract's `ChunkStore`, in place of a cast to the files Worker's class. The `bucket()` pass-through goes with the cast.
4. **What is inside a blob is the gateway's to test. The owner's tests assert which blob the owner kept.** No front door opens a credential, by design. So each `open(keyring("k2"), …)` becomes an assertion on the blob the owner stored, against what crossed its doors:
   - after a refresh, the stored blob is the one every call was admitted with (`egressOpen`'s `blob`), it opens at version 2 once `k1` is retired (so it is the refresh's, not the old blob kept), and it is never the reseal's;
   - a compare-and-swap of concurrent reseals keeps one of the blobs the gateway resealed;
   - after the sweep, the stored blob opens once `k1` is retired;
   - the exchange's tokens are in the blob alone: the gateway refreshes from it, and no row holds `rt-1` or `at-1`.

   That the tokens or the key inside are the ones sealed is the gateway's own suite's job (`gateway/test/keyring.test.ts`, `oauth.test.ts`).
5. **A model record is the one the gateway's setup check lists** (`connections.test.ts` `servedRecords`). The test asks for each built-in catalog by its provider and an API the gateway runs, once a file, in place of `gateway/src/catalog.ts` `recordOf` over pi-ai's models. The set is now the records an owner can be handed. Before, it also held the chat models of the APIs the gateway refuses (Bedrock, Vertex, `openai-codex-responses`, `pi-messages`), which no setup check ever lists. The gateway lists a catalog whatever its base URL, and several built-in base URLs are templates (`{location}`, `{CLOUDFLARE_ACCOUNT_ID}`), so each catalog is asked at one fixed URL.
6. **A tampered chunk is the files Worker's refusal at the FILES gate** (`holds.test.ts`). Only the files Worker opens a chunk, and only it rechecks a range's whole chunk against its hash (`files/test/chunks.test.ts`, "reads every range from its whole chunk, its hash rechecked (review L7)"). A chunk that still opens but holds other bytes can be made only with the data key. So the owner's test arms the gate to refuse the read with the files Worker's own message, and holds the owner's half: a ranged read fails loudly with that reason and answers no text. `files/src/datakey.ts`, `keys.ts` and the test's `BLOBS.put` go from it.
7. **The socket's upgrade is the contract's shape** (`runs-authority.test.ts`): `SOCKET_URL` and the three headers of `contract/src/socket-shape.ts`, the module both sides spell it from, in place of `doors/src/binder.ts` `socketRequest`. The object's own door is under test, so the test sends what the doors send.
8. **Measured:** the three catalog tests take 0.6 to 0.8 s each here, with the 49 served catalogs asked once a file. The six touched files' 213 non-large tests pass in 79 s. The owner config now bundles the gateway three times and the files Worker twice.
